# 功能扩展方案（参照芋道 yudao-cloud）

> 版本：1.0.1　　日期：2026-11-16
> 参照对象：[YunaiV/yudao-cloud](https://github.com/YunaiV/yudao-cloud)（MIT 协议）`master` 与 `master-jdk25` 分支，2026-11-16 的模块与接口清单；前端参照 [yudao-ui-admin-vue3](https://github.com/yudaocode/yudao-ui-admin-vue3)（MIT）。
> 原则：**柒衡 ERP 已有的功能不改**，只新增芋道有、本项目没有的模块和功能点。
> 配套：《开发计划》（版本排期与任务清单）、`docs/详细设计/`（各模块的表结构、接口、页面设计）、《企业级演进规划》（总体方向与 AI）、《优化文档》（技术优化）。

## 1. 结论先说

1. **芋道的 ERP 模块本身比柒衡简单。** 它的采购、销售、库存、收付款是“审核 / 反审核直接改库存和余额”的做法，没有预留、累计确认应收、未清项核销、冲销、期间关账和对账。柒衡在这些方面更完整，**不要用芋道 ERP 的单据模型替换现有实现**。从芋道 ERP 只需补 6 个小功能点（第 3 节）。
2. **真正值得参照的是 ERP 周边模块**：工作流（BPM）、CRM、财务总账（FMS）、仓储作业（WMS）、生产执行（MES），以及系统管理里的部门岗位、字典、公告、站内信、短信邮件模板、登录日志、定时任务管理、API 日志、数据大屏、AI 管理后台。
3. **技术上有一个关键信息**：芋道 `master-jdk25` 分支使用 Spring Boot 4.1.2（与本项目相同）、Flowable 8.0.0、Spring AI 2.0.1。说明这两个依赖可以和现有框架共存，工作流和 AI 的选型可以直接以此为依据。
4. **不照搬芋道的架构。** 它是 Spring Cloud Alibaba 微服务 + MyBatis Plus；柒衡继续用模块化单体 + JdbcTemplate + 现有的命令、幂等、加锁顺序和冲销规则。参照的是**功能清单、字段设计、页面交互**，不是代码结构。
5. **不纳入**：商城、会员、微信公众号运营、IoT、IM、HRM、OA、PMS。它们不是 ERP 的核心，需要时优先对接企业微信 / 钉钉 / 飞书或专业系统。

## 3. ERP 补充功能点

芋道 ERP 的单据和字段逐一对照后，柒衡缺少以下 6 项。全部是**在现有表和接口上追加**，不改变现有单据状态和过账规则。

| 编号 | 功能 | 芋道依据 | 柒衡做法 |
|---|---|---|---|
| X-01 | 销售员、采购员 | `ErpSaleOrderDO.saleUserId` | 销售订单、发货、退货、收款增加可选的 `sales_user_id`；采购订单、收货、付款增加 `buyer_user_id`。默认取制单人，可改。报表增加“按业务员”汇总；CRM 上线后用于业绩统计 |
| X-02 | 其它入库、其它出库 | `ErpStockInDO`、`ErpStockOutDO` | 新增“其它入库 / 其它出库”单据（赠品入库、样品领用、借出、内部领用等），可选往来单位和收支项目。走现有库存移动、成本和期间规则，草稿 → 提交 → 审核 → 过账，错误用冲销更正。与现有六类库存调整并列，不合并 |
| X-03 | 最低售价控制 | `ErpProductDO.minPrice` | SKU 增加 `min_sale_price`。订单行单价低于最低价时，按公司参数选择“提示”或“需要审批”（审批流上线后进入流程；之前沿用现有订单审批） |
| X-04 | 保质期、重量、规格 | `expiryDay`、`weight`、`standard` | SKU 增加 `shelf_life_days`、`weight_kg`、`spec`。保质期在批次管理（第 9 节）上线后用于到期预警和近效期先出 |
| X-05 | 默认结算账户 | `ErpAccountDO.defaultStatus` | 每家公司可设一个默认收款账户、一个默认付款账户，登记收付款时自动带出 |
| X-06 | 首页金额趋势 | `ErpSaleStatistics`、`ErpPurchaseStatistics` | 工作台增加“今日 / 昨日 / 本月 / 本年”销售与采购金额，以及近 12 个月趋势图；数据来自已过账事实，按用户数据范围过滤，需要 `report:sales_summary` / `report:purchase_summary` 权限 |

**不采纳的芋道做法**：反审核直接回滚库存和余额；订单上直接记“定金金额”而不形成预收未清项；金额只保留到“元”的两位小数而不区分单价精度。这些与《业务规则》冲突。

## 6. 工作流（BPM）

### 6.1 功能范围

按芋道 BPM 的功能清单，分两期实现：

| 一期（M11） | 二期（M14） |
|---|---|
| SIMPLE 设计器（仿钉钉 / 飞书的节点树） | BPMN 设计器（复杂流程） |
| 审批人：指定用户、角色、部门负责人、发起人自选、上级 N 级 | 子流程（同步 / 异步） |
| 会签、或签、依次审批 | 包容分支、路由分支 |
| 条件分支（金额、往来单位、部门、单据类型字段）、并行分支 | 触发器节点（HTTP 回调、更新业务数据） |
| 抄送、驳回（发起人 / 上一节点 / 任意节点）、转办、委派、加签、减签 | 延迟节点 |
| 撤销、管理员终止 | 流程报表、审批效率统计 |
| 超时自动处理、自动提醒（站内信 / 邮件 / 短信） | 表单字段级权限（只读、可编辑、隐藏） |
| 我的申请、待办、已办、抄送我的 | 通用审批（Z-05 动态表单） |

### 6.2 与现有单据的衔接

1. **业务单据是事实来源，流程只是审批过程。** 销售订单、采购订单、退款、冲销、库存调整、其它出入库、价格低于最低价等，在“提交”命令中判断该单据类型是否配置了流程：有就发起流程实例，单据进入“审批中”；没有就沿用现有单级审批。
2. 流程结束时回调业务命令（审批通过 / 驳回），回调走现有幂等记录，重复回调不会重复执行。
3. **硬规则不可被流程配置绕开**：经办与复核分离、两人经手、期间关闭、可用量不足等仍由业务服务校验；流程配置只能增加审批环节，不能减少。
4. 单据详情页显示流程进度（已审、当前节点、待审人），与现有操作记录合并展示。

### 6.3 技术选型

| 方案 | 说明 | 结论 |
|---|---|---|
| Flowable 8.0.0 | 芋道 `master-jdk25` 已在 Spring Boot 4.1.2 上使用；成熟的 BPMN 引擎，支持会签、驳回、子流程等全部能力；自带约 50 张 `ACT_*` 表 | **采用** |
| 自研轻量引擎 | 表少、可控，但会签、驳回到任意节点、加减签、子流程要自己实现和测试 | 不采用 |

实施要点：

- 先做 2—3 天技术验证：Flowable 8.0.0 + Spring Boot 4.1.2 + MySQL 8.0.46 + 现有 `JdbcTemplate` 事务管理器在同一事务中提交（业务单据状态与流程实例必须同成同败）。
- Flowable 表由 Flowable 自己的升级机制管理，单独配置 `flowable.database-schema-update`，生产环境设为 `false`，表结构变更随版本手动执行并写入《部署说明》；本项目自己的表继续走 Flyway。
- SIMPLE 设计器的节点树 JSON 在后端转换为 BPMN XML 再部署，与芋道做法一致；前端设计器组件可参照 `yudao-ui-admin-vue3` 的实现（MIT，复制代码时保留其版权声明，见第 15 节）。
- 新增包 `cn.erp.workflow`，对外只暴露“发起、查询进度、处理任务”三类服务，其他模块不直接调用 Flowable API。

### 7.2 与 ERP 的衔接

```text
线索 ──转化──► 客户（= 往来单位，角色“客户”）──► 商机 ──► 合同（审批）
                                                         │
                                         生成销售订单 ◄───┘
销售订单 ─► 发货 ─► 签收（应收） ─► 收款单 ─► 核销
                                       ▲
          回款计划 ── 回款登记（关联收款单）┘
```

- 客户与往来单位**一份主数据**：CRM 字段放在扩展表 `crm_customer_profile`（主键即 `business_partner.id`），现有往来单位功能不变。
- 合同生成销售订单时带出客户、产品、价格；订单后续的发货、签收、收款完全走现有流程。
- 回款统计取已确认收款和核销结果，不重复记账。

## 8. 财务总账（FMS）

对应《企业级演进规划》F-01、F-02，芋道 FMS 的功能可以作为字段和页面的参照。

| 功能 | 说明 | 与现有衔接 |
|---|---|---|
| 账套 | 一个公司一个账套，记录启用期间、会计准则、本位币 | 与现有 `company`、`accounting_period` 一一对应，不另建期间 |
| 科目 | 预置企业会计准则科目，可增加下级明细科目；设置余额方向、是否现金类、辅助核算 | 现有 `ledger_account` 的业务科目映射到正式科目 |
| 辅助核算 | 客户、供应商、部门、员工、项目、存货、自定义类型 | 客户、供应商、存货直接引用现有主数据 |
| 币种 | 本位币 + 外币、汇率 | 第一期只启用人民币，结构预留 |
| 凭证字、摘要库、凭证模板 | 记 / 收 / 付 / 转；常用摘要；常用分录模板 | — |
| 期初余额 | 按科目和辅助核算录入，试算平衡后才能启用 | 业务往来、资金、库存期初已在现有期初功能中，此处做汇总校验，不重复录入 |
| 凭证 | 手工凭证录入、审核、记账、冲销；业务投影凭证只读，可查看来源单据 | **现有业务凭证保持原样**，只是在总账中可见 |
| 账簿 | 总账、明细账、科目余额表、辅助核算余额表、多栏账 | — |
| 结账 | 期末结转方案与模板（结转损益、结转制造费用等），生成结转凭证 | 与现有关账流程合并：业务关账 → 财务结账 |
| 报表 | 资产负债表、利润表、现金流量表，公式可配置 | — |
| 财务指标 | 流动比率、毛利率、应收周转天数等 | 用于首页和驾驶舱 |

## 9. 仓储作业（WMS 补充）

芋道 WMS 的入库单、出库单、移库单、盘点单与柒衡的收货、发货、调拨、盘点功能重合，**这些单据不再新建**。补充以下能力：

| 功能 | 说明 |
|---|---|
| 库区、库位 | 仓库下分库区和库位；库存维度增加库位（现有 `location_key` 已预留） |
| 品牌 | 商品增加品牌主数据 |
| 批次、序列号、保质期 | 现有 `lot_key` 已预留；补批次档案、序列号档案；出库按先进先出或近效期先出推荐批次 |
| 上架、拣货 | 收货过账后生成上架任务；发货前生成拣货任务，按库位路径排序；任务完成才允许过账 |
| 移库 | 同仓不同库位之间移动，不影响成本 |

**货主（多货主仓储）不纳入**，除非以后做第三方仓储业务。

## 10. 生产执行（MES）

芋道 MES 有 127 个管理端接口，规模比现有 ERP 全部业务还大，必须分期。

| 期 | 功能 | 说明 |
|---|---|---|
| 一期：简单装配 | 物料 BOM（多版本、替代料）、生产工单、领料 / 退料、完工入库、生产成本归集 | 满足“组装 / 加工”型轻制造客户；领料和完工走现有库存移动与成本规则 |
| 二期：工艺与报工 | 车间、工作站、工序、工艺路线、生产任务派工、报工、流转卡；委外加工（发料、收货） | 引入工序级进度和工时 |
| 三期：质量 | 检测项与模板、来料检（IQC）、过程检（IPQC）、出货检（OQC）、退货检（RQC）、缺陷记录；质检结果影响可用量 | 来料检可在供应链一期先做（《企业级演进规划》S-03） |
| 四期：设备与排班 | 设备台账、点检、保养、维修；工装夹具；排班日历、班组、班次、节假日；安灯呼叫 | 视客户需要 |
| 计划 | MPS / MRP 运算，生成采购建议和生产建议 | 依赖一期、二期数据稳定后再做 |

编码规则（芋道 `MesMdAutoCodeRule`）做成平台能力，即《企业级演进规划》E-06，供所有模块使用。

## 14. 技术方案

### 14.1 总体架构

继续模块化单体，新增模块以包的形式加入 `erp-server`；AI 按原规划独立为 `erp-ai` 服务。

```text
erp-server（Spring Boot 4.1.2，JDK 21）
  现有：identity  catalog  reference  salesorder  fulfillment  purchasing  receiving
        inventory  accounting  reversal  period  reporting  importing  exporting ...
  新增：org        部门、岗位、部门数据范围（Y-01、Y-02）
        sysadmin   字典、公告、地区、系统参数、登录日志、在线用户（Y-03、Y-04、Y-07、Y-08、Z-01）
        notify     站内信、短信 / 邮件模板与日志、WebSocket 推送（Y-05、Y-06、Z-04）
        scheduler  定时任务登记与管理（Z-02）
        workflow   Flowable 封装、流程设计、待办（第 6 节）
        crm        线索、商机、合同、回款、跟进、统计（第 7 节）
        gl         账套、科目、凭证、账簿、结账、财务报表（第 8 节）
        wms        库区库位、上架拣货、移库、标签（第 9 节；批次序列号放在现有 inventory 包）
        mfg        BOM、工单、领料完工、工艺报工、质检、设备（第 10 节）
        dashboard  经营驾驶舱（第 11 节）
erp-ai（Spring AI 2.0.1）    模型网关、知识库、助手、工具（第 12 节）
erp-web（Vue 3 + Element Plus）  新增页面按模块分包懒加载
erp-mobile（新增，uni-app）    PDA 作业、移动审批
```

- 模块边界用 Spring Modulith 校验：新模块之间只通过公开服务接口和领域事件（现有 Outbox）交互。
- 新模块的单据继续使用现有的单号服务、幂等记录、审计、附件、打印、导入导出和期间屏障。

### 14.2 技术选型

| 领域 | 选择 | 理由 |
|---|---|---|
| 工作流 | Flowable 8.0.0 | 与 Spring Boot 4.1.2 已有同版本组合在用（芋道 `master-jdk25`） |
| 数据访问 | 继续 JdbcTemplate | 与现有正确性代码一致；不引入 MyBatis Plus 的逻辑删除和自动填充，避免和现有规则冲突 |
| 定时任务 | 现有数据库租约 Worker + 管理页 | 不增加 XXL-Job 一类的独立组件，部署简单 |
| 消息 | 现有 Outbox；实时推送用 WebSocket + Redis 发布订阅 | 不引入 RocketMQ / Kafka，单量增长到需要时再评估 |
| 前端 | Vue 3 + TypeScript + Element Plus（现有） | 与芋道 `yudao-ui-admin-vue3` 同栈，流程设计器、CRM 页面交互可直接参照 |
| 图表 | ECharts | 驾驶舱、CRM 统计、工作台趋势 |
| 移动端 | uni-app（Vue 3） | 一份代码生成 H5、安卓 App；PDA 扫码用设备厂商的扫描广播或 H5 摄像头扫码 |
| AI | Spring AI 2.0.1 | 芋道同版本在 Boot 4.1.2 上使用；与《企业级演进规划》第 5 节一致 |
| 搜索 / 向量 | OpenSearch | 商品与单据搜索、AI 知识库共用 |
| 数据库 | MySQL 8.0.46 | 保持不变；新表遵守《优化文档》第 1 节长期约定 |

### 14.3 数据与接口约定

- 新表全部带 `tenant_id`、`company_id`（全局主数据除外）、`created_at`、`updated_at`、`version`；表名按模块前缀：`org_`、`sys_`、`notify_`、`wf_`、`crm_`、`gl_`、`wh_`、`mfg_`。
- 迁移从 V34（当前最大为 V33）开始，一个模块一组迁移；Flowable 表不进 Flyway。
- 接口路径沿用 `/api/v1/{资源}`，例如 `/api/v1/crm/customers`、`/api/v1/gl/vouchers`、`/api/v1/workflow/tasks`；命令型操作用 `POST /{资源}/{id}/{动作}`，与现有单据一致。
- 权限码沿用 `资源:动作`，例如 `crm_customer:view`、`gl_voucher:post`、`workflow_model:design`。
- 每个模块上线前更新《业务规则》《数据库设计》《接口设计》《用户使用手册》。

### 15.2 每个模块的实施步骤

1. **需求确认**：对照芋道演示环境和本文档列出功能点，和业务人员逐项确认要 / 不要，记录到《业务规则》新章节。
2. **数据库设计**：参照芋道对应模块的数据对象字段，按本项目规范改写（租户、公司、版本号、金额精度、CHECK 约束），写入《数据库设计》。
3. **接口设计**：按 14.3 约定写入《接口设计》，明确哪些是命令、哪些会产生库存或账务事实。
4. **后端实现**：先写规则测试，再写服务；涉及库存和账务的部分必须复用现有过账、冲销和加锁顺序。
5. **前端实现**：参照芋道页面交互，按《UI 设计规范》实现，列表、详情、编辑页沿用现有模板组件。
6. **测试**：单元和集成测试；浏览器流程至少一条完整业务闭环；涉及工作流的增加“驳回、撤销、超时”场景；涉及权限的增加越权测试。
7. **文档与发布**：更新《用户使用手册》《更新日志》，按版本号规则发布。

### 15.3 验收示例

| 模块 | 验收场景 |
|---|---|
| 工作流 | 配置“金额 > 5 万需部门经理 + 财务会签”的销售订单流程；提交 → 经理同意 → 财务驳回到发起人 → 修改后重提 → 全部同意 → 订单变为已审批；全过程站内信提醒，单据详情显示流程进度 |
| CRM | 线索转客户 → 新建商机 → 合同审批通过 → 生成销售订单 → 发货签收 → 收款核销 → 回款计划显示已回款；业绩统计与收款金额一致 |
| 财务总账 | 一个月样例业务 + 手工凭证 → 结转损益 → 三大报表；资产负债表平衡，利润表与业务报表毛利一致 |
| WMS | 收货 → 上架到库位 → 拣货按库位路径 → 发货；批次商品按近效期先出；PDA 全程扫码 |
| 生产一期 | BOM 两层、替代料一种；工单领料 → 完工入库；产成品成本 = 材料成本 + 分摊费用，与库存成本一致 |

### 15.4 参照代码的方式

- 两个芋道仓库都是 MIT 协议，可以参照和复用。**复制代码时**（例如流程设计器前端组件），在仓库根目录新建 `THIRD_PARTY_NOTICES.md`，写明来源仓库、文件、版本和 MIT 许可全文。
- 后端业务代码建议**只参照设计、不复制**：芋道的数据模型、状态流转和柒衡的规则不同，复制后改造的成本往往高于按规则重写。
- 芋道演示环境（`cloud.iocoder.cn` 下各模块 preview）可用来确认交互细节；不要把柒衡的真实数据录入演示环境。

## 16. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围过大，单人无法完成 | 长期延期 | 严格按里程碑；MES 只承诺一期；按 15.1 扩充人手 |
| 工作流配置绕开内控 | 两人复核失效 | 硬规则在服务端强制，流程只能加环节（6.2 第 3 条） |
| Flowable 与现有事务不在同一提交 | 单据状态与流程不一致 | M11 先做技术验证；不通过时退回“流程结束后经 Outbox 回调业务命令”的最终一致方案 |
| CRM 客户与往来单位两套数据 | 客户信息不一致 | 一份主数据 + 扩展表（7.2） |
| 照搬芋道 ERP 的反审核做法 | 账实不符、对账失败 | 第 3 节明确不采纳；代码评审时检查 |
| 生产模块复杂度被低估 | 成本核算错误 | 一期只做简单装配，成本规则先写进《业务规则》并用样例逐分核对 |
