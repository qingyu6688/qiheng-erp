# 05 平台二期（1.6.0）

> 对应：《企业级演进规划》E-04、E-05、E-06、E-08；工作流二期见 02。
> 新增包：`customfield`、`coderule`、`openapi`；单点登录和 MFA 放在现有 `identity` 包中新增类。

---

## 1. 单点登录与 MFA（E-04）

### 1.1 范围

- OIDC（企业自建 IdP、Keycloak、Azure AD / Entra ID、阿里云 IDaaS 等）
- LDAP / Active Directory（账号密码由目录服务校验）
- 企业微信、钉钉、飞书扫码（OAuth2，复用 0.9.0 微信扫码的 state 绑定会话、回调同站校验做法）
- MFA：TOTP（验证器 App）；可选短信 / 邮箱验证码作为第二因素
- 与 0.9.0 多方式登录合并为统一身份模型

### 1.2 统一身份模型

现有 `user_login_identity`（method 为 sms / email / wechat）扩展为通用身份表：

- 新迁移把 `ck_login_identity_method` 扩展为 `sms / email / wechat / oidc / ldap / wecom / dingtalk / feishu`。
- `subject` 存外部唯一标识：OIDC 为 `{issuer}|{sub}`，LDAP 为 DN 的规范化形式，企业微信为 `{corpId}|{userId}`。
- 渠道配置沿用 `tenant_login_provider`，`method` 同步扩展；密钥用 O-21 的子密钥加密。

| 新表 | 关键字段 |
|---|---|
| `user_mfa` | `tenant_id`、`user_id`、`type`（totp）、`secret_cipher`、`recovery_codes_hash`（JSON）、`enabled_at`、`last_used_step` |
| `tenant_security_policy` | `tenant_id`、`mfa_required_roles`（JSON）、`password_login_allowed`、`sso_auto_provision`、`sso_default_role_id`、`version` |

### 1.3 登录流程

```text
OIDC：/api/v1/auth/sso/{providerId}/start → IdP 授权（PKCE + state + nonce）
      → /api/v1/auth/sso/callback → 校验 id_token（签名、iss、aud、exp、nonce）
      → 按 subject 找 user_login_identity
          ├─ 找到：进入 MFA 判断 → 建立会话
          └─ 找不到：tenant_security_policy.sso_auto_provision
                ├─ 开启：按邮箱匹配现有用户并绑定，或新建用户（默认角色，状态待管理员启用）
                └─ 关闭：提示联系管理员绑定
LDAP：登录页选择“企业账号” → 服务端 bind 校验 → 同上
```

- MFA：用户角色在 `mfa_required_roles` 中，或用户自己开启了 MFA 时，第一因素通过后会话处于“待二次验证”状态，只能访问 MFA 接口；TOTP 校验通过后才升级为完整会话（重新生成会话 ID）。
- TOTP：30 秒步长，允许前后各 1 步，`last_used_step` 防重放；10 个一次性恢复码（只存哈希）。
- 管理员可以重置用户 MFA，写审计。

### 1.4 接口与页面

| 接口 | 说明 |
|---|---|
| `GET /api/v1/auth/methods?tenantCode=` | 扩展返回已启用的 SSO 列表（名称、图标、类型） |
| `GET /api/v1/auth/sso/{providerId}/start` | 发起 |
| `GET /api/v1/auth/sso/callback` | 回调 |
| `POST /api/v1/auth/ldap/login` | LDAP 登录 |
| `POST /api/v1/auth/mfa/verify` | 二次验证 |
| `/api/v1/account/mfa/*` | 个人开启、关闭、查看恢复码 |
| `/api/v1/sys/security-policy` | 安全策略，权限 `tenant:security_policy` |

- 登录页：企业编码之后显示可用的登录方式（账号密码、各 SSO 按钮、企业账号）；“仅允许 SSO”时隐藏密码登录。
- 系统管理 → 登录方式设置：现有页面增加 OIDC、LDAP、企业微信、钉钉、飞书的配置表单和“测试连接”。
- 个人中心 → 账户安全：MFA 开关（显示二维码和恢复码）、已绑定身份。

## 2. 自定义字段（E-05）

### 2.1 数据模型

| 表 | 关键字段 |
|---|---|
| `cf_definition` | `id`、`tenant_id`、`entity`（sales_order / sales_order_line / purchase_order / business_partner / sku / crm_business …）、`field_key`（`cf_` 前缀，小写下划线）、`label`、`type`（text / textarea / number / decimal / date / datetime / select / multi_select / user / department / bool）、`options`（select 的字典类型或选项）、`required`、`default_value`、`searchable`、`list_visible`、`print_visible`、`import_export`、`sort`、`status` |

- 业务表增加 `ext_json JSON NOT NULL DEFAULT (JSON_OBJECT())`，自定义字段值存这里。
- 每个实体最多 30 个自定义字段；`searchable=true` 的字段最多 5 个。
- 可搜索字段：为该租户该字段建生成列和索引的做法不可行（列是全局的），改为：
  - 表上预留 5 个通用索引列 `cf_idx_1`—`cf_idx_5`（普通 `VARCHAR(128)` 列，不用 MySQL 生成列；应用保存单据时按 `cf_definition` 把对应字段的值同步写入），各建 `(tenant_id, cf_idx_n)` 索引；
  - `cf_definition.index_slot` 记录占用的槽位。
- 删除字段只能停用；停用后历史数据保留在 `ext_json` 中，不再显示。

### 2.2 后端

- 保存单据时，服务端按 `cf_definition` 校验 `ext_json`：未定义的键丢弃，类型、必填、选项值逐一校验，失败返回 400 并指明字段。
- 自定义字段**不参与任何过账、金额计算和状态判断**，只做信息记录、筛选、打印和导出。
- 列表接口支持 `cf.{fieldKey}=值` 筛选（只允许可搜索字段）。
- 导入模板、导出列、打印数据自动包含 `import_export` / `print_visible` 的字段。

### 2.3 前端

- 设置页：系统管理 → 自定义字段，按实体管理字段（拖拽排序）。
- 表单渲染：编辑页在“其他信息”区块用 `DynamicForm` 渲染；明细行字段追加为表格列。
- 列表：`DocumentBrowserPanel` 读取 `list_visible` 字段追加列；筛选区出现可搜索字段。

## 3. 编码规则（E-06）

| 表 | 关键字段 |
|---|---|
| `code_rule` | `id`、`tenant_id`、`company_id`（0 为全公司通用）、`target`（document:sales_order / masterdata:sku / masterdata:partner …）、`segments`（JSON 数组）、`reset_cycle`（none / year / month / day）、`status`、`version` |
| `code_rule_seq` | `rule_id`、`cycle_key`（如 `202611`）、`scope_key`、`next_value` |

段类型：

| 段 | 示例 |
|---|---|
| `literal` | `SO` |
| `company_code` | `C01` |
| `date` | `yyyyMM` / `yyMMdd` |
| `dept_code` | 单据所属部门编码 |
| `category_code` | 物料分类编码（主数据） |
| `serial` | 流水号，长度 6，补零 |

- **单据编号**：现有 `DocumentNumbers` / `document_sequence` 继续作为默认规则；配置了 `code_rule` 的单据类型改用新规则。取号与现有一样在业务事务内加行锁，断号不回收。
- 生成的单号长度不超过现有列长度（现有单号列已扩容到可容纳 33 字符），配置时校验最大可能长度。
- **主数据编码**：SKU、往来单位新建时可留空，由规则自动生成；手工填写时仍需唯一。
- 规则修改只影响之后的新编号；已生成的编号不变。
- 页面：系统管理 → 编码规则，段拖拽配置，右侧实时预览下一个编号。

## 4. 开放平台（E-08）

### 4.1 数据模型

| 表 | 关键字段 |
|---|---|
| `open_app` | `id`、`tenant_id`、`company_ids`（JSON，可访问的公司）、`name`、`app_key`、`secret_cipher`、`scopes`（JSON：权限码子集）、`ip_whitelist`、`rate_limit_per_minute`、`status`、`expires_at` |
| `open_call_log` | `id`、`tenant_id`、`app_id`、`method`、`path_template`、`status`、`latency_ms`、`request_id`、`created_at`（保留 90 天） |
| `open_webhook` | `id`、`tenant_id`、`app_id`、`url`、`events`（JSON）、`secret_cipher`、`status` |
| `open_webhook_delivery` | `id`、`webhook_id`、`event_id`、`status`（pending / delivered / failed）、`attempts`、`last_status_code`、`next_attempt_at` |
| `open_nonce` | 不用表，存 Redis：`erp:open:nonce:{appKey}:{nonce}`，有效期 10 分钟 |

### 4.2 认证与签名

请求头：

```text
X-App-Key: ak_xxx
X-Timestamp: 1763270400          # 秒，±5 分钟有效
X-Nonce: 32 位随机串              # 10 分钟内不可重复
X-Company-Id: 123
X-Signature: base64(HMAC-SHA256(secret, METHOD \n PATH \n QUERY(排序) \n TIMESTAMP \n NONCE \n SHA256(BODY)))
Idempotency-Key: …               # 写操作必填，与内部接口相同
```

- 开放接口路径：`/open/v1/**`，由独立的 Security 过滤链处理，**不使用会话和 CSRF**。
- 鉴权通过后构造“应用身份”：一个虚拟操作人（`open_app` 对应一个系统用户，类型 `app`），权限为 `scopes`，数据范围为 `company_ids`；之后复用内部服务的全部校验。
- 经办与复核分离：应用身份可以创建和提交单据，**不能审批、确认、过账**（这些动作的权限码不允许加入 `scopes`）。

### 4.3 开放接口范围（首批）

| 接口 | 对应内部服务 |
|---|---|
| 主数据查询：SKU、往来单位、仓库、库存可用量 | 现有查询 |
| 主数据写入：SKU、往来单位 | 现有命令 |
| 销售订单：创建、提交、查询、取消 | 现有命令 |
| 采购订单：创建、提交、查询 | 现有命令 |
| 发货、收货：查询 | 现有查询 |
| 收款、付款：登记（待确认） | 现有命令 |

开放接口的请求 / 响应模型单独定义（`OpenModels`），与内部接口解耦，内部接口改动不影响外部调用方。

### 4.4 Webhook

- 事件源：现有 Outbox。订阅的事件写入 `open_webhook_delivery`，由 Worker 推送。
- 推送签名：`X-Erp-Signature: HMAC-SHA256(webhookSecret, timestamp + "." + body)`。
- 重试：1 分钟、5 分钟、30 分钟、2 小时、12 小时，共 5 次；连续失败 50 次的 Webhook 自动停用并通知管理员。
- 首批事件：`sales.order.approved`、`sales.shipment.posted`、`sales.shipment.signed`、`purchase.receipt.posted`、`finance.receipt.confirmed`、`inventory.balance.changed`（按 SKU 合并，每分钟最多一次）。

### 4.5 限流与文档

- 按应用每分钟限流（Redis 滑动窗口），超限返回 429，带 `Retry-After`。
- 开放接口文档：springdoc 单独分组 `open`，生成后发布到“开放平台 → 接口文档”页面；附签名示例（Java、Python、Node.js）。

### 4.6 页面

开放平台菜单（系统管理下）：应用管理（创建后只显示一次密钥，可重置）、权限范围、IP 白名单、Webhook（测试推送）、调用日志、推送记录（失败可重推）、接口文档。

## 5. 迁移规划

1. `user_login_identity`、`tenant_login_provider` 的 method 约束扩展；`user_mfa`、`tenant_security_policy`
2. `cf_definition`；各业务表增加 `ext_json`、`cf_idx_1`—`cf_idx_5` 及索引（大表分批执行）
3. `code_rule`、`code_rule_seq`
4. `open_app`、`open_call_log`、`open_webhook`、`open_webhook_delivery`；`sys_user` 增加 `user_type`（human / app，默认 human）
5. 权限码

## 6. 测试要点

1. OIDC：篡改 `state`、`nonce`、过期 `id_token`、错误 `aud` 全部拒绝；同一授权码不能用两次。
2. MFA：待二次验证的会话访问业务接口返回 401；TOTP 同一步长不能重复使用。
3. 自定义字段：未定义的键被丢弃；必填校验；可搜索字段筛选走索引。
4. 编码规则：并发取号连续不重复；跨月重置正确；超长规则在配置时被拒绝。
5. 开放平台：签名错误、时间戳超窗、Nonce 重放、IP 不在白名单、超出 scopes 全部拒绝；应用身份调用审批接口返回 403。
6. Webhook：接收方返回 500 时按计划重试；签名可被接收方校验。

## 7. 验收

1. 企业员工用公司 OIDC 账号登录，权限与绑定的本地账号一致；管理员角色强制 MFA。
2. 外部系统用开放平台创建销售订单，审批通过、发货过账后收到两次 Webhook，签名校验通过。
3. 给销售订单加“项目编号”自定义字段，可在列表筛选、导出和打印中看到。
