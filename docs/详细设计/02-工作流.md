# 02 工作流（1.3.0 一期、1.6.0 二期）

> 目标版本1.3.0，当前软件仍为1.0.0候选，未正式发布。对应F工作流、X-03、Z-05及企业级演进E-02。实施依据和验证顺序见[M11工作流实施设计](../M11工作流实施设计.md)，验收以本轮真实测试及独立升级结果为准。

## 1. 范围与事务结论

一期使用Flowable 8.0.0内嵌BPMN引擎和SIMPLE节点树。支持五类业务、组织选人、会签/或签/依次审批、条件/并行分支、抄送和任务处理；不开放用户脚本、原始BPMN上传或任意Spring Bean。

先以独立MySQL演练库验证真实SalesOrderService和Flowable：提交后故障全部回滚、引擎启动故障回滚原命令、任务完成及库存预留故障全部回滚、另一连接不能看到未提交数据。四项均通过，正式V44—V46结构再次复测通过，采用同库同步回调。

Flowable与业务共用DataSource及PlatformTransactionManager。Spring Boot依赖管理保持原版本；使用flowable-spring而非Boot starter。生产运行时schemaUpdate=false，禁用IDM、事件注册和引擎异步执行器，超时统一交给现有Worker任务。

若后续引擎升级破坏同事务门槛，必须重新评审并改用Outbox回调原业务命令；不得增加现有状态机不接受的“提交中”状态。本轮没有启用此备用路径。

## 2. 模块与硬边界

```text
业务服务 ── shared.WorkflowPort ── workflow
                               │  发布/选人/实例/任务/受限BPMN
                               └─ shared.WorkflowBusiness
                                      ↑
                             workflowbridge组合适配器
                                      ↓
                             原业务查询与审核命令
```

业务模块只依赖共享接口。组合层登记五个适配器，工作流不直接写库存、额度、现金和凭证。最终审批选取当前epoch内有效人工审核人，重新检查来源权限和分离规则，再用受控WorkflowContext调用原命令；上下文在finally清理。事务失败时任务、历史、业务事实、幂等结果及消息Outbox一起回滚。

| 业务类型 | 发起时机与待审状态 | 流程通过 | 驳回到发起人/撤销/终止 |
| --- | --- | --- | --- |
| sales_order | submit，pending | 原approve，approved，保留原库存预留 | 原reject回draft |
| purchase_order | submit，pending | 原approve，approved | 原reject回draft |
| refund_request | submit，pending_review，先占用额度 | 原approve，pending_payment | 原reject回draft并释放额度 |
| document_reversal | create即pending | 原approve，approved | 原reject，rejected |
| stock_adjustment | submit，pending | 原approve，approved | 原reject回draft |

未匹配流程保持原单级审批。已绑定且运行中的单据隐藏原生审核按钮，后端guard同时拦截原approve/reject/withdraw/cancel/void，不能靠直接HTTP绕过。审批不替代退款登记或过账。期间、可用量、经办复核分离、两人经手等仍由原服务强制；配置不能授予业务权限。

## 3. 数据结构与升级

只能追加迁移。V44按Flowable 8.0.0原JAR的common、engine、history MySQL DDL创建官方ACT_*结构，每段保留来源与SHA-256，首次提交前统一LF，原SQL字符及官方空格不变，Flyway校验值保持一致。未安装IDM等无关引擎。V45、V46保存ERP业务扩展，五类业务头新增wf_instance_id默认0，旧记录不启动流程。

| 表 | 核心约束 |
| --- | --- |
| wf_category | 企业内分类编码唯一，独立版本 |
| wf_model | tenant/company（0企业共享）/code/business_type；草稿树、发布版本和乐观锁 |
| wf_model_version | 发布快照不可变，SIMPLE JSON、生成XML、SHA-256、引擎definition/deployment、发布人和时间 |
| wf_business_binding | 公司优先于共享，同范围按priority降序；条件、启停和版本 |
| wf_instance | 冻结模型版本、摘要、主部门、自选人员；active_key防重复运行，approval_epoch防复用旧审核 |
| wf_task_ext | 引擎任务、处理人/委派原人、父任务、加签位置、版本、截止/提醒时间、人工价格hash |
| wf_task_action | 追加式操作轨迹，保留历史意见和系统动作 |
| wf_copy | 按实例/节点/接收人/epoch去重，个人已读时间 |

实例状态running/approved/rejected/cancelled/terminated单独保存，不替代业务状态。任务有pending、approved、rejected、cancelled、removed、auto_approved、waiting_sign；转办和委派记录动作，不伪造已审批事实。官方引擎表为UTF8MB3，模型及节点名称禁止控制符、表达式标记和非BMP扩展字符，业务资料仍沿用UTF8MB4。

## 4. 模型与发布

公司内模型仅绑定当前公司；共享模型可用于共享或当前公司绑定。编辑不改变已发布快照，发布生成新版本；在途实例始终使用发起时版本。已发布版本可只读查看。停用后已匹配该模型的新提交明确失败，不能悄悄退回单级审批；旧实例继续。

绑定优先使用当前公司，再按priority从高到低取首个满足条件的绑定。无匹配才走原审批。绑定公司和业务类型不可修改，需新建；重复优先级由数据库唯一约束阻止。所有写操作具有版本、幂等键、权限和审计。

## 5. SIMPLE节点树

节点type为start、approver、handler、copy、condition_branch、parallel_branch，child表示后续，branches表示分支。最多100节点、30层，每节点编号唯一且不能使用引擎保留前缀。只允许服务端固定编译器生成表达式。

每条可达路径至少一次人工approver。办理、抄送和自动超时均不计人工复核。条件分支2—10条且恰一条默认分支，按声明顺序判断；并行分支全部汇合后继续。前端画布可以增加/删除环节、分支和配置，删除分支节点会确认并保留汇合后的后续节点。

### 5.1 选人

| 策略 | 实际解析 |
| --- | --- |
| users / role | 当前启用用户，或当前有效角色成员 |
| dept_leader | 发起人冻结主部门起第N级部门负责人，1为本部门 |
| multi_level_leader | 从本部门连续向上N级负责人去重，固定依次审批 |
| post | 当前公司岗位成员，可限制发起人主部门 |
| starter_select | 发起提交时选择，服务端逐人重新检查资格；只展示实际可达节点 |
| starter | 发起人，仍受经办复核分离限制 |
| field_user | 创建人、销售员或采购员，按业务类型白名单 |
| starter_dept_members | 当前有效部门成员，仅用于抄送 |

所有选人结果与实时企业、公司、仓库、部门、来源查看及业务审核权限取交集。价格环节还需sales_order:price_approve。无有效人可转交具备同样业务资格的流程管理员或自动驳回；人工复核节点禁止跳过。自选人无效时拒绝提交，不能悄悄删人。冲销创建前通过受控预览接口取可选节点和候选，创建时再次校验。

### 5.2 多人及任务处理

会签所有人完成、或签任一人完成、依次审批逐个产生任务。并发完成由实例锁、任务版本及引擎共同保证只执行一次业务回调。

转办替换当前处理人；委派意见返回原处理人，不直接计作同意。前加签未完阻止原人通过；后加签在原人同意后仍等待全部加签，waiting_sign不视为通过。仅原添加人可减少自己尚未完成的加签，不能删除原复核节点。加签最多20人。

驳回到发起人结束当前实例；驳回到历史已经过节点时增加epoch并重新审批，旧同意不能用于新轮完成。仅发起人可撤销，具备workflow_instance:terminate者可终止，且都要有来源权限。所有理由和原始动作保留。

### 5.3 条件摘要

条件支持==、!=、>、>=、<、<=、in，以及最多6层all/any组合；数值采用BigDecimal，文本/布尔仅等于、不等于、属于。字段按单据类型校验。

| 类型 | 条件字段（另有totalAmount、ownerDeptId、createdBy） |
| --- | --- |
| 销售订单 | discountRate（百分比，100为原价）、belowMinPrice、customerId、salesUserId |
| 采购订单 | discountRate、supplierId、buyerUserId、requisitionApproved |
| 退款 | customerId、refundMethod（账户类型） |
| 冲销 | sourceType、crossPeriod（业务日期是否跨月） |
| 库存调整 | adjustType |

不提供尚未存在的客户级别、信用额度字段。库存调整金额按录入总成本或发起时可得成本估算用于路由，最终过账仍按原服务实时成本规则。无cost:view时相关成本摘要不向查询接口返回；价格指纹不展示给用户。

## 6. 最低售价X-03

sku.min_sale_price为含税基本单位最低价，0不控制。company_policy.below_min_price_policy为warn/approval/block。比较整行折后未税金额+税额与最低价×基本数量，按分舍入，防止单位换算、税模式和折扣绕过。

warn允许保存提交并在详情提示；block拒绝保存/提交/批准；approval允许草稿，提交时必须匹配包含人工价格审批的实际可达路径。未配置或未匹配流程明确阻止提交，不降级为提示。

价格审核人须持有价格及原业务审核权限。审批证据绑定本轮行、数量、含税金额、当前最低价与公司策略的hash，最终原approve锁定再检查。改价、改策略或撤权后不能复用旧证据。已批准订单若经旧变更入口变成需要新的低价审批，拒绝该旁路并提示按新订单重新审批；本期不扩展原订单变更工作流。

## 7. 超时、消息与多实例

workflow.timeout纳入现有固定任务管理，默认每5秒扫描到期任务，批次100；实例及任务行锁保证双Worker不会重复动作。提醒可重复间隔1—168小时，首次超时1—720小时。人工approver不允许自动同意；handler可以自动办理，但最终必须已有本轮有效人工审核。自动驳回/终止以系统动作记录，不能冒充人工同意。

流程事务写notify.workflow Outbox意图，提交后Redis广播摘要，消费者幂等生成站内消息。铃铛/消息中心REST会即时补齐有权待办，转办或任务版本变化后旧待办失效。抄送已读按抄送记录关联，两个入口同步。模板及订阅复用Y-06；本轮不发送真实外部渠道。引擎AsyncExecutor关闭，不能依赖Flowable timer触发本期提醒。

## 8. REST与前端

公共前缀/api/v1/workflow，要求有效会话和X-Company-Id；写请求检查CSRF、版本及Idempotency-Key。列表采用游标，最大200。后台配置必须全组织管理范围及对应细权限；审批只能由当前处理人操作。查询不因持有模型管理权而扩大来源数据范围。

| 接口 | 用途 |
| --- | --- |
| GET/POST /models，GET/PUT /models/{id} | 模型查询、草稿维护 |
| GET /models/{id}/versions/{version} | 不可变发布快照 |
| POST /models/{id}/publish、/disable | 发布和停用 |
| GET/POST /bindings，PUT /bindings/{id} | 类型绑定与条件 |
| GET/POST /categories，PUT /categories/{id} | 分类 |
| GET /metadata | 管理端用户、角色、岗位、部门和各类型字段白名单 |
| GET /tasks/todo、/tasks/done、/instances/mine、/instances/all、/copies | 五种列表 |
| GET /instances/{id} | 实例任务及轨迹，仅参与人或view_all且来源有权 |
| POST /tasks/{id}/{approve\|reject\|transfer\|delegate\|add-sign\|remove-sign} | 人工任务命令 |
| POST /tasks/batch-approve | 同一发布版本和环节的 2 至 20 项普通待办逐条同意 |
| GET /tasks/{id}/candidates | 当前人可转交的合资格用户 |
| POST /instances/{id}/cancel、/terminate | 撤销或终止 |
| PUT /copies/{id}/read | 自己的抄送已读 |
| GET /progress、/todo-count、/start-options、/reversal-start-options | 单据进度、数量和发起选人 |

页面位于/workflow/models、/workflow/todo、/done、/mine、/copies、/all及/instances/:id。五类原单据详情展示进度；自选出现在提交或冲销创建表单。公司切换、迟到响应、权限失败和未知写结果均显式处理；未知结果冻结原内容和幂等键重试。

待办列表支持按 `keyword` 搜索单号、标题或发起人，返回发起人姓名、有权查看的金额和可批量同意待办的 `batchGroup`。审批预览通过来源单据接口读取摘要与明细，通用申请按当前任务查询表单字段。

批量同意传入 `group`（所选待办的 `batchGroup`）和 `items`（每项包含 `id`、`version`）。每项独立校验公司、来源单据范围、处理人资格、版本及环节，服务端复用单条同意命令，返回每项的 `id`、`approved` 和失败 `message`。通用表单含节点级字段权限，委派反馈、办理和加签任务也按单项处理。服务端先登记完整请求体的幂等指纹。请求中断时，使用原请求体和幂等键重试，已提交的单项返回原处理结果，同键换请求返回 409。

## 9. 测试与发布边界

测试包含四项真实事务门槛、受限模型校验、经理/财务会签及驳回重提、分支/或签/依次、所有选人策略、转委加减签、双Worker超时、双线程完成、最终故障回滚、五业务适配、价格证据及真实HTTP会话/CSRF/撤权/公司仓库部门交集。前端覆盖设计树、候选与进度迟到响应、原请求重试；浏览器使用真实服务和独立临时企业。

提交前运行完整后端verify、前端测试/lint/build、浏览器回归，独立数据库执行V43→V46增量演练。真实渠道、生产数据库权限及多实例生产部署仍须在正式上线环境另行验收，不据本机结果宣称1.3.0已发布。

## 10. 二期范围

1.6.0 候选包含受控 BPMN 预览、属性和节点树编辑、通用表单审批及字段校验。实施边界和使用步骤见 [M14 工作流二期使用说明](../M14工作流二期使用说明.md)。

### 10.1 BPMN设计器（二期）

- 使用 bpmn-js，按需加载（单独分包）；属性面板自研，只暴露本项目支持的属性。
- bpmn-js 采用 bpmn.io 许可，要求保留画布右下角的 bpmn.io 标识。

### 10.2 通用审批与表单（Z-05）

- 表单设计：form-create 设计器生成 `schema_json`，保存到 `wf_form`。
- 通用审批：员工在“审批中心 → 发起申请”选择流程，填写动态表单，提交后创建 `wf_generic_request` 并发起流程；可上传附件（复用附件服务）。
- 表单字段权限：每个审批节点配置字段 `read` / `write` / `hidden`；后端在保存表单数据时按节点权限过滤，防止前端篡改。
- 典型用途：费用申请、用印申请、合同用章、借款申请（报销在财务模块单独做）。
