> 对应：《功能扩展方案》第 6 节、X-03、Z-05；《企业级演进规划》E-02。

## 2. 核心原则

1. **单据是事实，流程是过程。** 单据状态仍由业务模块的状态机管理；流程只决定“谁来审、审完了没有”。
2. **同成同败。** 提交单据和发起流程在同一个数据库事务中；流程结束后回写单据也在一个事务中。
3. **硬规则不可绕开。** 经办与复核分离、两人经手、期间关闭、可用量、信用额度等，仍在业务命令中校验；流程配置只能**增加**审批环节。
4. **没有配置流程的单据，行为与 1.x 现有单级审批完全一致。**

## 3. 架构

```text
业务模块（salesorder …）
   │ submit 命令：校验 → 状态改为 pending（与现有一致）→ workflowService.start(…)
   ▼
workflow 包
   ├─ WorkflowService      对外：start / cancel / progress / handleTask
   ├─ ModelService         流程模型：SIMPLE JSON ⇄ BPMN XML、发布版本
   ├─ AssigneeResolver     解析审批人（角色、部门负责人、上级 …）
   ├─ ErpTaskListener      任务创建 / 完成时发站内信、写待办
   ├─ ErpExecutionListener 流程结束时回调业务：BusinessApprovalHandler
   └─ Flowable 引擎（ACT_* 表）
   ▲
   │ 回调接口 BusinessApprovalHandler.onApproved / onRejected / onCancelled
业务模块实现回调，执行原有 approve / reject 命令逻辑（幂等）
```

- 业务模块只依赖 `workflow` 的公开接口 `WorkflowService` 和回调接口 `BusinessApprovalHandler`，不直接使用 Flowable API。
- 回调用 `BusinessCommands.execute`，幂等键为 `wf:{processInstanceId}:{结果}`，流程引擎重试或重复回调不会重复执行。

## 4. Flowable 集成

### 4.1 配置

```yaml
flowable:
  database-schema-update: ${FLOWABLE_SCHEMA_UPDATE:false}   # 开发环境 true，生产 false
  async-executor-activate: ${ERP_WORKER_ENABLED:false}       # 只在 Worker 角色启用异步执行器
  history-level: audit
  check-process-definitions: false                           # 不从 classpath 自动部署
  id-generator: …                                            # 使用 Flowable 默认 UUID
```

- **数据源和事务管理器与 JdbcTemplate 共用**，这是“同成同败”的前提。上线前必须通过技术验证：在一个 `@Transactional` 方法中先 `UPDATE sales_order`、再 `runtimeService.startProcessInstanceByKey`，然后抛异常，确认两者都回滚。
- 验证不通过时的降级方案：提交命令只写单据状态和 Outbox 事件 `workflow.start.requested`，由 Worker 在独立事务中发起流程；流程结束同样经 Outbox 回调。单据在“提交中”状态可见。
- 生产环境的 Flowable 表结构由运维在升级时执行 Flowable 官方 SQL 脚本，步骤写入《部署说明》。
- 多租户：使用 Flowable 的 `tenantId` 字段，值为 `tenant_id` 的字符串形式；所有查询带租户条件。

## 5. SIMPLE 模型

### 5.1 节点 JSON

```json
{
  "id": "root", "type": "start", "name": "发起人",
  "child": {
    "id": "n1", "type": "approver", "name": "部门经理审批",
    "assignee": {"strategy": "dept_leader", "level": 1, "emptyHandler": "skip"},
    "multi": "or",
    "timeout": {"hours": 24, "action": "remind", "repeat": 12},
    "child": {
      "id": "c1", "type": "condition_branch",
      "branches": [
        {"name": "金额 > 50000", "condition": {"field": "totalAmount", "op": ">", "value": "50000"},
         "child": {"id": "n2", "type": "approver", "name": "财务会签",
                   "assignee": {"strategy": "role", "roleCodes": ["finance_manager", "cfo"]},
                   "multi": "and"}},
        {"name": "其他", "default": true, "child": null}
      ],
      "child": {"id": "cc1", "type": "copy", "assignee": {"strategy": "starter_dept_members"}}
    }
  }
}
```

### 5.2 节点类型

| 类型 | 说明 |
|---|---|
| `start` | 发起人节点，可配置发起人范围（哪些部门 / 角色能发起） |
| `approver` | 审批节点；`multi`：`or` 或签、`and` 会签、`sequential` 依次审批 |
| `handler` | 办理节点（只有“提交”，没有“驳回”，用于经办环节） |
| `copy` | 抄送节点 |
| `condition_branch` | 条件分支（排他），从上到下第一个满足的分支执行，必须有默认分支 |
| `parallel_branch` | 并行分支，全部分支完成后汇合 |
| `trigger` / `delay` / `inclusive_branch` / `router` / `sub_process` | 二期 |

### 5.3 审批人策略

| 策略 | 说明 |
|---|---|
| `users` | 指定用户 |
| `role` | 指定角色的全部成员（限当前公司） |
| `dept_leader` | 发起人主部门的负责人；`level=2` 表示上一级部门的负责人 |
| `multi_level_leader` | 从发起人部门向上逐级到第 N 级负责人，依次审批 |
| `post` | 指定岗位的成员（可限定在发起人部门内） |
| `starter_select` | 发起人在提交时选择 |
| `starter` | 发起人自己（用于“修改后重新提交”环节） |
| `field_user` | 取单据字段中的用户，如 `sales_user_id` |

`emptyHandler`（找不到审批人时）：`skip` 自动通过、`admin` 转给流程管理员、`reject` 自动驳回。

强制人工复核节点禁止配置 `skip` 或超时自动同意。发布、运行时都校验，避免历史配置或审批人离职绕过规则。找不到有效复核人时转交具备业务权限的其他人员，无法满足经办复核分离时阻止通过。系统自动处理不计入“两人经手”的人工人数，最终业务命令必须验证有效人工审批证据。

### 5.4 条件表达式

- 条件字段来自**单据摘要**：业务模块在发起流程时传入 `variables`，例如 `totalAmount`、`customerLevel`、`ownerDeptId`、`discountRate`、`belowMinPrice`。
- 每种单据类型在 `BusinessApprovalHandler.conditionFields()` 中声明可用字段（名称、类型、中文名），设计器据此提供下拉选择，**不允许手写表达式**。
- 转换为 BPMN 时生成 `${erpCondition.eval(execution, 'c1-0')}`，由后端按 JSON 条件求值，避免把用户输入直接拼进 JUEL 表达式。

### 5.5 发布

1. 前端保存 `simple_json`。
2. 发布时后端校验：每个分支有默认分支、审批节点有审批人策略、条件字段存在。
3. `SimpleModelConverter` 把 JSON 转成 BPMN XML，部署到 Flowable，写 `wf_model_version`。
4. 已运行的实例继续按旧版本执行；新提交的单据使用新版本。

## 6. 业务接入

### 6.1 回调接口

```java
public interface BusinessApprovalHandler {
    String businessType();                                  // 如 "sales_order"
    List<ConditionField> conditionFields();                 // 设计器可用的条件字段
    ApprovalSummary summary(CompanyAccess scope, long id);  // 标题、摘要、流程变量
    void onApproved(CompanyAccess scope, long id, ApprovalResult result);
    void onRejected(CompanyAccess scope, long id, ApprovalResult result);
    void onCancelled(CompanyAccess scope, long id, ApprovalResult result);
}
```

### 6.2 提交流程

以销售订单为例：

```text
POST /api/v1/sales-orders/{id}/submit
  └─ SalesOrderService.submit
       ├─ 原有校验（行、价格、信用、期间 …）
       ├─ binding = workflowBindings.find(scope, "sales_order", summary)
       ├─ 状态 → pending（与现有完全相同，不新增状态）
       ├─ 有绑定：workflowService.start(scope, binding, id, summary)，单据记录 wf_instance_id
       └─ 无绑定：不发起流程，等待现有单级审批
```

- 流程通过：`onApproved` 执行原有 `approve` 命令的逻辑（预留库存、冻结价格等），状态 → `approved`。
- 流程驳回到发起人：单据回到 `draft`，可修改后重新提交（新流程实例）。
- 发起人撤销：`POST /api/v1/workflow/instances/{id}/cancel` → `onCancelled` → 单据回到 `draft`。
- 单据头增加 `wf_instance_id BIGINT NOT NULL DEFAULT 0`。`wf_instance_id` 不为 0 时，单据详情的 `allowedActions` 不再返回 `approve` / `reject`，直接调用审批接口也会返回 409 `WORKFLOW_IN_PROGRESS`，只能通过待办处理。

### 6.3 一期接入的单据

| 单据 | 条件字段 |
|---|---|
| 销售订单 | 金额、折扣率、是否低于最低售价、客户级别、所属部门、是否超信用额度 |
| 采购订单 | 金额、供应商、所属部门、请购单是否已审 |
| 退款申请 | 金额、退款方式 |
| 冲销申请 | 原单类型、金额、跨期 |
| 库存调整 | 调整类型、金额 |

### 6.4 最低售价控制（X-03）

- `sku` 增加 `min_sale_price DECIMAL(24,8) NOT NULL DEFAULT 0`（0 表示不控制）。
- 公司参数增加 `below_min_price_policy`：`warn`（提示）/ `approval`（需要审批）/ `block`（禁止）。
- 订单保存时计算每行折后含税单价是否低于最低价，写入行字段 `below_min_price`；提交时作为流程条件变量 `belowMinPrice`。
- 没有配置流程时 `approval` 等同于 `warn`，并在订单详情显示提示。

## 7. 任务处理

| 操作 | 接口 | 说明 |
|---|---|---|
| 同意 | `POST /api/v1/workflow/tasks/{taskId}/approve` | `{comment, signature?}` |
| 驳回 | `POST /api/v1/workflow/tasks/{taskId}/reject` | `{comment, targetNodeKey}`：发起人 / 上一节点 / 任意已经过的节点 |
| 转办 | `POST …/transfer` | `{userId, comment}`；新处理人审完直接进入下一节点 |
| 委派 | `POST …/delegate` | `{userId, comment}`；被委派人处理后回到原处理人 |
| 加签 | `POST …/add-sign` | `{userIds, position: before \| after, comment}` |
| 减签 | `POST …/remove-sign` | `{taskIds}`，只能减自己加的 |
| 撤销 | `POST /api/v1/workflow/instances/{id}/cancel` | 发起人；流程尚未结束时 |
| 终止 | `POST /api/v1/workflow/instances/{id}/terminate` | 流程管理员，权限 `workflow_instance:terminate`，必须填原因 |

- 所有操作带 `Idempotency-Key`；只有任务的当前处理人可以操作，否则返回 403 `WORKFLOW_TASK_NOT_ASSIGNED`。
- **经办与复核分离**：审批人如果就是单据制单人，且该单据类型要求分离，则该任务自动转给流程管理员并提示，不允许本人审批。
- 每个操作写 `wf_task_ext` 和审计日志，并发站内信。

### 7.1 超时与提醒

- 审批节点配置 `timeout`：到期后执行 `remind`（提醒，可重复）、`approve`（自动同意）、`reject`（自动驳回）。
- 由 Flowable 定时器事件触发，执行器只在 Worker 角色运行。
- 自动同意 / 驳回的意见写“超时自动处理”，审计中操作人记为系统。

## 10. 二期：通用审批与表单（Z-05）

- 表单设计：form-create 设计器生成 `schema_json`，保存到 `wf_form`。
- 通用审批：员工在“审批中心 → 发起申请”选择流程，填写动态表单，提交后创建 `wf_generic_request` 并发起流程；可上传附件（复用附件服务）。
- 表单字段权限：每个审批节点配置字段 `read` / `write` / `hidden`；后端在保存表单数据时按节点权限过滤，防止前端篡改。
- 典型用途：费用申请、用印申请、合同用章、借款申请（报销在财务模块单独做）。

## 11. 权限码

`workflow_model:view|create|update|publish|disable`、`workflow_binding:update`、`workflow_instance:view_all|terminate`、`workflow_form:*`；待办处理不需要额外权限，只看是否分配给本人。

## 12. 测试要点

1. 同成同败：提交时流程发起失败 → 单据状态不变；回调执行失败 → 流程保持在最后节点并重试。
2. 会签三人：两人同意一人驳回 → 驳回；依次审批顺序正确。
3. 条件分支：金额边界值（等于 50000）走默认分支。
4. 驳回到任意节点、重新提交产生新实例，旧实例保留。
5. 转办、委派、加签、减签后的待办归属正确。
6. 制单人同时是审批人时，任务转给流程管理员。
7. 模型发布新版本后，运行中实例按旧版本完成。
8. 超时自动同意在两个 Worker 实例下只执行一次。
9. 越权：非处理人调用同意接口返回 403；跨租户看不到实例。

## 13. 验收

“金额 > 5 万需部门经理 + 财务会签”的销售订单流程：提交 → 经理同意 → 财务甲同意、财务乙驳回到发起人 → 修改金额后重提 → 全部同意 → 订单已审批并完成预留。全过程每个处理人收到站内信，订单详情显示完整审批轨迹。
