## 2. 服务架构

1.5.0 完整权限验收依赖 1.2.0 的组织模型。服务骨架、模型网关可提前开发；部门知识库、来源权限继承及撤权回归通过前，不开放部门资料检索。

M13 候选实现的接口与部署差异见 [使用与验收](../M13人工智能使用与验收.md)。ERP 当前身份以签名桥接接口为准，SSE 在完整回答和来源通过复核后发送。助手只接受用户选择的内置只读工具。Wiki 自动加工从待审队列取稿，使用在线审核者的授权和来源权限。评测以目标环境的运行结果为发版依据。

```text
浏览器 ── /ai/v1/** ──► Nginx（关闭缓冲，支持 SSE）──► erp-ai
                                                      │
          ┌───────────────────────────────────────────┼─────────────────────────────┐
          │ ChatController（SSE）   KbController   AdminController   EvalController   │
          │        │                                                                  │
          │  AssistantRuntime：取角色配置 → 检索知识 → 组装提示词 → 调模型 → 执行工具 → 输出 │
          │        │                 │                    │                           │
          │  ModelGateway（多模型、限额、计费、审计）  Retriever（OpenSearch）  ToolInvoker │
          └──────────┬─────────────────────┬──────────────────────┬────────────────────┘
                     ▼                     ▼                      ▼
              模型服务（外部 API     OpenSearch（片段、       erp-server /api/v1/ai-tools/**
              或私有化 vLLM）        向量、Wiki）             （带用户会话，按原权限执行）
                     erp_ai 库（MySQL）：会话、消息、文档元数据、Wiki、用量、评测
```

| 项 | 选型 |
|---|---|
| 框架 | Spring Boot 4.1.2 + Spring AI 2.0.1，JDK 21 |
| 存储 | MySQL 8.0.46 独立库 `erp_ai`；OpenSearch（片段正文 + 向量 + 关键词） |
| 文档解析 | Apache Tika；扫描件和图片用 OCR（私有化部署 PaddleOCR 服务，或使用支持图片输入的模型） |
| 向量 / 重排 | 私有化 bge-m3 / bge-reranker（独立推理服务） |
| 对话模型 | 经模型网关配置：境内默认已备案模型或私有化开源模型；海外或数据可出境场景可配置 Claude（默认 `claude-opus-5-5`，高并发对话路由经评测后可用 `claude-sonnet-5-5`，分类抽取用 `claude-haiku-5-5`） |
| 流式输出 | SSE（`text/event-stream`），事件：`token`、`tool_call`、`tool_result`、`citation`、`done`、`error` |

### 2.1 身份传递

- 浏览器请求 `/ai/v1/**` 带同一个会话 Cookie；`erp-ai` 调 erp-server 的 `GET /api/v1/auth/me` 校验会话并取得用户、租户、公司。
- 调用工具时，`erp-ai` 把用户的会话 Cookie 和 `X-Company-Id` 原样转发给 `/api/v1/ai-tools/**`，**erp-server 按用户自己的权限和数据范围执行**。`erp-ai` 不持有任何特权账号。
- 为防止会话 Cookie 在 `erp-ai` 日志中泄露：转发时只在内存中使用，日志过滤所有 Cookie 和 Authorization 头。
- erp-server 识别来自 erp-ai 的调用（内网来源 + 共享签名头 `X-Erp-Ai-Signature`），在审计日志中标记“经 AI 助手调用”。

## 4. 知识库与 RAG（1.5.0）

### 4.1 数据模型（erp_ai）

| 表 | 关键字段 |
|---|---|
| `kb_library` | `id`、`tenant_id`、`name`、`description`、`visibility`（all / roles / departments）、`status` |
| `kb_library_acl` | `library_id`、`target_type`（role / department）、`target_id` |
| `kb_document` | `id`、`tenant_id`、`library_id`、`title`、`file_object_key`、`mime`、`size`、`hash`、`version_no`、`status`（uploaded / parsing / indexed / failed / disabled）、`error`、`uploaded_by` |
| `kb_segment` | `id`、`document_id`、`seq`、`heading_path`（如“销售 / 退货 / 退款”）、`page_from`、`page_to`、`char_count`、`status`、`opensearch_id` |

- 上传沿用 erp-server 的附件规则（类型白名单、20MB、内容校验），文件存对象存储。
- 解析流水线（异步任务）：Tika 提取文本 → 按标题层级切分（目标 300—800 字，带上级标题路径，相邻片段重叠 50 字）→ 向量化 → 写 OpenSearch。
- 同一文档上传新版本：新片段写入后，旧片段标记失效并从索引删除。

### 4.2 OpenSearch 索引

```text
索引：erp-kb-{tenantId}
字段：segment_id, library_id, document_id, title, heading_path, content（ik_max_word 分词）,
      embedding（knn_vector, 1024 维）, acl_roles[], acl_departments[], updated_at
```

- 每个租户一个索引，从结构上隔离；检索时额外强制带 `library_id IN (用户可见库)` 过滤。

### 4.3 检索流程

1. 问题改写：结合最近 3 轮对话补全指代（使用小模型）。
2. 混合召回：BM25 前 30 + 向量前 30，按 RRF 合并。
3. 重排：bge-reranker 取前 6—8 段。
4. 先查 Wiki（见第 5 节），Wiki 命中的页面优先放入上下文。
5. 组装提示词：系统提示（角色、回答要求、引用格式、拒答规则）+ 参考资料（带编号）+ 问题。
6. 输出：回答中用 `[1]` 标注引用，前端渲染为可点击的来源卡片（文档名、章节、页码）。
7. 资料不足时回答“知识库中没有找到相关内容”，并把问题记入“未覆盖问题”清单。

### 4.4 管理功能

- 分段预览与手动调整（合并、拆分、停用片段）。
- **召回测试**：输入问题，显示命中的片段、分数和是否进入最终上下文。
- 文档列表显示解析状态和失败原因，可重试。

## 5. LLM Wiki（1.5.0）

| 表（erp_ai） | 关键字段 |
|---|---|
| `wiki_page` | `id`、`tenant_id`、`slug`、`title`、`summary`、`status`（draft / pending_review / published / archived）、`current_revision_id`、`view_count`、`updated_at` |
| `wiki_revision` | `id`、`page_id`、`content_md`、`source_segments`（JSON：引用的片段 ID）、`author_type`（ai / human）、`author_id`、`change_note`、`created_at` |
| `wiki_link` | `from_page_id`、`to_page_id` |
| `wiki_task` | `id`、`tenant_id`、`type`（create / update / lint）、`trigger`（document_indexed / uncovered_question / schedule / manual）、`payload`、`status`、`result_page_id` |
| `wiki_lint_issue` | `id`、`page_id`、`type`（contradiction / broken_link / stale_source / orphan）、`detail`、`status` |

流程：

1. **生成 / 更新**：文档入库或“未覆盖问题”累计到阈值时，创建 `wiki_task`。后台任务让模型读取相关片段和现有页面，输出新页面或修订稿（Markdown，每段末尾带来源编号），状态 `pending_review`。
2. **审核**：知识管理员在 Wiki 后台看到修订前后对比，可编辑后发布，或驳回。只有已发布页面参与问答。
3. **体检**（每周）：检查页面之间说法矛盾、引用的文档已失效、无入链的孤立页面、半年未访问的页面，生成 `wiki_lint_issue` 待办。
4. **问答**：检索时 Wiki 页面单独建索引并加权；命中 Wiki 时同时附上原文引用。

首批导入：仓库 `docs/` 中的《业务规则》《用户使用手册》《运维手册》，按文件拆为页面，由管理员审核发布。

Wiki 发布不扩大来源资料权限。每个修订记录全部来源片段与权限版本，读者必须有权读取全部来源；权限取交集，不能把受限资料汇总为全员可见页面。浏览、检索、引用预览和会话历史重新校验当前来源权限。来源停用、撤权或文档换版时，使相关索引、缓存及修订失效，重新审核后恢复；管理员发布操作不能解除来源访问限制。

## 6. 助手运行时

### 6.1 助手角色

| 表（erp_ai） | 关键字段 |
|---|---|
| `ai_assistant` | `id`、`tenant_id`、`code`（internal / customer_service / agent_assist）、`name`、`system_prompt`、`library_ids`、`tool_codes`、`scene`、`status` |
| `ai_conversation` | `id`、`tenant_id`、`assistant_id`、`channel`（web / portal / wecom / mp）、`user_id` 或 `portal_user_id`、`title`、`status`、`created_at` |
| `ai_message` | `id`、`conversation_id`、`role`（user / assistant / tool）、`content`、`citations`、`tool_calls`、`model_id`、`tokens`、`created_at` |
| `ai_feedback` | `message_id`、`user_id`、`rating`（up / down）、`reason`、`correction` |

- 会话保留 180 天；用户可删除自己的会话。
- 上下文管理：保留最近 10 轮完整对话，更早的压缩为摘要。

### 6.2 工具调用

- 工具定义保存在 `ai_tool`（`code`、`description`、`input_schema`、`erp_endpoint`、`scene`），由 erp-server 的 `aitools` 包实现对应接口。
- 每个工具的参数用 JSON Schema 严格校验，不通过时把错误作为工具结果返回模型，不执行。
- 一次回答最多调用 5 次工具；工具超时 10 秒。
- 工具结果中的金额、数量原样展示，**提示词要求模型不得自行计算或改写数字**；前端把工具结果渲染成表格，与模型文字分开显示。

|---|---|---|

| POST | `/ai/v1/conversations/{id}/messages` | 发送消息，SSE 返回 |
| GET | `/ai/v1/conversations`、`/{id}/messages` | 历史 |
| POST | `/ai/v1/messages/{id}/feedback` | 点赞、点踩、纠错 |
| 管理 | `/ai/v1/admin/providers`、`models`、`routes`、`assistants`、`tools`、`libraries`、`documents`、`wiki/*`、`usage`、`logs`、`evals` | 权限 `ai_admin:*`（在 erp-server 权限体系中登记） |

## 7. 业务工具（1.8.0）

### 7.1 智能查数（A-02）

erp-server 新增 `/api/v1/ai-tools/**`，**每个工具复用现有查询服务**，只是参数和返回为模型友好的格式：

| 工具 | 复用 | 参数 |
|---|---|---|
| `receivable_balance` | 应收账龄报表 | 客户名称或编码、截止日期 |
| `payable_balance` | 应付账龄报表 | 供应商、截止日期 |
| `available_stock` | 实时库存 | SKU 名称 / 编码 / 条码、仓库 |
| `order_progress` | 销售订单详情 | 订单号或客户 + 日期范围 |
| `purchase_progress` | 采购订单详情 | 订单号或供应商 |
| `sales_summary` | 销售汇总报表 | 日期范围、维度（客户 / SKU / 业务员 / 部门） |
| `gross_margin` | 毛利报表 | 日期范围、维度 |
| `cash_balance` | 资金日记账 | 账户、日期 |
| `document_search` | 单据浏览 | 关键字、类型、状态、日期 |

- 名称到 ID 的解析在工具内部完成：匹配多个时返回候选列表让模型追问用户，不猜测。
- 返回结果附带 `asOf`（数据截止时间）和跳转链接。
- 查数由消息中的 `toolCode=auto` 进入，沿用 `kb_chat` 模型路由。模型输出 JSON 查询计划，ERP 按原会话、公司和范围执行，模型只获取计划所需工具定义和问题。原始业务数字即时展示，历史消息不保留查询结果。 [使用与验收](../M15智能查数使用与验收.md)

### 7.2 单据解释（A-03）

- 工具 `document_explain`：输入单据类型和 ID，返回状态、`allowedActions`、阻挡原因（复用关账检查、提交校验、依赖检查的结果）、相关单据链接。
- 入口：单据详情页右上角“问 AI”，自动带上当前单据。
- 典型问题：“为什么不能发货”“为什么关账检查不通过”“这张单为什么不能冲销”。

### 7.3 AI 录单（A-04）

```text
上传（图片 / PDF / 邮件正文）
  → OCR 或视觉模型提取文本与表格
  → 抽取模型按 JSON Schema 输出：客户、日期、交货地址、明细（品名、规格、数量、单位、单价）
  → erp-server /api/v1/ai-tools/match：客户、SKU、单位匹配（编码 → 条码 → 名称相似度 → 历史订单）
  → 生成销售订单草稿（POST /api/v1/sales-orders，source_type=ai_extract、source_id=抽取记录 ID）
  → 页面打开草稿，低置信字段标黄，原图在左侧对照
  → 用户确认修改后，按现有流程提交
```

- 抽取结果和匹配置信度保存在 `ai_extraction`（erp_ai 库），用于评测和改进。
- 本版给 `sales_order` 增加 `source_type VARCHAR(32) NOT NULL DEFAULT ''`、`source_id BIGINT NOT NULL DEFAULT 0`（现有订单为空串和 0），1.9.0 的 CRM 合同生成订单也用这两列。
- 只生成草稿，**不调用提交接口**；草稿的制单人是当前用户。
- 支持的单据：一期销售订单；二期采购订单、供应商送货单（生成收货草稿）。

## 8. AI 客服与坐席辅助（1.9.0）

- 渠道：客户门户网页、公众号（只接消息）、企业微信客服。每个渠道一个接入适配器，统一转成 `ai_conversation`。
- 客服助手的工具集**独立配置且更少**：只能查当前门户用户所属往来单位的订单、发货、对账、发票；工具在 erp-server 端再次按门户用户的往来单位过滤。
- 回答前后都经过敏感词过滤（Y-10），命中时替换并记录。
- 转人工：用户要求、连续两次点踩、命中投诉 / 退款争议意图、置信度低时，生成 `cs_ticket`（见 07）并通知值班客服。
- 坐席辅助：客服处理工单时，侧栏显示客户近期订单、未结款项、相关知识和建议回复（建议回复只能复制，不能自动发送）。
- 上线前：完成生成式 AI 服务合规评估；越权、提示注入、转人工三类测试 100% 通过。

## 9. 安全

| 风险 | 措施 |
|---|---|
| 越权 | 工具在 erp-server 端按用户权限执行；客服工具再按往来单位过滤；工具不接受租户、公司参数 |
| 提示注入 | 知识库内容、用户输入、邮件、OCR 文本都放在“资料”区，系统提示明确其为数据；工具调用只能用预定义工具，参数 schema 校验 |
| 数据外泄 | 境内部署默认不把业务数据发送给境外模型；路由配置中标记模型的数据出境属性，管理员显式确认后才能启用 |
| 输出安全 | 前端用 markdown-it 渲染后经 DOMPurify 清洗；不渲染模型输出中的 HTML 和脚本链接 |
| 审计 | 每次工具调用在 erp-server 审计中标记“经 AI 助手”；erp-ai 记录请求日志 |

## 11. 评测

| 表（erp_ai） | 说明 |
|---|---|
| `eval_set`、`eval_case` | 评测集与用例：问题、标准答案要点、应引用的文档、应调用的工具与参数、应拒答标记 |
| `eval_run`、`eval_result` | 每次运行的模型配置、得分、逐条结果 |

| 场景 | 指标 | 上线线（初始，按实际调整） |

| AI 录单（≥ 100 份） | 字段级准确率 | 客户、SKU、数量 ≥ 95% |

评测由 `POST /ai/v1/admin/evals/{setId}/run` 触发，修改提示词、模型路由或检索参数后必须重跑，结果不低于上一版才能发布。

## 12. 部署

- `erp-ai`：独立进程，2 核 4G 起步；无状态，可多实例。
- OpenSearch：单节点 4 核 16G 起步，安装 IK 分词插件；每日快照。
- 向量与重排服务：CPU 可运行，GPU 更快；私有化对话模型需要 GPU（按模型规模评估）。
- Nginx：`/ai/` 路径 `proxy_buffering off`、`proxy_read_timeout 300s`。

## 13. 验收

1. 内部助手：员工问“退货后退款怎么操作”，回答步骤正确并引用《用户使用手册》对应章节；问知识库外的问题时明确说没有资料。
2. 查数：“华东商贸本月还欠多少”，结果与应收账龄报表一致；仓库范围受限的用户问不在范围内的仓库库存，回答“无权查看”。
3. AI 录单：客户订单截图 → 草稿，客户和 SKU 匹配正确，低置信字段标黄；草稿未经用户提交不进入审批。
4. 客服：门户用户问其他客户的订单，被拒绝；投诉类问题自动转人工并生成工单。
