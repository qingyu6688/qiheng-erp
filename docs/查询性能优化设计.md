# 查询性能优化设计

日期为 2026-11-16，所属任务为 M10 / O-26，维护邮箱为 maorongkang@gmail.com。

## 范围与基线

本轮以 M10 已验证提交 `b73ff35` 为基线，在独立工作目录和本机 MySQL 8.0.46 容量库中复测。保持六个真实查询入口、两个租户、四家公司、20100 个目录 SKU 和原有业务对账。

最终交付 0.8.1 曾完成两轮 1000 RPS，本轮先核对历史记录，再针对当前 M10 重新测量。采样轮实际完成 24580 次，P95 为 948ms，调度丢弃 5421 次，业务错误和对账差异均为零。该轮开启 JFR，另记录关闭采样的对照轮。

JFR 显示 `QueryInfo` 和 `StringInspector` 的 SQL 解析调用频繁，主要经由 JDBC 客户端预处理语句创建进入。当前驱动的预处理缓存关闭，重复查询会重复分析相同 SQL。

## 实现

通过 Hikari 数据源属性开启 Connector/J 的 `cachePrepStmts`，每个物理连接最多缓存 128 条 SQL，单条 SQL 长度上限 8192 字符。缓存保存驱动解析结果，业务查询仍读取数据库，账号状态、密码版本、角色和公司仓库权限继续逐请求核对。

Spring Session 显式使用 `on_save` 和 `on_set_attribute`。每次请求仍加载会话，并在结束时维护最近访问时间及滑动过期。记录 Redis 链路验证一次会话读取及实际写回次数。

容量诊断增加连接池上限、空闲及等待连接数、驱动缓存配置和 MySQL 连接上限，确认本机 HTTP 线程 200、Hikari 上限 30、MySQL 上限 150 的实际值。SQL 与字段映射的后续改动按测量证据决定。

## 正确性验证

沿用真实数据库和 HTTP 权限回归，增加同一会话连续查询后撤销角色、公司和停用账号的检查，确认下一请求生效。执行后端完整测试、前端 lint、测试、生产构建和浏览器回归。

## 压测与交付

先做固定阶梯预热，之后连续运行三轮 30 秒的 1000 RPS。每轮记录实际完成数、P50/P95/P99、六条路径各自 P95、调度丢弃、系统错误、四家公司八类对账和唯一性检查。保存失败轮与成功轮的原始结果、JAR SHA-256、JVM 参数和采样文件。

本机通过标准为每轮至少完成 30000 次，聚合及各路径 P95 小于 500ms，调度丢弃、业务错误及对账差异为零。本机结果写入容量报告，目标服务器分机压测继续按开发计划验收。

关闭采样的普通基线对照完成 30001 次、P95 138ms、P99 251ms、零丢弃。最终 M10 产物连续三轮完成 30001 / 30000 / 30001 次，P95 为 15 / 14 / 15ms，P99 为 61 / 19 / 24ms，全部零丢弃、错误与对账差异。采样失败、普通对照和最终各路径指标分别见《M10本机验收报告》。
