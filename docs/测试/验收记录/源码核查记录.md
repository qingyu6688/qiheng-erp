## 现有功能范围

官方说明将“开源版本”和“全部功能版本”区分展示。开源范围包括零售、采购、销售、仓库、财务、报表、商品、基础资料和系统管理；完整盘点、多级任务审核、生产和总账等列在全部功能版本中。

因此，不能仅凭演示站页面认定全部功能均可从该开源仓库直接取得。新系统的功能优先级以《重构设计方案》为准。

来源：[官方功能清单](https://www.gyjerp.com/doc/archive/fun-list.html)。

## 代码与表结构观察

| 观察 | 核查位置 | 对新系统的启示 |
|---|---|---|
| 构建配置使用 Spring Boot 2.0.0、Java 8；前端依赖 Vue 2.7 | 后端 `pom.xml`、前端 `package.json` | 参考业务和兼容行为，新工程重新选择受维护且相互兼容的工具链 |
| `DepotHeadService` 约 2027 行，依赖库存、客户、账户、财务单据、权限、日志等多个服务 | 该文件第 44—81 行及单据操作方法 | 按销售、采购、库存、结算拆分责任，应用服务协调用例 |
| `DepotItemService` 约 1631 行，明细处理、关联单据状态、库存和成本计算位于同一服务 | 明细保存、库存更新、成本更新方法 | 把库存余额、成本核算与单据输入解析分开 |
| 现有代码已经使用 `BigDecimal`、SQL `DECIMAL` 和事务注解 | 账户、单据和库存相关服务与初始化 SQL | 金额精度是基础，还需要一致的过账、幂等、锁和核销规则 |
| 多结算账户及其金额在单据主表中以两个字符串列表保存，服务逐项解析 | `DepotHeadService` 第 1252—1264 行；`AccountService` 第 322—369 行 | 新系统使用有约束的收付款明细和核销分配表 |
| 保存单据的重复提交检查采用 Redis 读取后写入两秒标记 | `DepotHeadService` 第 1436—1444 行 | 新系统使用数据库持久化幂等记录和业务唯一约束；短时防抖只改善交互 |
| 审核方法先读取状态、校验，再按 ID 更新；库存校验与库存更新分属不同步骤 | `DepotHeadService` 第 747—827 行 | 需要数据库条件状态迁移和并发测试，不能只依靠普通读取 |
| 当前库存更新读取并汇总业务数据，再插入或覆盖当前库存记录 | `DepotItemService` 第 1273—1290 行 | 写入使用余额条件更新加不可变库存流水；历史重算放到对账和修复任务 |
| 仓库初始化 SQL 中，单号为普通索引；当前库存的商品、仓库、租户为独立普通索引 | `jsh_erp.sql` 第 133—176、454—466 行 | 新系统显式建立租户内单号唯一约束和库存自然键唯一约束；不能推断所有实际部署均使用同一结构 |
| 编号服务以固定业务序列键获取 Redis 锁，再更新数据库序列 | `SequenceService` 第 79—119 行 | 避免所有租户、所有单据共用一个串行编号入口；业务编号分段，数据库唯一约束兜底 |

上述“先读后改”路径是否已经在其他入口获得锁，需要全链路运行验证。本次不把局部代码观察直接等同于已确认的超卖、重复记账或越权漏洞。

## 技术设计依据

以下资料用于验证机制和兼容性。业务拆分、表设计、验收指标及开发阶段是本方案建议，不是对这些项目实现的照搬。

- [Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)：核对 Java 和构建工具支持范围。
- [MyBatis Spring Boot Starter 兼容矩阵](https://mybatis.org/spring-boot-starter/mybatis-spring-boot-autoconfigure/)：Boot 4.x 与 Starter 4.0 的对应关系。
- [Spring Modulith 模块结构验证](https://docs.spring.io/spring-modulith/reference/verification.html)：验证模块无环和只通过公开接口访问。
- [Spring Modulith 事件机制](https://docs.spring.io/spring-modulith/reference/events.html)：区分事务内同步调用、异步监听和持久化事件发布。
- [Spring 事务回滚规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)：业务异常回滚必须有明确策略。
- [MySQL DECIMAL](https://dev.mysql.com/doc/refman/8.4/en/precision-math-decimal-characteristics.html)：验证精确数值存储能力。
- [MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)：事务内锁和队列任务领取设计。
- [MySQL 死锁处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)：短事务、固定加锁顺序和事务重试。
- [ERPNext 不可变账本](https://docs.frappe.io/erpnext/immutable-ledger-in-erpnext)：参考保留原始过账并追加冲销的业务处理原则。
- [ERPNext 收付款核销](https://docs.frappe.io/erpnext/payment-reconciliation)：区分资金发生、核销关系和银行对账。
- [Stripe Webhook 文档](https://docs.stripe.com/webhooks)：外部支付集成需要处理验签、重复和乱序通知；本方案不限定使用 Stripe。
- [Tailwind Preflight](https://tailwindcss.com/docs/preflight)：辅助使用工具类时可省略全局基础重置，避免对现有组件样式产生额外影响。
