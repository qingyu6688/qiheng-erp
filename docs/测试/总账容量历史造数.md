## 业务事实

历史按顺序交替办理金额 2 元的客户收款和金额 1 元的供应商付款。此配比刻意让账户始终可支付，且每个月两类来源都有可独立核对的金额。每张单据以制单人新建并提交，以另一位复核人确认。确认产生 `journal` 和 `journal_line`，并在同一业务事务内发布 `journal.posted`。真实 `ledger_projection` 消费者处理后发布 `gl.journal.requested`，真实 `gl_voucher` 消费者调用制证与过账，引擎更新期间余额。

现有容量夹具的历史订单只用于其它读写场景。`GlMonthAcceptanceIT` 验证单月购销闭环。历史生成器独立办理真实单据并消费两级事件，复用这些服务和账套初始化做法。

## 运行条件

在单独的 MySQL 和 Redis 实例上运行，数据库名格式为 `erp_load_o30_<小写字母或数字>`，主机使用回环地址。实际 ERP 后端、迁移和测试生成器须来自同一份固定源码。以 JDK 21 在 `erp-server` 目录执行以下命令。

```powershell
mvn -o -ntp "-Dtest=GlHistoryCapacityIT" test
```

构建所需的 Maven 依赖须在运行前准备妥当。`ERP_TEST_ROOT` 与 Java/Maven 的临时目录应使用隔离存储。Windows 拒绝 C 盘、相对盘符路径和网络根。Java 在启动 Spring 和迁移前先连指定实例，核对真实数据库名和 `@@datadir`。已存在目录用真实路径解析并与显式隔离根比较。业务数据库用户需要为本轮夹具创建三张进度表及准备主数据的权限，采集器仍使用专用只读账号。

## 阶段和恢复

1. 使用 `first`，固定相同数据集、源码、构件和运行环境，先加少量业务凭证做本机校准。每轮设置独立输出文件名。同一数据库、运行标识及首月下可多次调用 `first`，直到证据中 `complete=true` 且首月达到 100,000 张。生成器拒绝在已有后期业务分录时采集首期基线。
2. 完成第一期后，生成器额外生成 100 张同构手工凭证，逐张由另一用户复核并停在 `approved`。首期结果中的 `postVouchers` 是这些凭证的十进制 ID 字符串和已复核版本。按《容量测试报告》的清单格式，使用该期的实际 ID、月份、本次运行标识与同一候选包运行 `gl_capacity.py post`，保存原始 JSON 和逐次 JSONL。此时只允许存在第一期的已过账样本。
3. 使用 `remaining` 并提供首期原始采集 JSON。入口比对租户、公司、首期、源码、构件、运行环境和数据库参数；检查首期前后快照的规模、后期无已记账事实和至少 100 张唯一手工样本的真实记账状态、版本与 HTTP 结果。任一检查失败时，修正首期采集证据再运行。逐期生成剩余 11 个月，使用同一候选 JAR 与配置。每轮依然可限制新增数并在新文件中保存进度。
4. 完成末期后生成同构的另外 100 张待记账手工样本。合并首期和后 11 期 ID 作为末期清单，依次采集末期记账、稳态和收尾队列、正式两项逐行对账，按《容量测试报告》的原阈值运行 `evaluate`。

每张单据的建立、提交、确认及 `o30_history_cursor` 递增在同一事务。中途回滚时本张单据与进度都回滚；事务已提交而消费进程中断时，下次先恢复租约并处理剩余事件。在独立短事务中分配的单号允许出现间隙。事件身份和 Inbox 由现有业务层去重。每 25 张及期末通过正常领取与消费接口处理事件。已确认的死信、消费错误和等待超时会暴露为运行失败。

每期核对原收付款的状态和两位经手人、运营分录、两级 Outbox 和 Inbox、已记账总账凭证、关联业务分录的总账明细，以及余额行。目标 N 张时，收款数量为向上取整 N/2，付款数量为向下取整 N/2，总账明细为 2N 条，借方和贷方各等于收款数乘 2 元再加付款数乘 1 元。每条总账行逐项核对原分录金额和方向。正式的完整逐行余额与业务对账继续由异步对账接口出具，微型集成测另行实际调用相同两类对账逻辑。

## S09 负载

历史收付样本用于比较过账耗时随历史规模的变化。S09 稳态应办理真实销售与采购全流程并计算各自产生的总账事件。以销售 1,000 单/日、采购 200 单/日和最忙小时占 30% 计算，峰时销售约 0.08333 单/秒，采购约 0.01667 单/秒。如果完整销售链实测平均产生 S 条、采购链产生 P 条总账事件，队列目标为 `(300 × S + 60 × P) / 3600` 条/秒。保留测得 S 和 P 的原单范围、单据类型、退款或退货组合以及对应事件计数，再将结果传给 `evaluate --target-event-rate`。

## 增量余额与全量重建

独立的 `GlHistoryRefreshIT` 在同构隔离副本复核上述 12 期。先停止样本写入，待两级 Outbox 均清空后再比较，以免新增业务混入前后快照。按前述配置提供实例、样本和隔离根，另设置 `ERP_O30_REFRESH=1` 和 `ERP_O30_REFRESH_RESULT`，使用独立的新输出路径。在含同版生产源码的 `erp-server` 目录运行 `mvn -o -ntp "-Dtest=GlHistoryRefreshIT" test`。验证时恢复同一租户公司下复核人的真实权限和公司、仓库、部门范围。

每期先读取所有余额行的完整业务键（科目及七种辅助维度）、数量和各项期初、本期、期末金额，并实际查询资产负债表、利润表和现金流量表。随后在事务内调用 `GlBalances.refresh` 并再查一遍。按业务键排序后逐行比较，三大报表的全部报表行和勾稽结果也必须相同。每期事务明确回滚，再比较原余额行 ID，确认验证不改变库中原有余额实体。输出保留各期行数、前后 SHA-256、报表行数及勾稽状态。
