# 企业级演进规划

> 版本：1.0.0　　日期：2026-11-15
> 范围：从当前的进销存 + 业财一体系统，演进为面向中大型企业的 ERP，并加入 AI 能力（RAG、LLM Wiki、AI 客服等）。
> 前提：数据库继续使用 MySQL 8.0；不推倒重写，在现有模块化单体上扩展。
> 配套文档：《开发计划》2.0.0（M9—M16 的具体任务）、《优化文档》2.0.0（未完成的技术优化）、《业务规则》《数据库设计》《接口设计》。

## 1. 现状判断

### 1.1 已经具备的

| 方面 | 现状 |
|---|---|
| 业务范围 | 销售（订单、发货签收、退货）、采购（请购、订单、收货、退货）、库存（调拨、盘点、调整、预留）、资金往来（收付款、退款、核销、转账、开票登记、期初）、冲销、关账、十类报表、导入导出、打印、附件、审计 |
| 正确性底座 | 条件更新 + CHECK 约束、固定加锁顺序、同事务幂等、未结项 + 核销分配、累计法确认应收、期间屏障，八类对账零差异 |
| 工程 | 后端 28 个包、V1—V32 迁移；前端按路由分包；后端 410 项、前端 155 项单元测试、10 条浏览器流程；容量脚本、备份恢复演练、部署包 |
| 安全 | 会话 + CSRF、字段级权限（成本、银行账号）、仓库级数据范围、经办与复核分离、登录限流、多方式登录（短信、邮箱、微信） |

这套底座的质量已经高于很多商用中小 ERP，**后续扩展应当沿用同样的做法**（命令 + 状态机 + 事实表 + 冲销），而不是为了“企业级”换框架。

### 1.2 离“企业级大 ERP”还差什么

当前系统本质上是**单组织的进销存 + 简化业财**。企业级 ERP 的差距主要在五个方向：

1. **组织与集团**：只有“租户 → 公司 → 仓库”，没有集团、事业部、部门、成本中心，没有公司间交易和合并报表。
2. **财务深度**：凭证由业务投影生成，但没有完整的科目体系、辅助核算、手工凭证、三大报表、成本核算、固定资产、费用报销、预算、银企直连、数电发票。
3. **供应链深度**：没有批次 / 序列号 / 保质期、库位、质检、补货计划，也没有生产制造（BOM、工单、MRP）。
4. **平台能力**：审批流写死在代码里；没有自定义字段、编码规则、打印模板设计器、消息中心、开放平台和第三方对接（电商、物流、税务）。
5. **规模与运维**：0.8.1 已通过本机 20/100 行写入、1000 RPS 查询和冷连接验收，但 1000 RPS 确认轮仍有波动，且尚未在目标服务器复测；报表直接查业务库；缺少集中日志、链路追踪和告警。

## 2. 总体原则

1. **继续模块化单体。** 先用 Spring Modulith（测试依赖已引入）把 28 个包的边界验证起来，模块之间只通过公开服务和领域事件交互。只有当某个模块的扩缩容需求、发布节奏或团队归属明显不同（例如 AI 服务、报表分析、开放平台网关）时，才拆成独立服务。
2. **业务事实不可变。** 新增的财务、生产、质检模块都遵守“草稿可改、过账后只能冲销”的规则，继续使用现有的幂等、加锁顺序和期间屏障。
3. **读写分离。** 业务库只承担交易；报表、BI、AI 检索走只读副本或分析库，不在交易库上跑大查询。
4. **平台能力先于业务铺开。** 审批流、自定义字段、编码规则、消息中心这几样做好后，每个新业务模块的开发量会明显下降。
5. **AI 只做建议和草稿，不直接过账。** 所有写操作仍然走现有命令、权限和两人复核。

## 4. 业务域扩展

### 4.1 财务（最先做）

企业客户选 ERP，财务是否完整往往是决定因素。

| 编号 | 功能 | 说明 |
|---|---|---|
| F-01 | 总账 | 科目体系（按会计准则预置）、辅助核算（客户、供应商、部门、项目、成本中心）、手工凭证、凭证审核记账、结转损益；现有业务投影凭证并入同一总账 |
| F-02 | 财务报表 | 资产负债表、利润表、现金流量表，自定义报表公式；按组织合并 |
| F-03 | 应收应付增强 | 账龄分析、信用额度与信用控制、催收计划、坏账准备 |
| F-04 | 存货成本 | 在现有移动加权之外增加月末一次加权、标准成本与差异分摊；成本计算单可追溯到每笔出入库 |
| F-05 | 费用报销 | 申请、借款、报销、冲借款，按部门 / 项目归集，对接预算 |
| F-06 | 固定资产 | 卡片、折旧（直线、工作量、加速）、变动、处置，自动生成凭证 |
| F-07 | 税务 | 数电发票开具与接收（对接税务平台或第三方服务商）、进项认证、销项台账 |
| F-08 | 资金 | 银企直连（余额、流水自动下载）、银行对账、资金计划 |
| F-09 | 预算 | 编制、审批、执行控制（采购、费用超预算预警或阻断）、预实分析 |

### 4.2 供应链

| 编号 | 功能 | 说明 |
|---|---|---|
| S-01 | 批次、序列号、保质期 | 现有 `lot_key` 维度已经预留，补齐批次档案、先进先出 / 近效期先出、追溯 |
| S-02 | 库位与 WMS | 库位、上架策略、波次拣货、PDA 扫码作业、复核打包 |

| S-04 | 补货计划 | 安全库存、再订货点、按销量预测生成采购建议（见 5.6 的预测能力） |

| S-07 | 渠道对接 | 电商平台订单接入、物流单号回传、库存同步 |

### 4.3 生产制造（中期）

BOM（多版本、替代料）、工艺路线、生产工单、领料 / 退料 / 完工入库、委外加工、MPS / MRP 运算、车间报工、生产成本核算。这一块工作量最大，建议在财务和供应链稳定后再启动，或者先只做“简单装配”（BOM + 工单 + 领料完工），满足轻制造客户。

### 4.4 集团

公司间交易（内部销售自动生成对方采购）、内部往来对账、合并抵销、合并报表。依赖 E-01 组织模型和 F-01、F-02。

## 5. AI 能力规划

### 5.1 整体架构

新增独立服务 `erp-ai`，ERP 主服务不直接调用大模型。

```text
浏览器 / 企业微信 / 客户门户
        │
        ▼
   Nginx ──► erp-server（现有，业务与权限）
        │          ▲
        ▼          │ 以当前用户身份调用只读查询和“生成草稿”接口
     erp-ai ───────┘
      ├─ 模型网关：多模型路由、限流、计费、审计
      ├─ 知识库：文档解析、切分、向量化、LLM Wiki 维护
      ├─ 检索：OpenSearch（关键词 + 向量混合检索）+ 重排
      ├─ 工具层：把 ERP 接口包装成受控工具
      └─ 评测与反馈
```

**技术选型建议**：`erp-ai` 用 Java 21 + Spring AI，与主服务同一技术栈，团队不用维护第二种语言；文档解析用 Apache Tika。如果团队有 Python 经验、需要更多现成的 RAG 组件，也可以用 Python FastAPI，两者对外接口相同。

### 5.2 模型选择与合规

| 场景 | 建议 |
|---|---|
| 境内部署、处理客户和经营数据 | 使用已完成备案的国内大模型服务，或私有化部署开源模型（推理用 vLLM）。面向公众提供生成式 AI 服务（如对外 AI 客服）需符合《生成式人工智能服务管理暂行办法》，上线前做内容安全审核和备案评估 |
| 海外子公司、或数据可出境的场景 | 可接入 Claude：复杂分析和多步工具调用默认用 `claude-opus-5-5`；对话量大、需要压成本的路由在评测通过后可改用 `claude-sonnet-5-5`；意图分类、字段抽取这类简单任务可用 `claude-haiku-5-5`。三者都支持 100 万 token 上下文、工具调用、文档引用和提示缓存 |
| 向量模型与重排 | 中文效果好的开源模型私有化部署（如 bge-m3 + bge-reranker 系列），向量不出内网 |

模型网关必须做到：**换模型只改配置**；按租户统计 token 用量和费用；每次调用记录模型、输入摘要、工具调用和结果（不记录完整敏感字段）；单租户日额度上限。

### 5.3 知识分三层，业务数据不进向量库

| 层 | 内容 | 用法 |
|---|---|---|
| 制度与产品知识 | 用户手册、业务规则、操作 SOP、常见问题、产品资料、合同模板 | RAG 检索 + LLM Wiki |
| 企业私有文档 | 上传的合同、报价、技术规格、内部通知 | RAG 检索，按文档 ACL 过滤 |
| 实时业务数据 | 订单、库存、应收、单据状态 | **不做向量化**，通过工具实时查询，沿用当前用户的权限和数据范围 |

第三层最重要：把业务数据塞进向量库，会绕开字段权限和仓库范围，而且数据很快过时。模型只能通过“查询工具 → ERP 接口 → 权限校验”拿到业务数据。

### 5.4 RAG 设计

1. **入库**：上传 → 类型和大小校验（沿用附件规则）→ Tika 解析 → 按标题层级切分（保留章节路径）→ 向量化 → 写入 OpenSearch。每个片段带租户、组织、可见角色、来源文档、版本、页码。
2. **检索**：关键词（中文 IK 分词）+ 向量混合召回 → 按当前用户的租户和 ACL 过滤 → 重排取前 5—8 段。
3. **生成**：回答必须带引用（文档名 + 章节 / 页码），找不到依据时明确说“知识库中没有相关内容”，不编造。
4. **更新**：文档新版本上传后旧片段失效；删除文档同时删除片段和 Wiki 中的引用。
5. **隔离**：OpenSearch 按租户分索引或强制租户过滤条件，检索层不信任前端传入的租户号。

### 5.5 LLM Wiki

RAG 每次从原始片段里临时拼答案，同一个问题不同人问可能得到不一致的说法。LLM Wiki 的做法是：**让模型把原始资料预先整理成一套结构化、互相链接的知识页面，并持续维护**，问答优先查 Wiki，再回溯原文。

| 环节 | 做法 |
|---|---|
| 生成 | 新资料入库后，由后台任务让模型更新相关主题页（如“销售退货流程”“信用额度规则”），每页有摘要、正文、相关页面链接和引用来源 |
| 审核 | 模型生成或修改的页面先进入“待审核”，由知识管理员确认后发布；页面保留版本历史，可回滚 |
| 维护 | 定期“体检”：找出互相矛盾的说法、失效链接、引用已删除文档的页面、长期无人访问的页面，生成待办给管理员 |
| 问答 | 先检索 Wiki 页面，命中后附原文引用；Wiki 没覆盖时退回普通 RAG，并把高频未覆盖问题加入 Wiki 待写清单 |
| 起步内容 | 现有 `docs/` 下的《业务规则》《用户使用手册》《运维手册》可以直接作为第一批资料 |

这样做的好处是：答案口径统一、可审核、可追溯，员工也能直接浏览 Wiki，而不只是通过对话框。

### 5.6 功能清单

| 编号 | 功能 | 面向 | 说明 | 阶段 |
|---|---|---|---|---|
| A-01 | 知识助手 | 内部员工 | 基于 Wiki + RAG 回答“怎么操作”“规则是什么”，带引用 | AI-1 |
| A-02 | 智能查数 | 内部员工 | “华东商贸本月还欠多少钱”“SKU-A 还能卖多少”。模型从一组预定义的只读查询工具里选择并填参数，**不让模型自由写 SQL**；结果中的金额、数量直接来自接口，模型只负责组织语言 | AI-2 |
| A-03 | 单据解释 | 内部员工 | 在详情页问“为什么不能发货 / 为什么关账检查没过”，模型读取单据状态、`allowedActions`、关账检查结果后用人话解释，并给出跳转链接 | AI-2 |
| A-04 | AI 录单 | 内部员工 | 上传客户订单 PDF、微信截图、邮件、送货单照片 → OCR + 模型抽取 → 匹配客户和 SKU → 生成**草稿**，标出低置信度字段，由人确认后提交 | AI-3 |
| A-05 | AI 客服 | 外部客户 | 在客户门户、公众号、企业微信中回答订单进度、物流、对账、开票、退货政策；客户身份通过门户登录或绑定的往来单位联系人确认，只能查自己的数据；处理不了时转人工并生成工单 | AI-4 |
| A-06 | 客服坐席辅助 | 内部客服 | 人工客服接待时，侧栏实时给出客户近期订单、未结款项、建议回复和相关知识 | AI-4 |
| A-07 | 经营分析摘要 | 管理层 | 每周 / 每月自动生成经营简报：销售、毛利、库存周转、应收账龄的变化和原因，数字来自报表接口，附图表 | AI-5 |
| A-08 | 异常检测 | 财务、内控 | 重复付款、价格异常偏离、负毛利订单、异常折扣、频繁冲销等，用统计规则 + 模型解释，进入预警中心 | AI-5 |
| A-09 | 需求预测与补货 | 采购、计划 | 按 SKU、仓库预测未来 4—12 周销量，生成补货建议；以时间序列模型为主，大模型只负责解释和交互 | AI-5 |
| A-10 | 主数据治理 | 资料管理员 | 识别重复客户、重复商品，建议分类、规格标准化 | AI-5 |

### 5.7 安全与边界

1. **权限不外溢**：AI 调用 ERP 接口时使用当前用户的身份（或客户门户用户的受限身份），所有权限、数据范围、字段级权限照常生效；AI 服务本身不持有超级账号。
2. **只读优先，写操作只到草稿**：A-04 生成的是草稿；任何提交、审批、过账、付款都由人在原页面上点击完成，两人复核规则不变。
3. **提示注入防护**：知识库文档、客户输入、邮件内容都当作数据，不当作指令；工具调用参数做 schema 校验；对外客服的工具清单单独配置，比内部助手更少。
4. **数字不让模型算**：金额、数量、库存只展示接口返回值，和现在“前端不自行计算”的原则一致。
5. **审计**：会话、工具调用、引用来源、用户反馈全部落库，可按用户、客户、时间查询；敏感字段在日志中脱敏。
6. **人工兜底**：对外客服遇到投诉、退款金额争议、置信度低的问题直接转人工。

### 5.8 新增数据表（示意）

| 表 | 用途 |
|---|---|
| `ai_conversation` / `ai_message` | 会话和消息，带渠道（内部、门户、企业微信）和用户或客户联系人 |

向量和片段正文存 OpenSearch，MySQL 只存元数据和关联关系。按现有规范新增迁移文件，不修改历史迁移。

### 5.9 评测

AI 功能上线前必须有评测集，没有评测集的改动不发布。

- **知识问答**：200 条以上真实问题 + 标准答案 + 应引用的文档，指标为答案正确率、引用准确率、该拒答时的拒答率。
- **查数和单据解释**：每个工具 20 条以上问法，校验选对工具、参数正确、结果与报表一致。
- **AI 录单**：100 份以上真实单据样本，按字段统计抽取准确率。
- **AI 客服**：越权测试（问别的客户的数据）、提示注入测试、转人工触发测试，必须 100% 通过。
- 线上持续收集点踩样本，每月补充进评测集。
