# 可观测性设计

日期为 2026-11-16，所属里程碑为 M10，维护邮箱为 maorongkang@gmail.com。

## 本轮范围

按照《开发计划》第 7 节，在目标环境准备期间先交付 O-28 的运行监控能力，同时处理 O-21 和自动检查。使用 JDK 21、MySQL 8.0.46 以及现有模块化单体。

## 指标与访问

启用 `observability` 配置后，Actuator 使用独立的管理端口，默认仅监听回环地址。Prometheus 使用独立 Bearer 凭据采集 `/actuator/prometheus`。管理端口由运维网络访问，Nginx 对外入口继续使用原来的业务路由。

Micrometer 提供 HTTP 延迟直方图、错误数、JVM、磁盘和 Hikari 指标。后台每 30 秒采集 Outbox、导入、导出的待处理数、失败数和最旧等待时间，抓取请求读取内存快照。指标标签只包含固定任务类型和状态。数据库采集失败时，健康指标变为 0，旧快照由时间戳指标标识。

备份脚本通过可选的 node_exporter textfile 目录输出最近尝试、成功和失败状态。备份任务中断由成功时间过期和尝试超时规则检测。备份调度每天至少执行一次。

## 链路与日志

通过外置 OpenTelemetry Java Agent 采集 HTTP、JDBC 和 Redis 调用，使用 W3C Trace Context 传播链路。采样率可配置，生产初值为 10%。Agent 的指标、日志导出关闭，分别由 Micrometer 和日志采集器负责。

`observability` 配置排除 Spring Boot 的 `LettuceObservationAutoConfiguration`，由 Agent 统一提供 Lettuce tracing。内置配置会在客户端构建时覆盖 Agent 已注入的 tracing，本机演练对此执行真实 Redis 片段检查。

请求日志继续携带服务器生成的 `requestId`，同时写入 `trace_id`、`span_id`。Grafana 使用 Loki 日志中的 `trace_id` 跳转 Tempo。SQL 参数、HTTP 请求正文、Cookie、验证码和业务凭据不进入链路属性。

Prometheus、Grafana、Tempo、Loki、Alloy、Alertmanager 使用独立 Compose 文件，通过受控网络连接已有 API 和 Worker。服务端口默认绑定回环地址。所有服务保留持久卷并设置保留期。镜像标签与采集器版本写入配置和运维文档。

## 告警

告警覆盖业务 API 错误率、P95 延迟、Hikari 连接等待、Outbox 积压与死信、导入导出失败、指标采集失效、备份失败与过期、磁盘不足。Alertmanager 向私有配置中的 Webhook 投递，支持恢复通知。

规则测试覆盖触发与正常状态。本机演练使用测试库中的专用企业制造十分钟前的 Outbox 事件，确认实际指标、Prometheus 告警、Alertmanager 和本机接收器形成闭环，随后清理本轮数据。

## 登录密钥升级

按 RFC 5869 的 HKDF-SHA256 从现有 32 字节主密钥派生两把 32 字节子密钥，使用 `erp-login-cipher-v1` 和 `erp-login-code-v1` 区分用途。AES-GCM 密文使用 `2.` 前缀，旧 `1.` 密文继续按原主密钥解密。成功使用旧渠道配置后，以原密文和原版本为条件更新为新密文，并发配置更新优先。配置版本反映管理员修改，存储格式迁移沿用原版本。

所有 API 节点在同一维护窗口升级。升级前发出的验证码在新版本中需重新发送，最长等待原有 60 秒发送间隔。保留主密钥及数据库备份以支持恢复。
