# 柒衡 ERP 1.x 升级到 2.0 指南

## V107 进项核对底层（2.1.0 开发中）

当前开发构建的数据库终点为 107。本批只完成进项来源、多对多关系、历史释放及金额内核；核对接口、冲销联动、报表与页面尚未完成，当前没有发布本批构建。

V106→V107 已在独立新库装入旧关联后演练通过，原票和应付金额、版本、创建与更新时间均保持不变。旧关系保留，已失效、金额变更或已作废的关系标为已释放并附提示；旧更新时间不是已验证的原核对时间，`legacy_migrated` 用于标识该边界。新增手工登记、作废及未到票报表权限仅按已有授权管理条件迁移。V107 成功应用后冻结，后续结构变更必须另加迁移。

## V106 采购费用分摊（2.1.0 开发版）

该批数据库业务版本终点为 106。新增费用单、分摊和逐仓成本表、公司默认参数及费用权限；历史已确认订单费用只映射进度，原应付、到期日和库存成本不变。默认开启资本化，希望继续首次收货整笔记费用时，在新业务开始前关闭公司开关。

V105→V106 专用新库演练已通过，原费用、应付、更新时间和版本保持不变，超额确认、残缺账期、不平衡过账均被约束拒绝。迁移已应用并冻结。生产仍须停写、备份并完成还原演练；切换后检查分批收货、承运商费用、冲销、库存与往来对账及总账同步。

## V105 采购调价（2.1.0 开发版）

V105 新建调价头、明细、逐仓成本归属记录，并增加原收货累计调价和退货计价基准。迁移不回写历史收货货款、税额、单位成本、出库快照及往来到期日，历史未调价行继续沿用原退货算法。该批数据库业务版本终点为 105，升级前仍需按本指南保留应用、数据库和对象备份并完成停写检查。

运行账户需要新增调价权限；系统管理员按既有授权条件自动取得，其余角色由权限管理员配置。业务单据按当前部门和仓库范围可见，成本预览、批准、过账要求完整公司范围及成本权限。详情、往来、报表和旧幂等响应还会检查实际成本归属仓。

本轮 V104→V105 演练使用新建隔离库，不在出现过失败的库上做迁移修复。升级后的功能验收应覆盖部分出库调价、退货计价、冲销和总账同步。生产迁移、正式发布及历史全规模容量验收单独记录；本机开发通过不表示线上已经升级。

## V104 账期与存量到期日

升级后先在公司业务参数配置默认账期，再按客户、供应商角色维护例外账期。销售和采购订单审批时冻结账期；已存在的未清往来不自动补到期日，避免把未知付款约定改成逾期。

需要补录存量时，在项目根目录执行下面的只读预览命令。`DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASSWORD` 使用当前进程环境变量，账号只需查询权限；口令不会写入命令行。明确填写目标库、租户和公司编号，输出目录必须尚不存在：

```powershell
python scripts/preview-payment-terms.py --database <目标数据库> --tenant <租户编号> --company <公司编号> --output-dir <新的私有预览目录>
```

工具仅 SELECT，输出《到期日回填预览.json》和《回填到期日.sql》。候选范围为该公司尚未核销完、没有到期日的正常应收应付；按当前角色或公司账期计算建议日期，未设置账期的记录只列入预览。该结果不能代替历史合同，应由财务逐项确认。

管理员审核后可手工执行 SQL。每条更新检查租户、公司、原版本和到期日为空，并回显影响行数；SQL 保持事务未提交，全部确认后手工 COMMIT，有差异则 ROLLBACK。工具不会执行这些更新。预览含往来金额，留在私有目录，不提交 Git 或部署到静态网站。

## 版本和工具

源库以最后一个 1.x 候选的 Flyway V87 为基线，对应提交 `0f05ea31cbdf3446bb58d8f44442012f97eca1c7`。该源码的 Maven 构件内部版本为 `1.0.0`，部署时按源码提交、包摘要和 Flyway 历史识别。工具也接受通过历史脚本校验的 V88 至 V97 候选库。目标 ERP 版本为 `2.0.0`，数据库终点以候选构建报告为准，阶段 A 候选为 V103，增加审计封存表、摘要视图及定时任务。

在仓库根目录或解压后的 2.0 候选包根目录执行。Windows 使用 PowerShell 7，Linux 使用 `sh`。两者调用同一套 Python 3.11+、JDK 21 和 MySQL 8.0.46 工具。命令需要能从 PATH 找到 `mysql` 和 `mysqldump`，也可用同名参数指定可执行文件。应用、数据库版本探测和开放平台分别沿用 `/api/v1`、`GET /api/v1/system/version` 和 `/open/v1`。Web 和移动端检测到 API 主版本与 2.0 不一致时会提示升级。

升级工具操作专用 MySQL 实例。实例需开启 binlog、GTID 和持久化全局变量，binlog 须覆盖实例内全部数据库。工具用 `offline_mode` 拦住运行账户的连接。升级使用具备读取审计、备份、创建库、迁移和设置持久化变量权限的独立运维账户。API 和 Worker 账户不得持有可绕过停写或关闭会话 binlog 的管理权限，包括 `CONNECTION_ADMIN`、`SUPER`、`SESSION_VARIABLES_ADMIN` 和 `SYSTEM_VARIABLES_ADMIN`。维护期内暂停其他管理连接、复制写入、数据库调度事件和文件落盘任务。[MySQL 8.0 系统变量](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_offline_mode)

## 准备停写窗口

1. 保留 1.x 的服务端、前端、启动配置和包摘要。准备 2.0 的 JAR、Web 资源和移动端构建产物。
2. 准备一个新候选库、新候选对象路径和受权限保护的记录目录。生产使用共享对象仓时，先在停写窗口内完成私有对象导出。目录应包含原始对象键，工具会按数据库中的有效附件核对大小和 SHA-256。
3. 用私有配置文件设置 `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`。可选设置 `DB_SSL_MODE`、`DB_SSL_CA` 和 `JAVA_HOME`。跨主机使用 TLS，证书校验模式还需在 JDK 中信任相应 CA。配置文件、报告和备份保存在受限目录。
4. 设置 `UPGRADE_MAINTENANCE_HOOK` 为 JSON 命令参数数组，例如 `["/opt/qiheng/bin/upgrade-maintenance"]`。工具附加一个动作名称和一个 JSON 文件路径。维护脚本负责现场服务编排，先在隔离副本验证下表中的三个动作。

| 动作 | 维护命令要完成的操作 |
| --- | --- |
| `stop` | 入口进入维护状态。停止 API、Worker 和其他写入方接单，等待已接收请求和写事务结束。若先前放行脚本仍在运行，取消或等待其退出，保证它随后不会重新开放入口。入参为 `state.json`，同一动作可重复执行。 |
| `stopped` | 确认应用写入方已停止、先前放行已被收回且入口维持维护。入参为 `state.json`。核验成功时退出码为 0。 |
| `activate` | 读取 `handoff.json` 的库名、对象目录和 API 主版本。为指定目标配置独立的运行授权，启动匹配版本的 API 与前端，验证登录、权限及健康检查，再启动 Worker 并放开入口。 |

建议维护命令先通过回环地址检查启动结果和版本，再开放外部入口。升级确认前保持旧版 API、Worker、移动端设备和开放平台的写入口关闭。打开写入口后按新版本故障处置流程处理新发生的交易。

## 执行升级

以下命令均从候选包根目录运行。源码构建时把 `--jar` 指向 `erp-server/target/erp-server-2.0.0.jar`。

```powershell
./scripts/upgrade-2.0.ps1 preflight --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run
./scripts/upgrade-2.0.ps1 upgrade --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run --target-db erp_candidate_20 --target-objects /private/objects-20 --dedicated-instance
./scripts/upgrade-2.0.ps1 finish --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run --approve-scopes
```

Linux 用 `sh ./scripts/upgrade-2.0.sh` 替换命令开头，参数相同。执行 `finish` 前由管理员打开 `02-data-scope.json`，检查公司、仓库、部门规则和每类单据的可见数量及集合摘要。

| 步骤 | 核对点 |
| --- | --- |
| `preflight` | Flyway 脚本历史、文件任务和后台租约、当前运营科目映射及近 30 天废弃 API 调用。报告列出待续接单据。V87 的在库退役清单没有已经公告并标记废弃的路由，开放平台稳定版继续提供服务。 |
| 停写与备份 | 停写确认后记录 UTC 时间、MySQL 实例 UUID、binlog 文件及位置、最终 GTID。同步备份数据库及私有对象，校验备份期间水位。 |
| 恢复验证 | 将停写备份导入新候选库，逐表比对数据摘要，核对 Flyway 历史和有效附件。原库保留作为核对来源。 |
| Flyway 和数据转换 | 从源库的实际版本执行后续迁移。按实际启用公司生成、发布和绑定默认审批，已有自定义流程匹配优先。续接没有流程的待审单据，缺原发起人权限、缺合格复核人或原关联损坏时停止。三段转换及核验记录写入 `upgrade_log`。 |
| 核验 | 比对历史单据和账本数据、既有角色及开放应用授权。八类业务核对加上批次、冻结、库位、总账试算和运营分录同账核对。期间类核对检查已关账期间。报告保存在 `upgrade-verification.json` 和 `upgrade-inspection.json`。 |
| 放行 | `finish` 再次核对核验后的 binlog、GTID 和对象摘要，然后调用维护命令完成版本切换。 |

默认流程按原审批权限从当前公司的角色中选人，并复用仓库、部门、经办复核分离、最低售价及信用复核判断。系统绑定优先级保留给升级工具，管理员可通过自定义绑定调整未来单据。流程结果调用原业务服务执行实际审批。

当前默认绑定覆盖销售订单、请购单、采购订单、退款申请、冲销申请、库存调整、盘点、其他出入库、来料检验、信用提额、客户合同、总账凭证、坏账处理、BOM、生产领退料和完工入库。往来期初与订单变更仍使用各自的复核入口，资金确认、库存过账和期间关闭继续执行原有服务端规则。

转换后的公司或仓库授权落在 `org_user_data_scope`。脚本保留原授权行，继续使用原角色部门规则求交集。角色授权及开放平台 scopes 按 `03-permission-codes.tsv` 归一化。由于安装了仓储、生产和报表模块，迁移可按既有模板为系统管理员追加这些模块的新权限，新增项列在转换报告。

## 放行过程被中断

`finish` 在解除 MySQL 停写前将状态记为 `opening`。如果放行进程退出、机器重启或维护脚本执行结果不明，先把外部入口置于维护状态。使用原配置、候选 JAR、对象仓和记录目录执行 `recover`。

```powershell
./scripts/upgrade-2.0.ps1 recover --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run
```

工具调用维护命令停止写入方，重新持久化 MySQL 停写，并核对实例 UUID、binlog 文件和位置、GTID、交接清单与对象摘要。全部一致时，状态返回原来的 `ready` 或 `rollback-ready`，入口继续停写，可按原流程重新执行 `finish` 或选择回退。重复执行 `recover` 会再次核对现场。它不启动应用或重放迁移。

发现水位推进、binlog 轮转、对象变化或证据无法核对时，工具阻止自动放行及回退。维持入口维护，确认 MySQL 停写已生效，封存当前数据库、对象和 binlog，再由业务和运维核定新增交易及处理方案。每次尝试记录在独立的 `activation-recovery-*.json`，包含期望水位、实测水位和核验状态。维护命令日志按尝试追加。`state.json` 中的 `activationRecovery` 指向最近一次通过核验的记录。

## 停写期间回退

检查未通过且未进入维护时，原应用继续使用既有数据，处理报告阻断项后重新检查。已进入维护、迁移前失败时，用下面的 `rollback` 入口核对原库和停写水位，随后用 `finish` 恢复 1.x。

迁移开始后，在同一记录目录执行以下命令。使用全新的恢复库和对象目录。

```powershell
./scripts/upgrade-2.0.ps1 rollback --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run --rollback-db erp_rollback_1x --rollback-objects /private/objects-rollback
./scripts/upgrade-2.0.ps1 finish --settings /private/upgrade.env --jar ./erp-server.jar --objects /private/objects-1x --work-dir /private/upgrade-run
```

回退会重新导入经过校验的最终停写备份，核对行摘要、附件、已记账金额、原权限和待审单据，再交给维护命令启动 1.x。工具保留候选库和各步骤报告，数据库恢复后的库名通过 `handoff.json` 传给维护命令。维护出错后先查看 `state.json` 和对应日志。若目标恢复中断并留下残缺数据库，保留现场并使用另一组未占用的库名和对象目录完成回退。

一旦入口对 2.0 开放并接收写入，旧停写备份已落后于新账本。回退需另行安排新旧版本同步和核对，先保全 2.0 停写状态与 binlog。1.x 最后一个版本的安全维护按开发计划在正式发布后提供六个月。

## 演练证据与上线核对

Windows 本机演练前，在 PowerShell 中设置 `$env:ERP_TEST_ROOT = 'D:\erp-tests'`，并把 `--work-dir`、`--objects`、`--target-objects`、`--rollback-objects` 指向非 C 盘的独立目录。工具会校验这些目录及续跑记录中的路径，把报告、备份、SQL 核验临时文件和 Java 日志保存在工作目录。演练使用的 MySQL 实例也须将 `datadir`、`tmpdir` 和服务日志配置到非 C 盘。在仓库根目录运行 `python -B -m unittest discover -s scripts/upgrade-2.0 -p 'test_*.py'` 时，Windows 会要求设置 `ERP_TEST_ROOT`，自测文件存放在该目录的 `upgrade-unit/tmp` 下。

停写前在客户数据副本分别跑两次升级和回退，保留每轮私有记录目录。逐公司检查业务和财务账号，至少核对一位限仓库、限部门的人员和拒绝访问的另一方。抽查含私有附件的在途单据、原审批人和复核权限、期末余额及未清往来。根据两次演练记录确定正式维护窗口。

在独立副本补做两次中断演练。第一轮在解除 MySQL 停写后、受理业务写入前终止放行进程，连续两次执行恢复，核对入口维持维护、MySQL 停写已持久化、状态回到待放行并可重新完成切换。第二轮在测试库产生一笔带 GTID 的事务或新增附件后终止放行，核对恢复被阻止、数据及对象保留、自动回退入口拒绝执行，并归档恢复记录。维护命令需同时验证残留放行进程已退出且不会重新启动写入方。

| 证据 | 核对方法 |
| --- | --- |
| `upgrade-timing.json` | 比较停止写入方、备份、恢复、Flyway、数据转换、核验及放行的 `elapsedMs`。阶段计时使用单调时钟，记录失败和重试。维护窗口从准备进入停写到维护命令放行完成，根据 UTC 时间计算，包含两条命令之间的人工核对时间。窗口未结束时保留时间点。 |
| `flyway-timing.json` | 按 `installedRank` 查看目标库在原源库版本之后写入 Flyway 历史的 SQL 脚本和 `execution_time`（毫秒）。续跑保留候选库中首次已执行的记录。V87 源库已完成 V37、V38 的历史回填。 |

记录客户数据副本的业务表规模、数据库与对象备份大小、实例资源、磁盘吞吐、可用空间及业务方批准的停写上限。有主备环境时同步记录复制延迟。用阶段耗时和单迁移记录定位瓶颈，超过窗口时先在副本复测实际慢步骤。所选报告保存在受限目录，外发时仅摘录已脱敏的容量、时间和差异结论。

本机测试使用隔离构造的多公司业务样本，演练结果见 [测试报告](../测试/测试报告.md)。正式客户副本、生产维护命令和上线后的性能、故障切换验收由《开发计划》继续跟踪。
