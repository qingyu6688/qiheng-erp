# ERP 运维手册

## M11 消息与运维管理（未发布）

固定任务通过job_definition及job_run_log登记、排队和租约执行。暂停自动执行后仍可明确手动触发；执行前会复核发起人。发送失败查看当前公司“消息发送日志”，日志只含掩码目标及统一错误；不要把实际Webhook、SMTP口令、手机号或投递载荷写入工单。密钥主配置共享并安全备份，不直接替换导致存量密文失效。

WebSocket经Redis广播摘要，30秒心跳、90秒超时，代理使用Upgrade及至少100秒读取超时。广播不提供持久送达保证，消息表提供恢复依据。可在系统参数设置observability.grafana_url接入现有Grafana请求号及链路查询，默认使用组织1、Loki数据源loki。查看erp_api_logs_queue_size、erp_api_logs_dropped、erp_api_logs_write_failures_total及现有磁盘/队列告警；日志队列满时应用记录限频警告，文件请求日志仍保留。

访问与任务日志30天，异常90天，消息和登录日志180天，由按企业的平台清理任务分批执行。强制下线只针对选定公开会话标识，不能索要或复制实际Cookie。权限、订阅、重试及故障处理详见[M11使用说明](../使用说明/M11组织消息与运维使用说明.md)。

适用范围：M8 本机演练与生产部署包。数据库继续使用 MySQL 8.0.46，Java 使用 JDK 21。本文中的域名、私网地址、账号名和文件路径都是模板；真实口令放在不入库的配置文件或服务器密钥管理中。文档维护：maorongkang@gmail.com。

## M10 运行监控

监控设计见[可观测性设计](../设计/可观测性设计.md)。部署模板位于 `deploy/observability`，包含 Prometheus、Alertmanager、Tempo、Loki、Alloy、Grafana 数据源和“柒衡 ERP 运行状态”看板。

### 本机验证

Windows 在项目根目录执行以下命令，使用现有私有 `.env`、已迁移的独立测试库、JDK 21、Python 3.12 和 MySQL 客户端。先完成后端构建和前端验证，再运行演练。安装脚本校验官方发行的 SHA-256，下载到忽略的 `.local/tools/observability`。

```powershell
pwsh -NoProfile -File ./scripts/install-observability.ps1
pwsh -NoProfile -File ./scripts/project.ps1 verify
./.local/tools/observability/prometheus-3.16.0.windows-amd64/promtool.exe test rules ./deploy/observability/alerts.test.yaml
python ./scripts/verify-observability.py
```

演练创建随机测试企业和管理员，在随机回环端口启动 API、Java Agent、Prometheus、Alertmanager 和本机通知接收器。通过正常登录查询账户，验证 HTTP、Redis、SQL 的共同链路和请求日志关联。再生成十分钟前的 Outbox 待处理事件，等待原规则要求的两分钟，核对实际通知和恢复通知。正常结束及异常退出都会关闭本轮子进程并清理本轮测试企业，证据写入 `.local/observability-*`。临时进程停止使用操作系统进程终止，生产部署仍按正常服务停机流程执行。

### 启用服务端指标

API 私有配置设置 `SPRING_PROFILES_ACTIVE=prod,observability`，填写安全随机生成的 `ERP_METRICS_TOKEN`。默认管理端口为 `127.0.0.1:9091`。同机 Worker 使用 9092，并设置 `ERP_SERVICE_ROLE=worker`。启用独立管理端口后，健康检查改为对应管理端口的 `/actuator/health`。业务端口的监控路径继续受路由和认证校验。

`/actuator/prometheus` 只接受 `GET` 和独立 Bearer 凭据，抓取不建立业务会话。凭据留空时拒绝抓取。管理监听地址改变为内网 IP 时，须用运维网络的访问规则限定采集端。Nginx 模板继续只转发 `/api/`。

指标包含 HTTP 直方图、JVM、Hikari、磁盘、后台队列快照。队列每 30 秒更新一次，`erp_queue_collection_success` 和 `erp_queue_collection_timestamp_seconds` 显示本轮是否成功及数据时间。`erp_queue_jobs` 的 `queue` 为 `outbox/import/export`，`status` 为 `pending/running/failed`。导入部分失败计入失败任务，Outbox 死信计入失败任务。

### Compose 监控组件

在部署目录的私有 `api.env` 和 `worker.env` 中填写相同的 `ERP_METRICS_TOKEN`，将相同值写入 `private/metrics-token` 单行文件。将安装脚本校验后的 Agent 复制为 `private/opentelemetry-javaagent.jar`。准备随机的 Grafana 初始密码文件 `private/grafana-password`，复制 `observability/alertmanager.example.yaml` 为 `private/alertmanager.yaml` 并填写实际 Webhook。创建 `private/textfile`，用于备份状态。

私有目录限制为部署账号访问，API、Worker 的环境配置文件仅该账号可读。容器绑定的凭据文件须允许相应容器运行用户读取，宿主机的私有父目录继续限制访问。使用外部 Webhook 时，Alertmanager 需要到接收端的出站访问。示例通知地址需要替换为实际接收端。

部署包解压后，在 `deploy` 目录执行下列命令。基础镜像与现有证书、数据库和 Redis 配置仍由原部署步骤准备。

```bash
docker compose -f compose.yaml -f compose.observability.yaml config --quiet
docker compose -f compose.yaml -f compose.observability.yaml up -d
```

API 与 Worker 通过受控容器网络开放管理端口，Prometheus 以私有令牌文件抓取。Grafana 绑定宿主机回环 3000，Prometheus 和 Alertmanager 分别绑定回环 9090、9093。通过 SSH 端口转发访问 Grafana，使用私有密码登录。看板包含请求率、P95、错误率、连接等待、队列、内存、磁盘、备份和日志。日志正文里的 `trace_id` 可以跳转 Tempo，使用请求号检索可定位同一请求。

Java Agent 固定为 2.33.1，Compose 中固定 Prometheus 3.16.0、Alertmanager 0.35.0、Tempo 2.9.0、Loki 3.7.10、Alloy 1.22.0、Grafana 13.3.1 和 node_exporter 1.12.1。上线审阅镜像时记录所用摘要。Prometheus 保留 15 天，链路保留 7 天，Loki 保留 14 天，各组件使用独立持久卷，组件自身日志按 50MB、7 份轮转。

Java Agent 采用 `http/protobuf` 导出到 Tempo，初始采样率为 10%。指标和日志分别由 Micrometer 和 Alloy 收集。直接运行 systemd 服务时，在私有环境配置中设置 `JAVA_TOOL_OPTIONS=-javaagent:/opt/erp/otel/opentelemetry-javaagent.jar`，填写实际 OTLP 地址，并将 Prometheus 抓取目标改为管理端口。所有调用使用同一主机时仍要为 API 与 Worker 分配不同管理端口。

### 备份指标与告警

运行备份时增加 `-MetricsDirectory`，指向 node_exporter 挂载的 textfile 目录。目录需事先存在，备份任务使用该目录的写权限。

```powershell
pwsh -File ./scripts/backup-local.ps1 -SettingsFile .local/backup.env -ObjectRoot C:/ERP/private-objects -OutputDirectory C:/ERP/backups/本轮目录 -SourceStopped -MetricsDirectory C:/ERP/textfile
```

脚本在开始、成功或失败时原子更新 `erp-backup.prom`，保留最近成功时间。执行中的任务由 `erp_backup_in_progress=1` 表示。最近尝试失败、运行超过一小时、成功备份超过 26 小时和缺失备份指标都有独立告警条件。Linux 备份调度接入同名 textfile 指标，并确保定时任务每天执行。当前 PowerShell 一致备份脚本的数据库客户端使用 Windows 工具路径。

告警还覆盖接口错误率超过 1%、P95 持续超过 500ms、数据库连接等待、五分钟以上 Outbox 积压、失败任务、队列指标过期和磁盘可用不足 15%。阈值和持续时间在 `alerts.yaml` 中维护。本机 Webhook 接收只验证通知闭环，正式收件人和轮值仍需在目标环境配置。

指标接入依据 Spring Boot 的 Micrometer 自动配置，链路接入依据 OpenTelemetry Java Agent 配置，Loki 使用 Alloy 文件采集。[Spring Boot 指标说明](https://docs.spring.io/spring-boot/reference/actuator/metrics.html) · [Java Agent 配置](https://opentelemetry.io/docs/zero-code/java/agent/configuration/) · [Alloy 文件采集](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/)

GitHub Actions 的临时 Maven 配置使用 Google 托管的 Central 镜像，以处理首次远端执行时 Central 返回的 HTTP 429。该设置仅在 CI 运行账号目录生成，镜像范围为 `central`。[Google 托管镜像说明](https://docs.cloud.google.com/docs/buildpacks/java#google_cloud_hosted_maven_central_mirror)

## 运行边界

0.8.1 将高频请求日志写入独立的 `ERP_HTTP_LOG_FILE`，避免同步控制台管道使 HTTP 线程排队。请求日志与应用日志各自轮转，业务审计仍以数据库事实为准；突然断电可能丢失尚在内存队列中的请求日志，不能将它用作资金或库存审计凭据。正常部署按服务停止流程等待日志排空，不用强杀代替停机。API 与 Worker 的两个日志路径须分别配置并纳入日志采集、磁盘容量和权限检查。

同机容量验收采用常驻/最大 HTTP 线程 200/200、接入队列 2000、最大连接 8192、数据库池 30，以及 k6 的 `GOMAXPROCS=2`。这里的 2 是发生器运行时并行度，1000 VU 仍创建 1000 个新 TCP 连接；没有更改系统 TCP、全局优先级、事务隔离级别或数据库刷盘。生产放量前在独立压测机和实际入口复测，记录 CPU、内存、磁盘、连接数与日志积压。

本机开发服务使用 8080/5173，测试与容量服务使用独立库、随机企业和临时端口。Windows 恢复演练默认在 `ERP_TEST_ROOT` 下新建 `m8-recovery-*`，独立 MySQL 使用 13308 端口。脚本保留演练数据供复核，不自动删除或覆盖数据库。

部署包包括 `deploy/nginx.conf`、API/Worker 的 systemd 模板、MySQL 主备配置、Redis TLS 配置、容器 Compose 模板及生产环境变量示例。没有服务器、域名、证书和对象仓凭据时，交付结果是可审阅的部署包和本机演练；不得把它写成已经对外上线。

## 发布前检查

在源码项目根目录执行 `pwsh -File .\scripts\project.ps1 verify`，在 `erp-web` 目录执行 `npm run lint`、`npm test`、`npm run build`。`verify` 会执行完整的 `mvn clean verify`，包含真实数据库集成测试；`mvn test` 只执行单元测试，不代替完整验收。两个既有项目脚本使用 UTF-8 BOM，并兼容 Windows PowerShell 5.1 的解析；新运维脚本明确要求 PowerShell 7。

`project.ps1`、`prepare-local.ps1`、`package-release.ps1` 和前后端构建命令仅在完整源码目录使用，依赖 `erp-server/pom.xml`、`erp-web/package.json` 等文件。交付 ZIP 是运行成品，没有源码构建目录；虽然保留这些脚本供维护参考，不要在解包目录调用源码验证、编译、数据库准备或再次打包。

解包后可用 `verify-deployment.ps1` 验证 Nginx 入口。它需要本机 PowerShell 7、Windows Nginx、OpenSSL 和已经运行的回环 API，默认 API 端口为 8080。前端成品优先取解包根目录下的 `web`，其次取源码目录中的 `erp-web/dist`，也可通过 `-WebRoot` 指定。

部署检查优先读取环境变量 `ERP_TEST_ROOT`，其次读取解包或项目根目录的 `.env` 同名配置。请使用非 C 盘的绝对路径，例如 `D:\QihengERP-Test`。每次检查都会新建唯一的 `deployment-check-*` 子目录，保存临时证书、私钥、Nginx 配置、日志和检查结果 `deployment-result.json`。Windows 下如果没有配置该变量，放在非 C 盘的部署包可将结果写入包内 `.local`；放在 C 盘的部署包需要先配置输出位置。部署包和工具路径可以含空格或中文，配置中的证书与私钥都相对于本次检查目录。

在解包根目录执行以下命令，工具路径按本机实际位置填写。

```powershell
$env:ERP_TEST_ROOT = 'D:\QihengERP-Test'
pwsh -File .\scripts\verify-deployment.ps1 -NginxDirectory 'D:\ERPTools\nginx' -OpenSslPath 'D:\ERPTools\openssl\openssl.exe' -WebRoot .\web
```

生产包不得含浏览器夹具、测试配置或开发预填密码。每个应用实例使用不同的 `ERP_NODE_ID`。节点号会去除首尾空白，空值默认为 0，非法格式及越界值以中文错误说明。

生产环境必须同时配置 `DB_MIGRATION_USER`、`DB_MIGRATION_PASSWORD`，迁移账号必须与 `DB_USER` 不同。开发和测试的两项配置可同时留空，按当前数据源账号回退。跨主机生产数据库连接至少使用 `DB_SSL_MODE=REQUIRED`，有受信证书时使用 `VERIFY_IDENTITY`。JDBC 信任证书另按服务器证书链配置。生产 Cookie 必须 `secure=true`，默认调试规范关闭。开放平台的授权管理员通过 `/api/v1/open-platform/spec` 下载单独的接口规范。

### 初始化首个企业与管理员

在已完成 V31 迁移、尚无企业的目标库执行。先核对指定库、备份水位、企业与公司资料，随后使用经授权的数据库账号运行独立初始化工具。已有迁入身份数据的库由业务管理员复核原账号和权限。

工具复用已验收 JAR 中的 MySQL 驱动、密码散列与编号组件。它将企业、公司、管理员、角色、公司范围和初始化审计在同一事务提交。已有企业时命令拒绝执行。首次登录必须改密，之后按职责分配制单、审核、过账及对账权限。

在含 `scripts/initialize-tenant.ps1` 和 `scripts/java/InitializeTenant.java` 的源码或交付目录运行。示例中的企业资料、私有配置和 JAR 路径在执行前替换为已确认的值。私有配置的 `DB_NAME` 应与 `-Database` 一致。工具优先使用成对配置的迁移账号，默认使用连接加密。本机自有 CA 或生产 `VERIFY_IDENTITY` 可在私有配置中提供 `ERP_BOOTSTRAP_DB_TRUSTSTORE` 与配套口令，使用 PKCS12。

```powershell
$temporaryPassword = Read-Host '输入首位管理员的临时口令' -AsSecureString
try {
    $env:ERP_BOOTSTRAP_ADMIN_PASSWORD = ConvertFrom-SecureString $temporaryPassword -AsPlainText
    pwsh -NoProfile -File scripts/initialize-tenant.ps1 -JarFile ./erp-server.jar -SettingsFile ./private/database.env -Database erp_prod -TenantCode EXAMPLE -TenantName '示例企业' -CompanyCode HQ -CompanyName '示例公司' -AdminUsername admin
    if ($LASTEXITCODE -ne 0) { throw '首个企业初始化失败' }
} finally {
    Remove-Item Env:ERP_BOOTSTRAP_ADMIN_PASSWORD -ErrorAction SilentlyContinue
    $temporaryPassword.Dispose()
}
```

## 数据库与网络

部署固定 `mysql:8.0.46`，不使用 `mysql:8` 或 `latest`。MySQL 8.0 的支持周期风险已由项目优化文档记录，生产应限制私网访问并安排升级验证。其他镜像必须填写已审阅的固定版本与摘要，不在模板中追逐最新标签。

同机 systemd 部署按 `127.0.0.1` 监听；容器内数据服务需把模板中的监听地址改成容器私网 `0.0.0.0`，且保持 Compose 的数据网络 `internal`、不映射 MySQL/Redis 宿主端口。网络规则只允许应用和备份连接，禁止 root 远程登录。

Compose 已用命令参数覆盖容器内监听地址。API 和 Worker 同时连接应用网络以访问外部 S3，均不映射应用宿主端口；只有 Nginx 暴露 80/443。部署前在各自的私有环境文件设置 `DB_HOST=mysql-primary`、`REDIS_HOST=redis`、相同 S3 桶和不同日志文件。数据库及 Redis 证书 SAN 必须匹配连接主机名，客户端证书文件按运行 UID/GID 授予只读权限。Redis 使用双向 TLS，客户端三项 PEM 配置已列入 `production.env.example`，其中信任证书和客户端私钥分别配置。MySQL `VERIFY_IDENTITY` 使用的 CA 需加入专用 Java truststore，通过私有 JVM 参数配置其路径与口令；不要把实际证书或口令放进模板。Redis 客户端配置依据 [Spring Boot SSL bundle](https://docs.spring.io/spring-boot/reference/features/ssl.html) 和 [Redis SSL 配置项](https://docs.spring.io/spring-boot/appendix/application-properties/index.html)。

容器模板按交付包解压根目录作为构建上下文：`docker build -f deploy/Dockerfile --build-arg JRE_IMAGE=<固定摘要的JRE21镜像> -t <私有镜像名> .`。填好 Compose 所需镜像摘要及 `deploy/private` 配置后再启动；前端挂载解包后的 `web` 目录。基础 JRE 镜像须提供 shell，以便建立仅运行用户可写的日志目录。API/Worker 示例各限制 2GiB，正式容量根据服务器实测调整；日志卷与 `ERP_LOG_FILE` 配合，不能让应用以 root 身份绕过目录权限。

主库开启 ROW binlog、GTID、`sync_binlog=1` 和 `innodb_flush_log_at_trx_commit=1`。备库使用不同的 `server-id`、只读与 `super_read_only`，通过受限复制账号和 TLS 设置复制。主备模板不会自动发起复制，也不自动提升主库；正式环境需核验复制延迟、故障隔离和防双主后再切换。异步复制不能承诺所有已确认交易零丢失。

在项目根目录执行下列命令生成基于实际表的权限脚本，先审阅输出，再由数据库管理员执行：

```powershell
pwsh -File .\scripts\database-grants.ps1 -SettingsFile .local\admin.env -Database erp_prod -OutputFile .local\grants.sql
```

生成脚本按表授权，运行角色对库存流水、预留变化、成本调整、凭证、凭证行、审批记录、审计和调拨事件事实仅有 SELECT/INSERT；权限目录、账本账户目录和 Flyway 历史只读；其他业务表按需 DML。迁移角色另有 DDL。不能先授予运行账号整库 UPDATE/DELETE 再试图用表级 REVOKE 撤回，上层授权仍会生效。账号使用 `caching_sha2_password`，跨主机账号另设 `REQUIRE SSL`。

备份账号与运行账号分开。完整逻辑备份需要 SELECT、SHOW VIEW、TRIGGER、EVENT，读取水位需要 REPLICATION CLIENT，冻结备份使用 RELOAD；这些全局权限不交给应用运行账号。对象仓桶保持私有，API/Worker 使用同一桶和区域，Nginx 不代理对象根目录。

## 一致备份

每天完整数据库加对象仓备份，持续归档 binlog，至少保留七天，每月至少做一次新目标恢复。恢复时间和恢复点必须以实测为准。

本机备份脚本要求先停止所有 API 和 Worker 写入，确认没有对象上传或清理在途，再显式提供 `-SourceStopped`。脚本在这个停写窗口内追加 MySQL 全局读锁，完整保存所有业务表、账本、幂等、Outbox、任务和审计，同时复制对象仓；清单记录数据库 SHA-256、每个对象的 SHA-256/字节数、备份时刻及 binlog 文件/位置。全局锁会在脚本结束或异常时释放。

```powershell
# 在项目根目录执行，配置文件仅包含备份账号与源库连接。
pwsh -File .\scripts\backup-local.ps1 -SettingsFile .local\backup.env -ObjectRoot C:\ERP\private-objects -OutputDirectory C:\ERP\backups\20261115 -SourceStopped
```

## 恢复与回切

在本机隔离实例执行：

```powershell
pwsh -File .\scripts\restore-local.ps1 -SettingsFile D:\erp-tests\restore.env -BackupDirectory D:\erp-tests\backups\20261115 -TargetDatabase erp_restore_20261115 -ObjectRoot D:\erp-tests\restore-objects-20261115
```

恢复脚本仅接受回环连接、未存在的 `erp_restore_*` 库和未存在的对象目录。先验证清单摘要，再导入 SQL、还原对象；发生错误时保留目标供复核，不自动删除。恢复账户和目标目录与在线服务分开。恢复后禁止立即开放流量，先核对 Flyway 历史、对象字节、幂等/Outbox/任务水位，以及库存、成本、预留、资金、未清项、凭证、库存账本、期间八类对账。

需要恢复到指定时间点时，从清单的 binlog 位置开始重放至明确的事务结束位置；不能用任意文件字节或事务中间位置截断。`recovery-drill.ps1` 会在新 MySQL 8.0.46 实例中实际验证这一过程，插入目标前后两笔标记事务，确认前一笔恢复而后一笔排除，并逐表校验与附件摘要：

```powershell
$env:ERP_TEST_ROOT = 'D:\erp-tests'
pwsh -File .\scripts\recovery-drill.ps1
```

Windows 请使用非 C 盘的英文路径，也可用 `-WorkDirectory` 指定本次演练的新目录。MySQL 的数据、临时文件、binlog、日志，以及备份、对象副本和临时凭据均保存在该次演练目录下。脚本默认结束自己启动的实例，提供 `-KeepInstance` 时保留供后续隔离应用核验。保存的指定恢复点 RPO 为零，仅表示已归档到该事务结束点的交易完整重放，不代表实时生产环境零丢失。恢复耗时、数据量和结果写入 `recovery-result.json`。

恢复到新库后，可用已构建的生产 JAR 运行同一套业务对账规则。该步骤只读恢复库，从已有真实凭证中选择三家公司，检查库存、成本、预留、资金、未清项、凭证、库存账本和期间，任何非零差异都会以非零状态退出：

```powershell
pwsh -File .\scripts\verify-recovery.ps1 -SettingsFile .local\restore-runtime.env -Database erp_restore_20261115 -JarFile .\erp-server\target\erp-server-0.8.0.jar -JavaHome E:\JDK21
```

配置文件必须指向恢复实例，使用只读所需的连接权限并启用 TLS；不能拿生产库名替换受保护的 `erp_restore_*` 参数。交付包内 JAR 名为 `erp-server.jar`，请相应调整路径。

回切前停止旧实例写入，确认新旧水位、数据范围和对象仓一致。旧服务只保留只读核对入口，不让两套系统同时写同一账本。未完成任务按原租约、断点和幂等键恢复，资金操作不能因不确定而换新请求号重复发起。

## 健康、队列和告警

接入模板配置 `SERVER_TOMCAT_ACCEPT_COUNT=2000`、`SERVER_TOMCAT_MAX_CONNECTIONS=8192` 和 `SERVER_TOMCAT_THREADS_MAX=200`。三个值分别控制 TCP 接入等待队列、Tomcat 同时管理的连接上限和处理请求的工作线程上限，不能互相替代。等待队列长度仍受操作系统实际支持影响，须通过真实连接突发测试验收。

本次容量环境的 Hikari 数据库池为 30 个连接：200 个应用线程不代表同时占用 200 个数据库连接，1000 个并发客户端也不需要 1000 个数据库连接；请求可能依次等待接入、线程、数据库连接及行锁。队列 2000 是吸收瞬时接入的缓冲，不是每秒吞吐保证。生产数据库池按数据库连接预算和实测设置，不能为消除排队而无限增加线程或连接。客户端连接拒绝、HTTP 业务错误和数据库锁等待分开统计，状态 0 的连接失败不能写成服务端业务 5xx。

`GET /actuator/health` 仅返回健康状态，生产 Nginx 不公开该路径。由内网探针检查 API、Worker 进程及数据库/Redis健康，探针失败先停止流量，再定位依赖，不能立即强行重放所有任务。

`GET /api/v1/admin/operations` 使用正常登录与 `X-Company-Id`，要求 `admin:outbox` 和整家公司范围。它只返回当前公司的导入、导出、Outbox 计数、最旧待处理秒数和未处理对账差异数，不含载荷、文件键、凭据或其他公司数据。失败任务、超过五分钟的积压、未处理差异会返回中文警告；这些是应用内告警信号，正式通知渠道和轮值由部署方接入。

基础指标包括 HTTP 延迟/错误率、Hikari 连接池占用、任务重试、最旧积压、死锁、锁等待、复制延迟和磁盘/对象仓空间。`deploy/monitoring.sql` 为受控运维连接提供不含查询正文的基础检查，不能给应用账号加系统库写权限。发生任何资金或库存对账差异都应立即调查，不用 UPDATE 抹平余额；修正走业务单据或冲销。

应用日志保留请求 ID、路径、HTTP 状态和耗时，不记录 query、请求体、Cookie、票据或口令。请求日志按 50MB 滚动，天数和总量分别由 `ERP_LOG_MAX_HISTORY` 和 `ERP_LOG_TOTAL_SIZE_CAP` 控制；Nginx/MySQL/Redis 的轮转模板单独管理。结合请求 ID 串联失败事件与审计。

## 工作流运行检查（M11，未发布）

运行角色只需主库DML，官方ACT_*结构由迁移账号执行V44创建；不打开引擎自动建表、Flowable REST、IDM或额外异步执行器。workflow.timeout纳入现有租约任务，每5秒扫描到期任务。观察job_run_log、Outbox积压/死信、流程轨迹及原单状态，结合请求号定位，不直接修改引擎或业务状态表。

API和Worker同库同事务版本运行，ERP_NODE_ID不同；消息推送仍沿用Redis广播和REST补齐。停Worker会延迟超时动作，停用匹配模型会阻止新提交流程；停用绑定后未匹配单据回到原单级审批。真实外部渠道沿用既有发送日志与重试，投递前重新校验接收人和来源权限。

恢复必须同时考虑流程、原单、幂等和Outbox，不得仅恢复业务表。关账、库存不足、原单依赖、复核分离及价格证据失败时，整次任务操作回滚，用户可刷新后通过合法驳回/重提处理；禁止直接完成ACT任务掩盖业务失败。升级和用户操作参见[部署说明](部署说明.md#m11-工作流待发布升级)及[使用说明](../使用说明/M11工作流使用说明.md)。

## M12 总账与催收运维

运营投影与总账生成是独立事件。GL映射失败应先核对公司、原journal及gl_sync_error，修正映射并重新财务确认后用期末页面补齐；禁止直接改journal或已记账凭证。关账会拦截未生成、未记账及对账差异，不能通过旧期间入口绕过。

ar.collection_remind是统一任务管理中的固定任务，按业务日期和提醒键幂等投递站内信；暂停任务会延后提醒，不修改原计划。信用快照池最多2连接，读取主库已提交事实，不使用延迟备库。观察主库连接总数时应计入API原池、Worker原池及此独立池。

定期检查财务角色的完整仓库/部门范围、cost:view、导出对象过期、失败事件与结账快照。恢复数据库必须包含运营事实、GL事实、权限、Outbox/Inbox和文件任务；不能只恢复gl_balance缓存。运行授权生成脚本把gl_standard_preset列为只读，旧迁移禁止修写。

### 审计封存检查

Worker 的 `audit.seal` 默认每五分钟逐租户封存已提交记录。运行账号对审计日志、批次和成员表使用查询与追加授权，摘要视图使用查询授权。迁移 V103 后、启动 Worker 前重新生成并应用最小权限脚本。

从部署包根目录使用 Python 3.11+、MySQL 客户端与私有只读配置核对。核验账号只需查询 `audit_log`、`audit_seal_source`、`audit_seal` 和 `audit_seal_member`。首次以现有链核验，得到非空批次后将输出保存至有独立访问控制的外部存储。后续每日将外部保存的上次检查点传给核验命令，成功时追加保存新检查点。租户编号使用需要巡检的实际编号。

```powershell
python -B scripts/upgrade-2.0/audit_seal.py --settings /private/audit-reader.env --tenant 123 --anchor /private/audit-anchor.json
```

加入外部检查点后，缺少该批次、删除链尾或修改已封存记录会令核验失败。核验失败时保留报告、数据库与独立检查点，检查受影响租户和批次。检查任务失败与未封存积压后才能确认留存有效。180 天是默认轮转周期，容量上限会提前清理本地文件。生产按每类日志实际增长率配置容量和独立归档，定期检查最早可读取日期。
