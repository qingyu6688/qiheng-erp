# 本地部署与使用

## 2.0.0 升级候选

已运行的 1.x 数据库通过停写工具升级到当前候选构建要求的版本。生产启动需要已核验的目标库。先在同版本 MySQL 上还原一份最终停写备份，审阅权限范围报告，再切换 API、Worker、Web 及对象仓。新安装按本文件的生产初始化流程建立独立账号。 [升级与回退操作](1.x升级到2.0指南.md)

从源码生成 2.0 候选包时，先确认源码提交、通过回归并完成生产构建，再在源码根目录用 PowerShell 7 执行。候选编号按发布计划递增。以下示例包含 AI 服务 JAR 和移动端 H5，按部署范围选择相应开关。

```powershell
pwsh -NoProfile -File scripts/package-release.ps1 -Version 2.0.0 -Candidate rc.2 -IncludeAi -IncludeMobile
```

部署包附有 SHA-256 文件和包内 `manifest.json`。切换前核对源码提交 `sourceCommit` 和逐文件摘要。包内 `LICENSE` 是该版本的项目许可证，对应源码可按清单中的提交号从项目仓库取得。

## 分阶段资源预算与上线前检查

下表用于准备验收机器，内存按 GiB 计算。实际最低配置须由同一目标环境、真实单量和历史数据规模下的容量复测确认。工作流与总账运行在 ERP JVM 和 MySQL 中，向量、重排和生成模型按所选模型的实际配置单独核算。

| 版本与模块 | 部署组合 | 起始 CPU / 内存预算 | 上线时核对 |
|---|---|---|---|
| 1.0 核心销售、采购、库存和资金 | 单个 ERP 进程同时承载 API 与 Worker，本机 MySQL、Redis；AI 服务独立选配 | 主机 2 核 / 4 GiB；ERP 进程上限 2 GiB、堆 1280 MiB；MySQL 约 512 MiB、Redis 约 256 MiB，其余留给系统、代理和连接峰值 | 原有服务占用后仍有足够可用内存，单据写入、查询和导出容量达标 |
| 1.2—1.9 组织权限、工作流、总账与供应链 | API、Worker 各一进程，MySQL 和 Redis；AI、检索及模型使用独立节点 | 主机 4 核 / 8 GiB；API 与 Worker 各 2 GiB、MySQL 约 1.5 GiB、Redis 约 512 MiB | 各启用模块的 P95、Outbox 积压、数据库连接和锁等待 |
| 2.0 高可用核心业务 | 至少两台应用节点，每台 API 与 Worker 各一实例；MySQL 主备独立节点；Redis Sentinel | 每台应用节点 4 核 / 8 GiB，API 与 Worker 各 2 GiB；每台数据库节点 4 核 / 8 GiB 起，数据库进程预算 6 GiB；Redis 节点按会话及队列规模单列 | API、Worker、主库与 Redis 故障切换及恢复时间；负载均衡后的真实入口容量 |
| 启用 AI 网关 | `erp-ai` 独立节点，连接独立检索与模型服务 | 2 核 / 4 GiB 起，`erp-ai` 进程预算 2 GiB | 真实模型限流、超时、知识入库和查询并发 |
| 启用本机 OpenSearch | 独立检索节点 | 4 核 / 16 GiB 起，进程与文件缓存预算 12 GiB；示例 JVM 堆 4 GiB | 数据量、索引大小、检索并发、磁盘延迟和快照恢复 |

对应机器档位保存在 `deploy/resource-profiles.json`。`compact-core`、`modular`、`ha-app`、`ha-db`、`ai-gateway`、`ai-search` 分别检查上述节点的 CPU 分配、总内存和启动前可用内存。预算已包含该档位的新进程，采样应在准备启动 ERP 时进行。已有 ERP 正在运行时，先按实际进程峰值重算新增内存需求。

单机核心业务可使用 `deploy/erp-combined.service`，启动参数中的 `erp.worker.enabled=true` 让同一进程处理后台任务。从 `production.env.example` 准备私有 `/etc/erp/combined.env`，将工作角色设为 `combined`、后台任务设为开启，并填写当前环境的数据库、Redis、对象仓和日志参数，节点编号仍在部署内唯一。单机使用主库查询报表，保留模板中三项报表备库参数为空。运维安装时选用合并服务，在移除原实例后启动；原 `erp-api.service` / `erp-worker.service` 用于分离方案。生产数据库最小权限、TLS、备份和私有对象仓继续按本文件设置。AI 功能使用独立服务后再在管理端按企业授权启用。

MySQL 小规模试运行在原 `deploy/mysql-primary.cnf` 的基础上加载 `deploy/mysql-compact.cnf`。该文件将 buffer pool 设为 256 MiB，最大连接数 50，并保留原刷盘与 binlog 设置。应用连接池、管理连接与备份连接合计须在连接预算内。它是起始样例，每次调整都应复测回归和容量。

在项目或部署包根目录执行以下命令。预检仅读取当前主机的资源数据，`--data-path` 选取承载数据库和升级工作目录的分区。空间预算由真实备份、目标库、对象副本及保留策略的演练峰值确定，多分区部署分别检查。

```powershell
python scripts/check_deployment_resources.py --profile compact-core --data-path . --output .local/deployment-resources.json
```

在目标 Linux 节点同样运行 Python 3。也可将只含容量值的采样 JSON 存在私有目录，再在本机检查。以下为合成示例，单位均为 MiB。

```json
{
  "cpuCores": 4,
  "totalMemoryMiB": 8192,
  "availableMemoryMiB": 7000,
  "freeDiskMiB": 100000
}
```

```powershell
python scripts/check_deployment_resources.py --profile modular --inventory .local/target-resources.json --required-free-disk-mib 80000 --output .local/target-resource-check.json
```

退出码 0 表示提供的容量值满足起始预算，1 表示预算不足，2 表示输入或采样失败。报告另列容量复测、CPU 持续使用率、故障演练和未提供的空间预算。目标主机的 IP、凭据、绝对目录及已有服务清单由私有运维记录保存。正式验收还需收集真实业务数据规模、CPU 峰值与内存峰值、数据库和对象空间增长、磁盘吞吐、备库延迟和可批准的停写窗口。

## 可选报表备库

启用报表备库时，在 API 与 Worker 的私有环境文件填写同一组 `ERP_REPORT_JDBC_URL`、`ERP_REPORT_DB_USER`、`ERP_REPORT_DB_PASSWORD`。连接串使用 TLS 证书校验及 UTC 会话，可按下面的地址格式填写，再通过私有配置注入实际的报表账号和密码。报表账号只授予 `scripts/database-grants.ps1` 生成的报表表 SELECT 权限；运行账号需更新水位表。账号授权由管理员在受控维护窗口完成，备库恢复 `read_only`、`super_read_only` 后再启用报表读取。

```dotenv
ERP_REPORT_JDBC_URL=jdbc:mysql://mysql-replica.internal:3306/erp?sslMode=VERIFY_IDENTITY&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true&characterEncoding=UTF-8
```

启用 Worker 的实例每五秒在主库更新水位。核对复制线程和延迟，确认报表、导出的截止时间在暂停复制时停止、恢复追平后前进。配置了备库的部署在备库不可用时应恢复备库后重试报表。

## M19 经营驾驶舱、打印与预警

升级后按当前数据库表重新生成运行与备库最小权限。报表账户只需要授权查询，用户表仍只开放编号、企业编号和显示名。分离运行与迁移角色时，迁移角色负责创建视图，运行角色只能读取生产成本视图。驾驶舱沿用 `ERP_REPORT_*` 备库配置，业务预警扫描及后台打印沿用 Worker、Redis 与文件对象存储配置。

启用 Redis ACL 时，允许 API 在现有会话命名空间的 `:dashboard:v1:*` 子键执行 `GET`、`SET`、`INCR`、`EXPIRE` 以及限流脚本的 `EVAL`、`EVALSHA`。同一部署的 API 实例共享命名空间和刷新配额。

批量打印 PDF 在生成文件的 Worker 上读取 `ERP_PRINT_PDF_FONT` 指定的中文 TrueType 字体。部署可复用原中文 PDF 字体 `ERP_PORTAL_PDF_FONT`。在 Linux 或容器中通过只读挂载提供经授权的字体，并让 API 与 Worker 指向同一字体文件。

## M18 生产一期

升级前备份 ERP 数据库，按项目原流程依次执行 V92 至 V94。为生产角色分配 BOM、工单、领退料、完工或报表权限，并核对公司、仓库和部门授权。成本归集和过账还需要金额权限及整家公司范围。

启用总账的公司应复核 `WIP`、`PRODUCTION_VARIANCE`、`PRODUCTION_LABOR`、`PRODUCTION_OVERHEAD` 的映射。企业样例默认映射到 5001、6401、5102、5101，小企业样例为 4001、5401、4102、4101。自定义账套使用现有映射管理。首次使用生产前，在副本完成两层 BOM、领退料、完工、成本过账和关账试跑。 [生产操作手册](../产品/用户使用手册.md#m18-生产一期本机候选)

## M17 仓储作业与移动端

备份后由迁移账号执行 V88 至 V91，已有仓库保持原作业模式。重新生成运行角色表级授权，其中 `wms_task_confirmation` 只授予查询与新增。按职责配置上架、拣货、波次、复核、移库、盘点、标签和设备配对权限，并明确作业员的公司、仓库和来源部门。启用作业模式需同时有 `wms_task:configure`、`warehouse:update` 和当前公司全部部门范围。

在「库区库位」维护收货区、发货区和存储区。先在样例仓配置收货位及发货位，再从「库存 → 上架任务」开启需要的模式。强制模式要求复核后过账，改仓库作业模式只影响新发起的发货作业。Worker 的 `wms.replenishment` 定时任务检查启用仓库的补货规则，也可在管理端手动生成补货单。

在 `erp-mobile` 运行 `npm ci`、`npm run build:h5` 和 `npm run build:app`。H5 放在 ERP HTTPS 同源的 `/mobile/`，使用现有 `/api/` 代理。使用候选包脚本时添加 `-IncludeMobile`。Android 构建资源位于 `erp-mobile/dist/build/app`，由 HBuilderX 使用现场 AppID 和 Android 签名打包。在实际机型验收相机、外置扫码枪、震动、音效和标签打印。 [移动端使用说明](../../erp-mobile/移动端使用说明.md)

设备配对要求 `device:pair`。同一部署实例共用已有 `spring.session.redis.namespace`，使用其 `:device:*` 子键，Redis ACL 需允许 `GETDEL`、`GET`、`SET` 和 `DEL`。通过 HTTPS 生成、兑换和使用设备凭据。标签 PDF 可复用 `ERP_PORTAL_PDF_FONT` 的中文字体配置。

## M16 客户门户与 AI

门户静态入口为 `/portal.html`，业务接口通过 `/api/v1/portal/` 转发到 ERP。启用门户在线客服时，在 ERP API 的私有配置设置 `ERP_PORTAL_ASSISTANT_ENABLED=true`，并在 AI 管理配置 `customer_service` 场景。Compose 的 AI 组合已将 `ERP_PORTAL_AI_ORIGIN` 指向 `http://erp-ai:18081`，独立部署时按 AI 服务实际地址设置。ERP 与 AI 使用同一份私有 `ERP_AI_SIGNING_KEY`。内部分类入口由 ERP 发起签名请求，Nginx 只代理公开的 `/ai/v1/`。

同一部署的 ERP 实例统一使用 `APP_ENV`。共享 Redis 时按环境授权门户会话键 `erp:portal-session:<环境>:*` 和客服状态键 `erp:portal-assistant:<环境>:*`。会话和短信需要 `GET`、`SET`、`DEL`、`INCR`、`EXPIRE`、`EVAL`、`EVALSHA`。客服状态另需 `EXISTS`、`HGET`、`HSET`、`HINCRBY`、`PEXPIRE`。调整 ACL 后在目标环境验证门户登录、会话失效和客服反馈。

需要中文对账 PDF 时，将允许在部署环境使用的中文 TrueType 字体以只读方式挂载到 ERP API，再在 API 私有环境设置 `ERP_PORTAL_PDF_FONT` 为进程可读的字体文件绝对路径。未设置时使用内置西文字体、英文表头及公司和客户编号。启用后用实际客户名称和单据号下载一份 PDF，检查字体、分页和金额列。

要启用门户短信登录，在 ERP API 私有环境设置 `ERP_PORTAL_SMS_ENABLED=true` 和现有的 `ERP_LOGIN_SETTINGS_KEY`，并在该企业后台配置已启用的短信验证码渠道。为门户账号绑定有手机号的联系人，分别验证发送、验证码登录和旧码失效。

现有库从 ERP V78 升至 V87，启用 AI 时同时将 AI 库从 V4 升至 V5。停写并完成备份后由迁移账号执行。先更新运行账号和报表账号的表级权限，等待只读库追平，再用业务副本核对旧单据、客户画像和门户账单。为内部用户按职责配置新增 CRM、门户账号及客服权限。对外启用前按开发计划验收渠道、正式模型和内容安全。 [迁移与回归记录](../测试/测试报告.md#m16-客户与-crm-本机回归2026-11-17)

## M11 组织消息与运维待发布升级

升级追加V38—V43，沿用JDK21和MySQL8.0.46。先停写、排空API和Worker、最终一致备份，再迁移并校验；备库追平后再开放请求。新权限按职责授予，自定义角色不自动提权。当前软件仍为1.0.0候选构建，不据此发布1.2.0正式版。

所有API及Worker共享ERP_LOGIN_SETTINGS_KEY和Redis会话命名空间，ERP_NODE_ID各不相同。新增可选ERP_WEBSOCKET_ALLOWED_ORIGINS，默认只允许同源，禁止通配符；部署模板增加/ws/的Upgrade、100秒超时和关闭缓冲。Redis ACL增加本环境在线有序集合、发布订阅命令及events频道访问；API和Worker必须使用同一环境隔离配置。站内消息持久化在MySQL，Redis广播短时不可用时重连后恢复。

完整升级、渠道配置、调度和恢复步骤见[M11使用说明](../使用说明/M11组织消息与运维使用说明.md)。大表回填及新增索引需在生产副本测量，真实渠道及生产网络仍按原上线门槛验收。

## M11 Y-02 待发布升级

本轮为目标1.2.0的部门数据范围增量，当前候选软件版本保持1.0.0。沿用JDK21、MySQL8.0.46和Redis，无新增环境变量及外部服务。

升级先停写、排空API和Worker，再做最终一致备份并保存恢复点。API使用迁移账号执行V37，Worker以同一代码版本启动并校验；有报表备库时等待V37结构与回填追平后再开放流量。迁移对17张业务头增加两列及索引并回填，需在正式数据副本测量耗时；DDL不能作为普通事务回滚。回退应恢复与停写恢复点一致的数据库和旧应用。

未配置部门范围的角色仍为全部，新迁移不自动限制现有账号。管理员先核对各公司用户主部门和历史单据回填结果，再逐角色保存范围，至少保留一位全范围角色管理员。无部门的历史保持0，受限角色不可见。抽查详情、分页计数、打印附件、报表及旧导出下载的收窄行为，重点区分共享库存快照和部门事实口径。

开发与本机测试命令见下文，验收证据及限制见[M11部门数据范围本机验收报告](../测试/验收记录/M11部门数据范围本机验收报告.md)。正式部署不执行测试夹具，不将私有.env或测试日志放入交付包。文档维护：maorongkang@gmail.com。

## M11 Y-01 待发布升级

本轮为后续1.2.0的部门岗位功能，仍沿用当前1.0.0候选构建版本，不创建正式发行标签。部署前先停写并排空请求、任务，再做最终备份并记录恢复点，随后由 API 执行新增 V36；Worker 启动校验迁移。沿用 JDK21、MySQL8.0.46 和既有 Redis，不需要新的外部依赖或环境变量。

V36 新建五张组织表、六项权限。迁移只给具备既有用户/授权管理能力的系统管理员及演示企业仓管角色补充组织权限，自定义角色需明确授予。部门及用户任职按公司隔离，岗位定义在企业内共享。

升级后核对可访问公司中的部门树、岗位、用户配置及审计；尝试跨公司引用应返回404，缺操作权限403。回退必须与备份恢复点一致，不手工删除迁移历史。仅安装V36时保持原公司仓库规则，V37和对应应用启用前述Y-02规则。本机通过仅代表本机验证，正式目标环境发布门槛仍按《开发计划》执行。

## M10 待发布升级

## 0.8.1 运行与压测配置

数据库仍为 V31，没有新增或改写迁移。升级只替换经过测试的 JAR 和完整前端构建，先备份业务库与私有对象。JDBC 启用 `rewriteBatchedStatements=true`，库存、凭证和核销的批量写入仍在原业务事务中提交；不能通过降低刷盘级别或拆成逐行提交来替代该配置。

HTTP 常驻线程与上限分别由 `SERVER_TOMCAT_THREADS_MIN_SPARE`、`SERVER_TOMCAT_THREADS_MAX` 配置，本机验收均为 200，接入队列 2000、最大连接 8192、Hikari 最大连接 30。改变线程上限时必须同时检查常驻下限，预留线程栈与连接内存；这些值是本机单 API 的验收组合，目标服务器仍须复测。

容量发生器和 API、MySQL 同机运行时，`run-capacity.ps1` 默认通过 `GOMAXPROCS=2` 限制 k6 的 Go 调度并行度，结束后恢复原环境值。冷连接仍使用 1000 VU，强制禁止连接复用，不添加请求延时或网络重试。查询按 500ms 延迟预算预分配客户端，1000 RPS 时预分配 500 VU，目标请求率与零调度丢弃要求均保留。不同压测机可显式传 `-LoadGeneratorCpus` 并记录结果，不能把同机参数直接当作外部客户接入容量。启动容量 API 使用 `spring-boot.test-run.optimizedLaunch=false`，避免 Maven 的开发启动参数关闭 C2；也可在完成构建后使用 `server -JarFile erp-server/target/erp-server-0.8.1.jar`，以已验证生产 JAR 加独立测试夹具启动。容量复跑在源码目录完成。正式部署使用 `java -jar`，预热结果与正式测量分开保存。

生产环境在服务器环境变量或私有配置中完整提供下列项目；不要提交实际地址凭据或把凭据写入文档。

| 配置 | 用途 |
|---|---|
| `STORAGE_ENDPOINT` | S3 兼容对象仓的 HTTP/HTTPS 地址 |
| `STORAGE_BUCKET` | 私有存储桶 |
| `STORAGE_ACCESS_KEY`、`STORAGE_SECRET_KEY` | 最小读写权限凭据，两项均需配置 |
| `erp.storage.region` | S3 区域，默认 `us-east-1`；可通过 Spring 配置覆盖 |
| `erp.storage.local-root` | 仅开发、测试的本机私有对象目录 |
| `ERP_WORKER_ENABLED` | 是否执行 Outbox、导入、导出与文件清理任务；单独 API 实例可设为 `false`，至少保留一个同库、同对象仓的 Worker 实例为 `true` |

对象仓使用路径风格 S3 接口。所有 API/Worker 实例需指向同一个桶；密钥、存储键和原始导入文件不返回页面。入口与应用均允许 20MB 单文件及 multipart 封装开销，应用请求上限至少 21MB；反向代理还需为上传和大报表下载预留超时。批量导入只接收 CSV，不把附件 XLSX 当作导入格式。

后台导出每个任务最多 50000 行，每人同时 3 个，生成成功后 24 小时过期；未完成任务从创建起有 24 小时排队期限。清理任务每分钟检查到期对象。未关联对象先登记补偿候选，一小时后重试清理，引用中的有效附件不会被当作孤儿删除。五分钟文件票据存数据库摘要并定期清理；恢复数据库备份时应一起恢复同一时间点的私有对象仓。

删除附件会在逻辑删除事务内登记回收候选，立即拒绝下载，一小时后检查有效引用并物理清理；失败候选继续保留重试。导出内容由 Worker 按中文业务列白名单生成，不包含内部 ID 或 URL，没有成本权限时不生成成本表头；下载入口必须携带五分钟有效票据。

本机 M5 升级前开发库备份位于未提交的 `.local/erp_dev-before-m5-*.sql`。0.5.0 启动追加 V20—V23：采购与请购退役标记、采购审批容差快照、收货成本税身份快照、付款关联采购订单外键及索引，以及采购、收货退货、付款转账和期初操作权限。升级前备份开发数据库，启动后检查 Flyway 校验与迁移日志；已应用迁移不得编辑。升级继续使用现有 JDK 21、MySQL 8.0.46 和 Redis，不增加外部服务或银行配置。

管理员按职责授予 `purchase_requisition:*`、`purchase_order:*`、`goods_receipt:*`、`purchase_return:*`、`payment:*`、`account_transfer:*`、`stock_adjustment:*`、`opening_entry:*` 的具体动作。应付核销沿用 `settlement:view/allocate/revoke`，供应商退款沿用 `receipt:*`；查看成本另需 `cost:view`，改税率另需 `document:change_tax_rate`。正式环境显式授权，不能依赖演示账号的开发初始化授权。

采购前准备供应商角色、SKU、单位换算、有效公司仓库和开放期间。付款与转账需要有效结算账户和足够余额，其他支出还需有效支出项目。库存期初在“库存期初”页面创建，写入 `stock_adjustment` 的 `opening` 类型，数量按所选单位输入，总成本按整行填写；换算不允许静默损失精度。往来及资金期初从“往来与资金期初”录入，由另一名人员审核后过账。客户与供应商往来可录欠款或预收预付，资金期初只录借方余额，具体方向见《用户使用手册》。

单据过账使用业务日期对应开放期间；历史日期补录仍按实际过账顺序维护移动加权成本，不重算已出库历史成本。收货成本税身份在过账时冻结，后改公司纳税人参数不回写原入库或退货。采购容差在订单审批时冻结，后改参数不扩大旧订单上限。

验证命令继续使用前文的 `verify`、前端 lint/测试/构建和 `e2e`。M5 浏览器流程复用随机测试企业与隔离测试库，覆盖期初、请购、采购、收货、付款、应付核销、退货和供应商退款。最终后端 241 项、前端 48 项、浏览器 4 项全部通过，采购、期初与资金样例八类对账零差异，详见《测试报告》。确认付款、供应商退款和账户转账只登记财务已经执行的操作，不向银行发送指令。

## M6 升级与库存作业、关账

本机 M6 升级前开发库备份已保存到未提交的 `.local/erp_dev-before-m6-20261115-133330.sql`。0.6.0 启动追加 V24—V27：关闭和重开期间权限、调拨权限与分批事件事实表、盘点权限与首次盘盈录入单价、冲销权限及应收应付来源唯一索引。索引保留履约来源头，支持冲销后的新履约重新确认费用。升级前先备份开发数据库到未提交的 `.local` 目录，启动后核查 Flyway 校验和迁移；已经应用的迁移不得改写。继续使用本机 JDK 21、MySQL 8.0.46 和 Redis，不增加外部服务。

按职责配置 `stock_transfer:*`、`stock_count:*`、`reversal:*`、`period:close/reopen`；库存调整沿用 `stock_adjustment:*`，成本详情另需 `cost:view`。调拨操作人须同时有两仓范围；冲销还需相应原单查看权限；关闭及重开必须有整家公司范围。正式角色由管理员明确授权，不能依赖开发演示角色的首次升级初始化。

原“库存期初”页面已整合为“库存调整”，支持 opening、gain、loss、block、unblock、scrap 六种类型，原库存期初记录继续可查。盘点首期采用 watermark，实盘按开始盘点快照时点录入，过账只处理差额。调拨在途和分批、退回、损失事实保存在 MySQL，重启后从原单继续处理。

M6 将相关提交和审核加入原期间共享锁屏障。关闭前用独立短事务补齐待投影凭证，沿用 Inbox 去重；持期间排他锁后复核最新五项及待投影事件，不持有该锁等待投影。后台 Worker 应继续运行，关闭或重开都保留审计；只有最近一个已关闭期间可重开。已关闭期间的原单更正记在开放期间，不能回写旧账。

验收命令与前文一致，浏览器夹具继续仅在测试 classpath、随机测试企业和隔离测试库运行，不能进入常规开发或生产 Jar。M6 累计后端 302 项、前端 70 项、浏览器 5 项通过，lint、类型检查与构建成功，样例八类对账零差异，详见《测试报告》。本机升级仍须在版本提交后核查迁移、健康状态及实际登录；验收记录不代替启动检查。M5 的 241/48/4 为历史记录。

### 前端构建目录保护

在 `erp-web` 执行 `npm run build`，`prebuild` 先校验当前包名、固定的项目根及 `dist` 真实路径，再清理该构建目录。脚本不接收清理路径参数，遇到符号链接或 Windows 目录联接时拒绝执行，避免删除外部目录；Vite 仍启用 `emptyOutDir`。四项回归和连续两次真实构建已确认旧标记、旧入口哈希均被移除。部署只复制本次完整 `dist`，不要把新旧资源目录叠加。

## M11 工作流待发布升级
