# 无源销售退货设计

- 对应《业务完整性评估与改进方案》B-05，按B-02销售侧之后的顺序实施。
- 状态：V110及独立旧库升级、成本计算基础和原单兼容回归通过；无源业务命令与页面接入中，本文件不表示功能已经交付。

## 1. 现有入口和范围

继续使用销售退货单及其右侧详情，不新造另一套库存、往来或凭证。`SalesReturnService`当前强制每行引用发货行，提交占用原行可退数量，提交后可直接过账；无源模式须绕开原行占用，同时增加不可省略的另一人审批。已有原单退货保持原计价、数量限制和单据流转。

`RefundApplicationService`和`accounting/RefundService`都要求有效原收款，并占用其可退金额。老系统的无源退货可能没有本系统收款，因此只增加客户信用额仍不能完成现金退款。本项同步扩展既有退款申请的“无源退货信用额”方式，不伪造原收款。

## 2. 默认业务规则

| 项目 | 规则 |
|---|---|
| 模式 | 单据分为原单退货、无原单退货；一张单据不能混用，建单后不切模式 |
| 授权 | 原退货动作权限之外，无源新建、修改、提交及过账增加 `sales_return:sourceless`；审批增加独立 `sales_return:approve`，经办人不得审批自己的单据 |
| 明细 | 选择启用客户、授权退回仓、商品及单位，数量大于零；手填含税退货单价和税率，冻结单位换算与价格，金额、税额按R3累计舍入规则计算 |
| 历史依据 | 填退货原因，可记录历史单号、票号或凭证说明；这些说明不创建伪造发货、收款或实际发票，也不能当作已完成红字 |
| 数量 | 无源不占用或增加任意发货行、订单行的已退数量；原单模式仍严格按原来源数量限制 |
| 期间 | 保存不产生事实；提交、批准、过账检查开放期间，业务日期不能在未来 |
| 质检 | 复用合格、待检、不合格及冻结处理；库位、批次、序列号和上架按现有入库路径校验，不能因无原单跳过追溯要求 |
| 往来 | 过账生成客户贷方应收未清项，不自动核销或退款；无原应收到期日可继承，本项新增信用额不凭空计算销售账期 |

## 3. 成本选择与复核

按公司、退回仓、SKU取当前成本，不读其他仓库、不采用手填售价作为成本。取价顺序固定：

1. 当前库存成本数量大于零：按当前总成本除以基本数量计算。
2. 当前数量为零：使用 `inventory_cost.last_in_unit_cost`。
3. 最近入库单价为空：由有成本权限的人员填写基本单位成本，必须说明依据，并展示给复核人。

零成本与没有成本是两个状态；已有的零单价合法，不能把零误判为缺失。自动取价存在时，客户端手填成本不能覆盖它。金额按总成本和基本数量计算后舍入到分，单位成本保留现有八位精度，不先截断单价再计算总额。

提交时冻结每行的来源方式、库存成本版本、基本数量、单位成本及预计入库总成本。审批人必须有成本查看权限，看到全部成本依据后批准。无成本权限人员可以建立商品及售价草稿；需要补填成本时由有权人员接手，不能通过接口或旧响应获得隐藏成本。

过账按仓库、SKU排序持有库存和成本锁，重新取当前成本。自动取价的来源或金额与审批快照变化时拒绝过账，返回明确的成本变化原因，重新提交审批；不能悄悄采用未经复核的新成本。手填成本仅在当前仍无可用自动来源时生效。同SKU多行使用本次入库前的同一成本基准，避免前一行无源退货改变后一行取价。

同仓同SKU先按总退回基本数量计算一次本组成本，再按各行数量使用R3最大余数法分摊到分，余数相同时优先行号小的行。不能把已舍入的行成本简单累加后当作本组金额，也不能把负尾差一次扣在一行造成负成本。例如当前3件总成本0.01元，本次分三行各退1件，本组仍为0.01元，不能因逐行舍入变成0.00元。人工取价时，同组输入的基本单位成本必须一致；不同成本依据需要拆单，不能在一次入库中混用未经统一复核的基准。

质检待检或不合格的退回数量使用原销售拒收冻结原因。序列号管理还须冻结具体序列号，复用现有质检冻结状态，不能仅减少仓库可用总量。正常发货和自动选择均排除这些序列号；普通解冻或报废继续走原调整审批，但按实际所选序列号消费对应来源的冻结，记录释放或报废轨迹。部分释放后再次退回的同一序列号不能被旧来源的释放操作误处理，冲销仍还原原状态和原冻结来源。

## 4. 单据与工作流

无源状态采用 `draft → pending → approved → posted`，驳回回到可更正状态；未过账可按状态作废。提交、批准、驳回和过账使用独立动作、版本及幂等键，审批不会自动过账。

将 `sales_return`登记到现有工作流适配器和默认审批模板，只让无源模式走这一新增审批分支；原单模式继续原流程。有企业自定义流程时使用现有任务、自选复核人和当前权限校验；未配置时由系统默认流程分配另一名有权人员。流程终止或驳回不产生库存、应收或总账。

每次更正、提交、审批、终止及过账在现有审计记录中保存前后快照，包含模式、历史依据、行成本来源和分摊金额。重新提交后仍能查到前一轮冻结成本及审批事实，不覆盖历史。审计查询继续按公司完整范围开放，并按当前`cost:view`权限递归移除成本字段及整个`costBasis`；普通经办人不能通过审计取得隐藏成本。待审批、已批准未过账和原单已提交均拦截期间关闭，检查结果返回对应单据供右侧穿透。

直接调用审批接口不能绕过正在运行的任务；任务同样不能越过公司、仓库、部门及成本权限。审批快照按当前身份投影，旧幂等响应和命令结果查询继续复核当前授权。切公司、撤权、网络结果未知和离开保护沿用已验证模式。

## 5. 数据与迁移

本项使用V110，已在专用旧库完成升级验收并冻结；后续结构调整另加迁移，V110及更早脚本不改。冻结摘要见[数据库设计](数据库设计.md)。

- `sales_return`增加 `return_mode`（默认原单）、历史依据、审批状态与经办复核字段；原单号长度与既有长公司编码约束一致。
- `sales_return_line.shipment_line_id`允许为空，增加模式、手填价格与税率、成本选择及审批快照。以头行同模式外键和行CHECK保证：原单模式必须引用发货行，无源模式不能引用；不能只靠前端判断。
- 原单数据迁移为原单模式，金额、税额、成本、原来源、状态、版本、时间及历史关系保持；已过账旧退货不补做审批。
- 增加独立权限；只按既有系统管理员授权管理条件迁移，普通角色不自动提权。
- 保留库存来源 `sales_return_line`和退货凭证来源 `sales_return`，增加明确的无源标识和成本依据，便于报表及审计识别，不另记重复库存或凭证。

### 5.1 字段及约束口径

| 表 | 新增或调整 | 约束及兼容要求 |
|---|---|---|
| `sales_return` | `return_mode`默认`original`，另允许`sourceless`；历史依据、提交人与批准人/时间、工作流实例 | 原单保留`draft/submitted/posted/reversed/voided`；无源允许`draft/pending/approved/rejected/posted/reversed/voided`，不能进入`submitted`绕过审批 |
| `sales_return` | 模式与编号的组合唯一键 | 供行表外键同时引用当前头和模式，不以客户端模式替代头表事实 |
| `sales_return_line` | `shipment_line_id`可空，`return_mode`默认`original` | `original`必须有原发货行；`sourceless`必须没有。头行模式须相同，原发货外键保留 |
| `sales_return_line` | 无源`unit_price/tax_rate`，人工基本单位成本及依据，`cost_basis`快照 | 原单不使用手填售价或人工成本；无源价格非负，税率0—1。人工成本允许零，填写时须有非空依据；预览或快照不能覆盖已过账金额 |
| `refund_request` | `refund_mode`默认`receipt`，另允许`sourceless_credit`；`original_receipt_id`可空 | 收款模式仍必须引用原收款；信用额模式必须为空且显式选择非空贷方项数组，贷方来源再由持锁业务校验 |

批准人与批准时间同时为空或同时存在；无源进入已批准、已过账或已冲销状态时必须有批准事实，并且批准人与制单人不同。已过账及已冲销仍沿用原期间和过账时间的双向CHECK。无源的新增数据必须记录制单人，原单历史空制单人不做伪造回填。

模式在建单后固定，后端更正和旧幂等结果都读取当前头表模式。迁移不更新旧表的业务时间、版本及金额；升级演练按变更前字段逐列比较，新增默认字段另外断言。

## 6. 接口和页面

原 `POST/PUT /sales-returns`请求不带模式时视为原单，旧Java构造签名和既有调用兼容。无源请求显式携带 `returnMode=sourceless`，明细选择 `skuId/unitId/qty/unitPrice/taxRate/qualityResult/stockSelection`，没有 `shipmentLineId`。

成本预览由统一API层读取，只向有权用户返回成本金额；显示“当前平均成本 / 最近入库成本 / 人工填写”及依据。提交和审批保存快照，预览不能代替过账重验。新增批准、驳回动作及所需权限，返回 `allowedActions`与工作流进度；不把后台锁或表名展示给访客。

退货列表明确模式，信用金额与质检状态突出显示。详情、审批成本依据及报表穿透均在右侧抽屉，不离开当前列表，关闭保留筛选和页码。只读演示没有创建、审批、过账或退款操作。

## 7. 信用额、退款及账务

无源退货过账使用同一笔业务事实生成：借记销售收入及销项税、贷记应收；借记库存、贷记销售成本。收入、税、库存成本与客户信用额使用相同冻结金额，不改写任何历史发货或开票。真实发票事项仍按实际凭证另行处理，无源退货不会替用户声称完成红字。

扩展原退款申请的模式，不改变原收款退款规则：

- 原收款模式继续要求有效原收款，同时限制原收款可退余额和客户贷方额度。
- 无源退货信用额模式不要求原收款，但必须显式选择本客户、当前范围内、已过账且未冲销的无源退货信用额；不能混入任意收款、补价、其他客户或仅草稿退货。
- 提交时沿现有未清项和核销锁预占额度，由另一人审批，再登记实际退款；超额、并发争用、重复确认、驳回与撤回释放继续复用资金、核销和幂等机制。
- 不伪造收款，也不跳过真实账户、开放期间和已退款限制。退款成功追加原有资金及总账事实，无须也不得更新不存在的原收款累计字段。

退款模式在建单后固定。信用额模式在草稿保存、提交、审核、释放和付款时逐次验证所选来源；持锁动作先按退货单编号锁定原退货，再锁未清项，避免冲销与预占交叉穿透。客户、当前部门及实际退货仓库范围均须满足。列表、工作流待办、独立命令结果及详情沿用同一来源可见性，不能通过历史响应或另一入口读取范围外信用额。取消后的历史可在有来源权限时查看，但不能再次占用已冲销退货。

## 8. 冲销与报表

无源退货仍走既有冲销申请及另一人复核，先处理有效核销、退款预占或已确认退款、后续库存使用等依赖。冲销按原冻结入库成本反向，不能用当前售价或当前成本重算历史；不恢复或减少任意发货、订单的已退数量。

现有 `ReversalProgress`通过原发货连接读取退货行，须增加无源分支；不能因关联为空而漏掉库存或资金依赖。销售、毛利、客户对账、账龄、总账映射、门户及AI来源摘要应保留单据，显示“无原单退货”。库存成本对账及审计记录带模式与成本来源，可定位抽查，八类业务对账及两类总账对账仍要求零差异。

库存流转与销售事实行、批次及序列号追溯已接入模式标记；冲销仍指向原冲销单，并由原库存流水还原退货成本依据。资料查询分批且只读取当前结果涉及的行，成本来源在无权限时不查询、不返回。逐单CSV按权限输出中文模式及成本来源，不包含内部快照。库存成本对账增加入库、冲销逐行比较，差异键保留单号、模式及来源，防止两行错误相抵后漏检。真实总账的退货、冲销、信用额退款及三大报表已通过3项专项；总账来源展示和完整页面验收继续实施，不能将报表标记通过视为本节全部完成。

## 9. 实施和验收顺序

1. 单独迁移演练：有源旧数据保持、无源CHECK、空来源及权限、退款模式约束。
2. 数量换算、含税退价、平均/最近/手填成本及零成本单元测试；真实业务成本取价与并发变化、双人审批、默认/自定义工作流。
3. 无源退货、核销及两种退款、失败回滚、冲销与后续库存依赖、批次/序列号/库位和质检；旧有源流程回归。
4. 真实总账、销售毛利与门户对账，按当前公司、仓库、部门及成本权限检验详情、列表、历史与旧幂等结果；不能以新模式放宽旧权限。
5. 右侧界面、原位置保留、未知结果原键恢复、双账号真实浏览器、390px布局及只读上下文；必要容量样本及生产构建。
6. 完成后才更新Q11、R5-01及业务规则版本、用户说明、接口和知识问答；把本机与真实服务商、目标环境发布边界分开记录。
