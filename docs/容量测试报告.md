## 0.8.0 历史基线

## 环境与验收线

本机为 Windows、Intel Core i5-13400（10 核、16 逻辑处理器）、约 32GB 内存；JDK 21.0.3、独立 13308 端口的 MySQL 8.0.46，Redis 复用本机配置但使用本轮专有会话命名空间。API、数据库与压测发生器同机，所得吞吐不能当作生产集群容量。当前使用一份 API 与 Hikari 最多 30 个连接。

独立实例实际配置：`innodb_buffer_pool_size=1073741824`（1GiB）、`max_connections=150`、TLS `REQUIRED`。1000 个 VU 竞争经连接池排队，不表示建立 1000 个 MySQL 连接。正式测试在恢复演练的大量导入与校验 I/O 完成后开始。

项目及独立 MySQL 数据所在 F 盘实测为 WDC WD20EJRX SATA 机械盘（约 2TB），不是本机另一块 NVMe。没有关闭事务刷盘或降低隔离级别来提高测量结果。

k6 2.4.0 取自 [Grafana 官方 GitHub 发布](https://github.com/grafana/k6/releases/tag/v2.4.0)，下载 ZIP 后同时检查官方资产 SHA-256；安装器只写项目忽略的 `.local/tools/k6`。七场景依据《重构设计方案》11.3，构造数据而非客户真实业务数据。

S09 假设每天销售 1000 单、采购 200 单，最忙小时占 30%，约为每秒 0.1 单、平均每秒 1 条明细。200/500/1000 查询 RPS、20/50/100/200 写操作每秒用于探索性能拐点，不是已经达到的承诺。

本机初始验收线：普通查询 20 RPS，P95 小于 500ms；分散完整销售流程 2 次/秒，1/20/100 行分别运行，其中每次真实 REST 写操作的 P95 小于 1000ms；系统错误比例小于 1%。销售创建、提交、异人审批、发货创建、提交、关联预收创建、提交、异人确认、发货过账共 9 步分别进入 `write_duration`，完整闭环另计 `workflow_duration`，不把总耗时除以步骤数冒充单操作分位数。预收确认后执行自提签收，真实 `auto_order` 核销消费该订单关联额度；另通过正式 GET 核验订单已关闭、履约与结算均为 full 才计完成。业务拒绝单独统计，不把预期库存或额度不足作为系统故障。热点争抢、重复命令及退款额度正确性不放宽。

## 数据隔离

只允许本机 `erp_load_<小写字母数字及分段下划线>` 独立容量库、19080 端口、随机运行编号、临时登录口令和独立请求密钥。运行配置、日志、数据和结果 JSON 均在未提交的 `.local`。不写开发库或普通测试库，不停止既有数据库或修改其全局配置。

`cn.erp.capacity` 夹具、控制器与诊断仅在测试 classpath 且 `dev,load` 启用，出现 `prod/production` 即不注册，生产 Jar 不包含它们。HTTP 仍要求真实会话、CSRF、当前公司权限；销售闭环直接访问产品已有 REST 接口，热点、退款和幂等压力入口调用真实领域服务和数据库事务。

默认数据：2 个独立租户，每租户 2 公司，每公司有分散仓、热点仓、客户、结算账户及当前开放期间。主租户 20000 个 SKU、次租户 100 个 SKU。每公司另有 1000 张单行热点订单；主公司保留 1000 张销售、200 张采购历史头，每张 10 行，日期分布过去 360 日；其他公司保留较小历史集合。历史头为已取消的无履约单据，金额和行结构满足约束。各公司以真实库存期初、账本和已确认收款准备竞争数据。

## 七个场景

| 场景 | 执行及正确性标准 |
|---|---|
| 普通查询 | 销售/采购列表、库存余额、SKU 搜索、新单据浏览的日期状态筛选；记录 P50/P95/P99、错误和实际请求率 |
| 分散写入 | 1/20/100 行实际建销售、提交、异人审批、确认关联预收、自提过账签收及自动核销，GET 检查结算 full；返回时已完成数据库事实，不把 202 当完成 |
| 热点抢库存 | 同 SKU 100 件、1000 个 VU 各预留 1 件、不释放；恰好 100 次成功，其余明确库存不足，库存不可负 |
| 重复命令 | 100 VU 使用相同幂等键调用真实库存与账本入库；所有响应有效，库存来源和凭证副作用均仅一次 |
| 退款争抢 | 原收款 100.00，100 VU 各提交 2.00；50 笔占用成功、50 笔明确拒绝，占用加已退不能超过 100.00 |
| 混合读写 | 60% 查询、20% 预收销售闭环、10% 原子库存入库及账本、5% 实际收款后退款审核登记、5% 库存 CSV 导出；全部实际完成，不遗留失败/积压 |
| 稳态与突发 | 30 秒稳态、15 秒增加至三倍、30 秒回落；检查积压回落、响应和对账 |

每轮收尾先释放本次退款竞争的合法占用，等待 Outbox 与导出完成；对全部 4 公司运行八类 `ReconciliationChecks`，另检超量履约、重复账本来源、热点余额与退款额度。任何差异均判失败。日志记录对账结果，不记录临时密码、CSRF 或 Cookie。

混合入库使用独立 `capacity_mixed_inbound` 来源，`BusinessCommands` 同事务调用真实库存入库与借库存/贷期初权益凭证，不占用重复命令场景的来源。混合退款使用正式 REST 新建独立 1 元收款，提交、异人确认后读取本次贷方额度，再创建退款、提交、异人审批、登记退款；不借用原 100 元争抢额度。入库、已登记退款及导出都必须有实际完成计数，且所有收款的占用加已退不得超过原金额。

准备阶段记录 4 公司的实际头、行、SKU、库存及账本数量，并对销售/采购游标列表、日期状态列表、日期状态计数、SKU 包含搜索、库存 CTE 共 8 条 SQL 执行 `EXPLAIN`。只采集执行计划及少量锁等待/慢查询计数，不自动改索引或 MySQL 参数。是否新增索引以实际访问类型、扫描行数和慢接口结果为依据。

首次突发检查发现压测脚本入库/退款键缺少场景名，复用了前一混合轮次的请求键，正确的幂等重放使 3 次额度查询找不到已完成退款的旧额度。原始 `ssd` 结果保留为脚本失败；修复为运行编号、阶段、场景、迭代共同组成请求键，并使用全新 `ssdrefined` 标签重跑，未删除旧事实。
