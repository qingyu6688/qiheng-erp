# 优化文档

> 版本：1.0.0　　日期：2026-11-15
> 范围：M0—M7 评审中发现的问题、后台页面 UI 调整，以及继续使用 MySQL 8.0 需要做的保障。
> 用法：按第 6 节的顺序逐项处理，每项做完勾掉并在 `docs/更新日志.md` 记一笔。
> 配套文件：`docs/UI设计规范.md`、`docs/ui/`（后台页面设计稿，入口 `docs/ui/index.html`）。

---

## 1. 总体结论

M0—M7 的核心正确性与设计一致：条件更新 + CHECK 约束、固定加锁顺序、同事务幂等、未结项 + 核销分配、累计法确认应收、期间屏障都已落地，`mvn test` 362 个用例全部通过。

需要处理的问题集中在三类：

1. **环境与脚本**：Windows PowerShell 5.1 下脚本乱码、`.env` 带回车导致启动失败、构建产物越积越多。
2. **数据与文档不一致**：草稿删除实际用了 `is_deleted` 标记，和《数据库设计》2.8 写的不一样；订单行 `reservation_state` 有两处被直接写成 `expired`。
3. **页面体验**：时间显示 UTC 原始字符串（打印单上也是）、菜单平铺 50 多项、列表筛选太少、登录后默认进仓库管理。

没有发现需要回滚已有迁移或推翻已有接口的问题。

## 2. 数据库版本决定

**决定：继续使用 MySQL 8.0（当前 8.0.46），本阶段不升级。**

MySQL 8.0 已在 2026 年 4 月结束官方支持，之后不再有安全补丁。继续使用不影响功能，但要靠部署方式把风险压住，并且现在就避免使用 8.4 不再支持的写法，以后升级时只换版本、不改代码。具体措施见 O-01。

## 4. 优化项明细

### O-01 MySQL 8.0 运行保障与升级预留（P1）

**现状**：本地和测试都是 8.0.46；8.0 已停止官方支持。

**要做的事**

1. **锁定版本**：部署文档写明 MySQL 8.0.46，Docker 镜像用完整标签 `mysql:8.0.46`，不要用 `mysql:8` 或 `latest`。
2. **不暴露到公网**：3306 只监听内网或 `127.0.0.1`，防火墙只放行应用服务器；远程维护走跳板机或 SSH 隧道。
3. **账号分权**：应用账号只给 `SELECT, INSERT, UPDATE, DELETE`；迁移账号见 O-04；`root` 禁止远程登录。
4. **连接加密**：跨主机连接开启 TLS，JDBC 加 `sslMode=REQUIRED`；同机部署可以不开。
5. **备份与恢复演练**：每天全量 + binlog 增量，保留 7 天；每月至少做一次恢复到新库并跑 `mvn test` 中的一致性检查，记录到 `docs/部署说明.md`。
6. **为升级留路**（现在就遵守，以后升级 8.4 时不改代码）：
   - 账号使用 `caching_sha2_password`，不要新建 `mysql_native_password` 账号（8.4 默认禁用）。
   - 字符集保持 `utf8mb4` + `utf8mb4_0900_ai_ci`（现状已如此，迁移中的建表语句全部一致）。
   - 不使用 `SQL_CALC_FOUND_ROWS` / `FOUND_ROWS()`、`FLOAT(M,D)`、整数显示宽度（`TINYINT(1)` 作布尔除外）。
   - `ON DUPLICATE KEY UPDATE` 改用行别名写法，见 O-08。
7. **试跑新版本**：每个里程碑结束时，用 `mysql:8.4` 镜像起一个临时库，跑一次 `mvn test`，有失败就记到本文档，不要求修完才能发版。

**验收**：部署文档有版本、端口、账号、备份四项说明；8.4 试跑结果记录在案。

### O-02 `scripts/project.ps1` 在 Windows PowerShell 5.1 下乱码（P1）

**现状**：脚本是不带 BOM 的 UTF-8，Windows PowerShell 5.1 按系统代码页（GBK）读取，中文提示变乱码，部分字符串被截断导致解析失败。评审时只能绕过脚本直接运行 `mvn`。

**改法**（二选一，推荐第一种）

- 把 `scripts/project.ps1` 另存为 **UTF-8 with BOM**；`.editorconfig` 中给 `*.ps1` 单独设置 `charset = utf-8-bom`，防止以后被编辑器改回去。
- 或者在《部署说明》《环境检查》里写明只支持 PowerShell 7（`pwsh`），脚本开头加版本检查，低于 7 时给出中文提示并退出。

**验收**：在 Windows PowerShell 5.1 中执行 `.\scripts\project.ps1 test`，提示文字正常，测试能跑起来。

### O-03 `ERP_NODE_ID` 带回车时启动失败（P0）

**位置**：`erp-server/src/main/java/cn/erp/shared/Ids.java:17`

```java
long node = Long.parseLong(System.getenv().getOrDefault("ERP_NODE_ID", "0"));
```

**现状**：`.env` 是 CRLF 换行时，用 Git Bash 或 `source` 方式加载，值会变成 `"0\r"`，`parseLong` 抛 `NumberFormatException`，整个应用起不来，报错信息也看不出是换行问题。

**改法**

1. 读取后先 `strip()`，空字符串按默认值处理。
2. 解析失败时也抛出带中文说明的异常，与现有范围检查合并为一句：`ERP_NODE_ID 须为 0 到 1023 之间的整数，当前值为 "..."`（现在非数字时只抛原始 `NumberFormatException`）。
3. 仓库根目录 `.gitattributes` 增加 `.env* text eol=lf`；`.env.example` 统一 LF。

**验收**：补单元测试，覆盖 `"0\r"`、`" 3 "`、`""`、`"abc"`、超出范围五种输入；前两种正常解析，后两种给出清晰错误。

### O-04 Flyway 迁移使用独立账号（P1）

**现状**：`application.yaml` 中 Flyway 与应用共用同一个数据源账号，应用账号因此需要 `CREATE`、`ALTER`、`DROP` 权限。

**改法**

1. 新增环境变量 `DB_MIGRATION_USER`、`DB_MIGRATION_PASSWORD`，配置 `spring.flyway.user` / `spring.flyway.password`；未设置时回退到应用账号，保证本地开发不受影响。
2. 生产环境：迁移账号有 DDL 权限，应用账号只有 DML 权限。
3. 《部署说明》写明两个账号的授权语句（不写真实密码）。

**验收**：用只有 DML 权限的应用账号 + 迁移账号启动成功；只用 DML 账号且有待执行迁移时，启动失败并提示缺少迁移账号。

### O-05 草稿删除方式与《数据库设计》2.8 不一致（P1）

**现状**：《数据库设计》2.8 写的是“不做软删除，草稿物理删除”。实际 `V15__sales_permissions.sql`、`V20__purchase_permissions.sql` 给 `sales_order`、`sales_order_line`、`purchase_order`、`purchase_order_line`、`purchase_requisition` 加了 `is_deleted`，删除草稿时置 1。

**判断**：代码的做法可以接受。草稿单号已经分配，标记删除后单号不回收，不会出现 2.8 担心的“同号出现两次”；而且审计能直接关联到原记录。问题只是文档没跟上。

**改法**

1. 更新《数据库设计》2.8：改为“单据草稿用 `is_deleted` 标记删除，单号不回收；主数据停用；已过账单据永不删除”，列出这 5 张表。
2. 检查所有查询这 5 张表的地方都带了 `is_deleted = 0`（列表、详情、导出、报表、关账检查、来源单据选择）。可以先用 `grep -rn "FROM sales_order\b"` 之类逐个核对。
3. 其他单据（发货、收货、退货、调拨等）草稿目前怎么删的，在文档里一并写清楚，保持一种做法。
4. **不要修改** V15、V20，需要调整只新增迁移。

**验收**：文档与代码一致；补一个测试：删除草稿后，列表、详情、导出、关账检查都看不到它。

### O-06 订单行 `reservation_state` 被直接写成 `expired`（P0）

**位置**

- `erp-server/src/main/java/cn/erp/fulfillment/ShipmentService.java:193`：签收有差异时 `reservation_state=IF(? > 0,'expired',reservation_state)`
- `erp-server/src/main/java/cn/erp/reversal/ReversalProgress.java:55`：冲销发货时无条件 `reservation_state='expired'`

**问题**：`sales_order_line.reservation_state` 是预留表的投影，应当由预留记录推导。这两处直接改写投影，会出现：

- 签收少收时，预留并没有到期（发货时已经消耗或仍有剩余），订单行却显示“已过期”，页面和“预留到期”相关的统计都会误导业务员；
- 冲销发货后订单行可以重新预留（`reserveAll` 会补足），但在下一次预留动作之前，状态一直显示过期。

**改法**

1. `ReservationService.java:127` 释放预留时已经按预留记录推导行状态（还有剩余 → `reserved`；到期 → `expired`；其他 → `released`）。把这段逻辑抽成一个方法（例如 `refreshLineState(scope, orderLineId)`），改为直接查询该行的 `inventory_reservation` 记录来推导：有 `active` 记录 → `reserved`；最后一条以到期结束 → `expired`；以发货消耗、关闭或手工释放结束 → `released`；没有记录 → `none`。只用现有四个枚举值，不新增。
2. 签收、冲销、预留、释放、到期任务结束时都调用它，删掉上面两处直接赋值。
3. 方法放在现有加锁顺序的“预留”一层之后执行，不额外加锁。

**验收**：补回归测试——

- 订单 10 件、发货 10 件、签收 8 件：订单行状态与预留记录一致（此例为 `released`），不为 `expired`；
- 发货后冲销：订单行状态与预留表一致；
- 到期任务把预留置为过期后：状态为 `expired`。

### O-07 `dist/assets` 旧文件不清理（P1）

**现状**：`erp-web/dist/assets` 已累积 294 个文件，其中 4 个 547 KB 的 `index-*.js` 是不同次构建留下的。原因是项目同时通过 `F:\projects\erp` 目录联接访问，Vite 判断 `outDir` 不在项目根目录内时不会自动清空。

**改法**

1. `vite.config.ts` 增加 `build: { emptyOutDir: true }`。
2. 部署脚本复制 `dist` 前先删除目标目录，避免旧文件被 Nginx 继续提供。
3. 构建和部署统一从一个路径执行（建议 `F:\projects\erp`），写进《环境检查》。

**验收**：连续构建两次，`dist/assets` 中只有一份 `index-*.js`。

### O-08 `ON DUPLICATE KEY UPDATE ... VALUES()` 已废弃（P2）

**位置**：`erp-server/src/main/java/cn/erp/accounting/LedgerProjectionHandler.java:42`

`VALUES(col)` 写法从 8.0.20 起标记为废弃，8.0 和 8.4 仍可用但会产生警告。改用行别名：

```sql
INSERT INTO ledger_balance(...) VALUES(?, ...) AS new
ON DUPLICATE KEY UPDATE opening_balance = new.opening_balance,
  debit_amount = debit_amount + new.debit_amount,
  credit_amount = credit_amount + new.credit_amount,
  projected_journal_id = GREATEST(projected_journal_id, new.projected_journal_id)
```

**验收**：现有总账投影测试全部通过；`SHOW WARNINGS` 不再出现废弃提示。

### O-09 补齐时间格式化工具和测试（P2，O-10 的前置）

**现状**：`erp-web/src/utils/format.ts` 只有金额、单价、数量的格式化，没有时间格式化，各页面直接输出接口返回的 UTC 字符串。

**改法**：在 `format.ts` 中新增：

| 函数 | 输出 | 用于 |
|---|---|---|
| `formatDateTime(value)` | 同年 `MM-DD HH:mm`，跨年 `YYYY-MM-DD HH:mm` | 列表、详情 |
| `formatDateTimeSeconds(value)` | `MM-DD HH:mm:ss`，跨年带年份 | 审计 |
| `formatPrintTime(value)` | `YYYY-MM-DD HH:mm` | 打印 |
| `formatRelativeTime(value, now)` | 今天 `HH:mm`、昨天 `昨天 HH:mm`、更早同 `formatDateTime` | 工作台 |

要求：输入为空或无法解析返回 `—`；不引入新依赖，用 `Intl.DateTimeFormat`；`now` 作为参数传入便于测试。业务日期（`businessDate`、`signDate` 等只有日期的字段）保持原样，不做时区换算。

**验收**：`tests/format.test.ts` 覆盖同年、跨年、跨零点、空值、非法值，覆盖率不低于 80%。

### O-11 首屏包 547 KB，按依赖拆分（P2）

**验收**：首屏入口文件小于 300 KB（未压缩），构建无体积警告，所有页面正常打开。

### O-13 新增工作台（P1）

**现状**：`router/index.ts:29` 的 `home` 路由进入 `WarehousePage.vue`，登录后先看到仓库管理，对大部分角色没用。

**改法**

1. 新增 `pages/WorkbenchPage.vue`，`home` 路由指向它；`defaultWorkspace` 相应调整。
2. 新增接口 `GET /api/v1/workbench/summary`，一次返回：待审批订单数、签收超期数、待确认收付款数、库存不足 SKU 数，以及待办前 10 条。后端按当前用户权限和仓库范围过滤，没有权限的块不返回。
