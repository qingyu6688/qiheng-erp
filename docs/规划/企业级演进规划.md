# 企业级演进规划

> 版本：1.3.0　　日期：2026-11-19
> 范围：从当前的进销存 + 业财一体系统，演进为面向中大型企业的 ERP，并加入 AI 能力（RAG、LLM Wiki、AI 客服等）。
> 前提：数据库继续使用 MySQL 8.0；不推倒重写，在现有模块化单体上扩展。
> 配套文档：《开发计划》《优化文档》2.1.0（未完成的技术优化，O 编号）、《容量测试报告》《运维手册》《部署说明》《业务规则》《数据库设计》《接口设计》。差距项用 G 编号，见第 1.2 节；解决方案与分期见第 7 节。

### 1.2 离“企业级 ERP”还差什么

功能面已经比较全，差距主要在**没有经过真实环境验证**、**合规与安全治理**、**可用性证据**，以及少数财务和集团能力。

## 2. 总体原则

1. **继续模块化单体。** 先用 Spring Modulith（测试依赖已引入）把各业务包（2.0 时为 54 个）的边界验证起来，模块之间只通过公开服务和领域事件交互。只有当某个模块的扩缩容需求、发布节奏或团队归属明显不同（例如 AI 服务、报表分析、开放平台网关）时，才拆成独立服务。
2. **业务事实不可变。** 新增的财务、生产、质检模块都遵守“草稿可改、过账后只能冲销”的规则，继续使用现有的幂等、加锁顺序和期间屏障。
3. **读写分离。** 业务库只承担交易；报表、BI、AI 检索走只读副本或分析库，不在交易库上跑大查询。
4. **平台能力先于业务铺开。** 审批流、自定义字段、编码规则、消息中心这几样做好后，每个新业务模块的开发量会明显下降。
5. **AI 只做建议和草稿，不直接过账。** 所有写操作仍然走现有命令、权限和两人复核。

## 3. 平台层建设

按依赖顺序排列，前面的是后面的基础。

### 3.1 技术底座

| 方面 | 建议 |
|---|---|

## 5. AI 能力规划

### 5.1 整体架构

现有独立服务 `erp-ai` 承担模型调用、知识检索和评测，业务服务负责数据权限与命令校验。

```text
浏览器 / 企业微信 / 客户门户
        │
        ▼
   Nginx ──► erp-server（现有，业务与权限）
        │          ▲
        ▼          │ 以当前用户身份调用只读查询和“生成草稿”接口
     erp-ai ───────┘
      ├─ 模型网关：多模型路由、限流、计费、审计
      ├─ 知识库：文档解析、切分、向量化、LLM Wiki 维护
      ├─ 检索：OpenSearch（关键词 + 向量混合检索）+ 重排
      ├─ 工具层：把 ERP 接口包装成受控工具
      └─ 评测与反馈
```

**技术选型建议**：`erp-ai` 用 Java 21 + Spring AI，与主服务同一技术栈，团队不用维护第二种语言；文档解析用 Apache Tika。如果团队有 Python 经验、需要更多现成的 RAG 组件，也可以用 Python FastAPI，两者对外接口相同。

### 5.2 模型选择与合规

| 场景 | 建议 |
|---|---|
| 境内部署、处理客户和经营数据 | 使用已完成备案的国内大模型服务，或私有化部署开源模型（推理用 vLLM）。面向公众提供生成式 AI 服务（如对外 AI 客服）需符合《生成式人工智能服务管理暂行办法》，上线前做内容安全审核和备案评估 |
| 海外子公司、或数据可出境的场景 | 可接入 Claude：复杂分析和多步工具调用默认用 `claude-opus-5-5`；对话量大、需要压成本的路由在评测通过后可改用 `claude-sonnet-5-5`；意图分类、字段抽取这类简单任务可用 `claude-haiku-5-5`。三者都支持 100 万 token 上下文、工具调用、文档引用和提示缓存 |
| 向量模型与重排 | 中文效果好的开源模型私有化部署（如 bge-m3 + bge-reranker 系列），向量不出内网 |

模型网关必须做到：**换模型只改配置**；按租户统计 token 用量和费用；每次调用记录模型、输入摘要、工具调用和结果（不记录完整敏感字段）；单租户日额度上限。

### 5.3 知识分三层，业务数据不进向量库

| 层 | 内容 | 用法 |
|---|---|---|
| 制度与产品知识 | 用户手册、业务规则、操作 SOP、常见问题、产品资料、合同模板 | RAG 检索 + LLM Wiki |
| 企业私有文档 | 上传的合同、报价、技术规格、内部通知 | RAG 检索，按文档 ACL 过滤 |
| 实时业务数据 | 订单、库存、应收、单据状态 | **不做向量化**，通过工具实时查询，沿用当前用户的权限和数据范围 |

第三层最重要：把业务数据塞进向量库，会绕开字段权限和仓库范围，而且数据很快过时。模型只能通过“查询工具 → ERP 接口 → 权限校验”拿到业务数据。

### 5.4 RAG 设计

1. **入库**：上传 → 类型和大小校验（沿用附件规则）→ Tika 解析 → 按标题层级切分（保留章节路径）→ 向量化 → 写入 OpenSearch。每个片段带租户、组织、可见角色、来源文档、版本、页码。
2. **检索**：关键词（中文 IK 分词）+ 向量混合召回 → 按当前用户的租户和 ACL 过滤 → 重排取前 5—8 段。
3. **生成**：回答必须带引用（文档名 + 章节 / 页码），找不到依据时明确说“知识库中没有相关内容”，不编造。
4. **更新**：文档新版本上传后旧片段失效；删除文档同时删除片段和 Wiki 中的引用。
5. **隔离**：OpenSearch 按租户分索引或强制租户过滤条件，检索层不信任前端传入的租户号。

### 5.5 LLM Wiki

RAG 每次从原始片段里临时拼答案，同一个问题不同人问可能得到不一致的说法。LLM Wiki 的做法是：**让模型把原始资料预先整理成一套结构化、互相链接的知识页面，并持续维护**，问答优先查 Wiki，再回溯原文。

| 环节 | 做法 |
|---|---|
| 生成 | 新资料入库后，由后台任务让模型更新相关主题页（如“销售退货流程”“信用额度规则”），每页有摘要、正文、相关页面链接和引用来源 |
| 审核 | 模型生成或修改的页面先进入“待审核”，由知识管理员确认后发布；页面保留版本历史，可回滚 |
| 维护 | 定期“体检”：找出互相矛盾的说法、失效链接、引用已删除文档的页面、长期无人访问的页面，生成待办给管理员 |
| 问答 | 先检索 Wiki 页面，命中后附原文引用；Wiki 没覆盖时退回普通 RAG，并把高频未覆盖问题加入 Wiki 待写清单 |
| 起步内容 | 现有 `docs/` 下的《业务规则》《用户使用手册》《运维手册》可以直接作为第一批资料 |

这样做的好处是：答案口径统一、可审核、可追溯，员工也能直接浏览 Wiki，而不只是通过对话框。

### 5.7 安全与边界

1. **权限不外溢**：AI 调用 ERP 接口时使用当前用户的身份（或客户门户用户的受限身份），所有权限、数据范围、字段级权限照常生效；AI 服务本身不持有超级账号。
2. **只读优先，写操作只到草稿**：A-04 生成的是草稿；任何提交、审批、过账、付款都由人在原页面上点击完成，两人复核规则不变。
3. **提示注入防护**：知识库文档、客户输入、邮件内容都当作数据，不当作指令；工具调用参数做 schema 校验；对外客服的工具清单单独配置，比内部助手更少。
4. **数字不让模型算**：金额、数量、库存只展示接口返回值，和现在“前端不自行计算”的原则一致。
5. **审计**：会话、工具调用、引用来源、用户反馈全部落库，可按用户、客户、时间查询；敏感字段在日志中脱敏。
6. **人工兜底**：对外客服遇到投诉、退款金额争议、置信度低的问题直接转人工。

### 5.9 评测

AI 功能上线前必须有评测集，没有评测集的改动不发布。

- **知识问答**：200 条以上真实问题 + 标准答案 + 应引用的文档，指标为答案正确率、引用准确率、该拒答时的拒答率。
- **查数和单据解释**：每个工具 20 条以上问法，校验选对工具、参数正确、结果与报表一致。
- **AI 录单**：100 份以上真实单据样本，按字段统计抽取准确率。
- **AI 客服**：越权测试（问别的客户的数据）、提示注入测试、转人工触发测试，必须 100% 通过。
- 线上持续收集点踩样本，每月补充进评测集。

### 7.2 阶段 A：发布前加固

**G-05 CI 安全扫描**

- **依赖漏洞扫描**：在 `verify.yaml` 新增 `security-scan` 作业。
  - 使用实际解析的 Maven 运行依赖与 npm 生产锁文件生成 CycloneDX SBOM，统一用 Trivy 检查。官网扫描随其源码与锁文件接入本仓。
- **静态扫描**：CodeQL 检查 Java 和 JavaScript / TypeScript。安全作业依据结果的严重级别阻断高危告警，并保留可复查的报告。
- **合并门禁**：对 `main` 启用 PR 和必须通过的构建回归、公开仓库检查及安全作业。现有依赖例外逐项固定告警、组件和版本，登记原因、处理计划及到期日期。
- **交付**：候选包附同一源码的 SBOM 和 SHA-256；扫描工具版本、依赖版本和验收结果可追溯。

**G-06 日志留存与审计封存**

- 应用滚动天数和容量上限由部署配置决定。网络日志、应用日志、审计日志按用途和适用的保留要求分别配置，验收以实际最早可检索记录及容量测算为准。
- 审计记录至少在线保留一年，后续归档时保留摘要、成员与外部检查点。封存按租户执行，由事务锁串行生成批次，逐批选择已提交且没有成员记录的审计行。批次摘要和成员同事务写入。
- 审计表和封存结果表的运行权限限定为查询和追加。运维工具逐批校验摘要、成员、记录及前一批链接，记录未封存数量，在独立存储每日保留核验通过的检查点。
- 验收覆盖迟提交、双 Worker、失败后续跑、缺失或被修改的记录、多租户隔离和外部检查点核对。启用目标环境后补做留存与外部存储恢复验收。

**G-07 密码与会话策略**

- **策略配置**：新增迁移文件，建两张表。
  - `password_policy`：按租户配置，包括最小长度（默认 10）、字符类别数（默认 3）、历史条数（默认 5）、有效天数（默认 90，0 表示不过期）和空闲超时分钟数（默认 30）。
  - `password_history`：保存最近 N 个 BCrypt 哈希。
- **密码校验**：
  - `CredentialsService` 改为读取策略，替换写死的 `MIN_PASSWORD_LENGTH`。
  - 改密时比对历史密码，并检查常见弱密码字典（约 1 万条，随代码打包）。
- **过期处理**：登录成功但密码已过期时，接口返回“需修改密码”状态，前端强制进入改密页。
- **空闲超时**：`SessionAccount` 记录最近一次活动时间，过滤器按策略判断，超时就注销会话。现有的 12 小时绝对超时保持不变。
- **兼容**：升级后老用户不会立刻被要求改密，从策略启用之日起算有效期。
- **验收**：集成测试覆盖长度、类别、历史、弱密码、过期和空闲超时。

**G-13 RPO / RTO 目标**

先定目标，到 B 阶段再验证。

| 档位 | RPO | RTO | 前提 |
|---|---|---|---|
| 标准（单机） | ≤ 15 分钟 | ≤ 1 小时 | 每日全量备份，binlog 每 5—10 分钟同步到另一台机器 |
| 高可用 | ≤ 1 分钟 | ≤ 15 分钟 | MySQL 半同步复制，主备切换有脚本、有演练 |

- 目标写入《运维手册》和《部署说明》。
- `recovery-drill.ps1` 在输出中对照目标，直接给出“通过”或“不通过”。

**G-08 第一步：漏洞报告渠道**

- 根目录新增 `SECURITY.md`，写明受支持的版本、报告方式和响应时限（3 个工作日内确认收到）。
- 在仓库设置中开启 Private vulnerability reporting 和 Secret scanning push protection。

### 7.3 阶段 B：真实环境验证与发布 2.0.0

单机档准备符合《部署说明》资源预算的应用、数据库、Redis、监控及独立负载机。高可用档另外演练下列拓扑：

- 应用节点两台。
- MySQL 主备两台。
- Redis Sentinel 三个节点，可以和应用同机。
- 独立的负载机一台。
- 监控机一台。

**单机档发布门槛**：阶段 A 安全及回归检查通过。目标环境容量与恢复达标，监控和告警接收验证通过，客户副本两轮升级和停写回退通过，两周业务试运行八类对账零差异。明确目标环境负载与版本、包摘要、维护窗口、验收人，发布说明注明范围。

**高可用档发布门槛**：在单机档对应的验收项基础上，应用、MySQL 和 Redis 切换实测达到 G-13 的高可用 RPO / RTO。未验收高可用时发布说明按单机档承诺。

G-02 将工作流、PDA 和总账分别记录真实场景、负载、通过阈值和证据。120 万张凭证长跑单独排期，作为大容量总账交付门槛，单机档仅承诺已实测规模。若签约工作负载要求该规模，长跑通过后验收该客户。

**G-01 容量验收**

- 在负载机上运行 `scripts/load/run-capacity.ps1`（k6 `capacity.js`）。
- 验收口径沿用《容量测试报告》：1000 RPS 查询的 P95、额定完成次数、零丢弃和错误率。
- 没通过时，先定位瓶颈（连接池、慢 SQL、GC、Nginx 连接数），调整后复测。未达标轮次保留。业务方核准更改容量档位时，先记录变更后的容量承诺与验收线，再按该口径完整复测。
- 结果作为新章节补进《容量测试报告》。

**G-02 新模块压测**

- 脚本：
  - `workflow-sales.mjs`：审批流。
  - `wms-picks.mjs`：PDA 拣货。
  - `gl_capacity.py`：总账，12 期 × 每期约 10 万张凭证。
  - `s09_trade.py`：购销单组。
- 重点观察：
  - 总账结账耗时。
  - 待办查询的 P95。
  - 拣货并发冲突率。
  - 造数后八类对账是否仍为零差异。

**G-12 高可用演练**

- 逐项演练并记录中断时长和数据丢失量：
  - 停一台应用节点：Nginx 摘除该节点，会话不丢。
  - 停 Redis 主节点：Sentinel 自动切换。
  - MySQL 主库故障：按《运维手册》人工切换，依次提升从库、切换连接、把旧主重建为从库。
- 2.0.0 保持人工切换，但切换步骤要脚本化，并有演练记录。
- 2.1 评估 MySQL InnoDB Cluster（Group Replication + MySQL Router）实现自动故障转移。
- **验收**：每项演练结果都满足 G-13 定的目标。

**G-14 可观测性落地**

- **部署**：用 `install-observability.ps1` 和 `compose.observability.yaml` 部署，再用 `verify-observability.py` 验证。
- **告警规则**：
  - 接口 5xx 比例、P95。
  - 数据库连接池使用率、复制延迟。
  - 磁盘余量。
  - 备份失败。
  - Outbox 积压、Worker 租约丢失。
  - 证书到期。
- **告警出口**：Alertmanager 接入企业微信机器人或邮件。
- **值班流程**：在《运维手册》中写明谁接告警、多久内响应、什么情况下升级处理。

**G-21 试运行与正式发布**

- **试运行**：经授权后使用一家意向客户的最小数据副本。导入前确认脱敏、隔离、访问权限、备份加密和到期清理要求。导入期初后回放或并行运行两周，要求八类对账零差异。
- **发布流程**：
  1. 以阶段 A 通过的提交和候选包记录作为基线。
  2. 按升级指南在客户副本完成两轮 1.x → 2.0 升级和停写回退，按部署档完成验收。
  3. 由已验收的源码提交创建 `v2.0.0` 标签。代码或依赖变化时重验受影响范围。
  4. 发布部署包，附 SHA256 和 SBOM。
  5. 更新《更新日志》。
  6. 官网 `VERSION` 改为 `2.0.0`。

### 7.4 阶段 C：合规

**G-08 等保 2.0 三级与渗透测试**

- **自查**：对照 GB/T 22239—2019 第三级要求，检查应用和数据相关的条目：
  - 身份鉴别。
  - 访问控制。
  - 安全审计。
  - 入侵防范。
  - 数据完整性和保密性。
  - 备份恢复。
- **威胁建模**：用 STRIDE 分析登录、开放平台、客户门户、AI 查数、文件上传和批量导入，结论写进 `docs/设计/`。
- **渗透测试**：每年一次第三方测试，大版本发布前加做一次。高危问题 30 天内修复。
- **公开范围**：自查和测试中发现、但尚未修复的问题不写进公开仓库，修复后再在《更新日志》中说明。
- **职责划分**：系统定级、备案和测评由使用单位负责；项目提供部署侧配置清单和证据材料。

**G-09 个人信息保护**

- **字段清单**：梳理含个人信息的字段，包括联系人姓名、手机号、地址、门户用户、员工信息等，在《数据库设计》中标注分级。
- **展示脱敏**：在现有字段权限上增加“脱敏可见”级别，列表默认显示 `138****1234` 这类格式；查看明文时记一条审计。
- **导出管控**：
  - 导出含个人信息的数据需要单独权限，文件带导出人和时间水印，并记审计。
  - 超过阈值的批量导出走审批。
- **权利请求**：新增个人信息请求登记（查阅、更正、删除），流程走现有工作流。导出展示和试运行副本按用途脱敏。原始会计资料按法定留存与个人信息请求的适用条件处理，维持原件完整性并记录访问、限制处理和处置决定。
- **处理记录**：建立个人信息处理活动记录，与 AI 出境审批放在同一个管理页。

**G-10 电子会计档案**

依据《会计档案管理办法》（2015）。

- **归档包**：
  - 会计年度结账后，按年生成归档包。
  - 凭证、账簿、报表导出为 PDF 或 OFD，另附结构化元数据（JSON）；原始发票的 OFD 或 XML 一并放入。
  - 包内带文件清单和 SHA-256，摘要沿用 G-06 的封存链。
- **锁定**：已归档的期间要重新打开时，需要档案管理员额外审批。重新归档时生成新版本，旧版本保留。
- **保管期限**：

  | 资料 | 保管期限 |
  |---|---|
  | 会计凭证、会计账簿 | 30 年 |
  | 月度、季度、半年度财务报告 | 10 年 |
  | 年度财务报告 | 永久 |
  | 银行对账单、纳税申报表 | 10 年 |

  到期鉴定后才能销毁，并留存销毁清单。
- **存储**：写入开启版本控制和对象锁定的对象存储，或刻录到离线介质；每年做一次可读性检测。
- **移交**：提供导出移交包，供单位档案系统接收。

**G-11 第一步：备份与密钥**

- **备份加密**：
  - `backup-local.ps1` 的输出用 AES-256 加密（age 或 OpenSSL），密钥不放在备份所在的机器上。
  - 按 3-2-1 原则至少异地保存一份：3 份副本、2 种介质、1 份异地。
- **密钥管理**：
  - 抽象 `SecretProvider` 接口：默认从环境变量读取，可接入 HashiCorp Vault 或云 KMS。
  - 写明数据库密码、配置加密主密钥、开放平台签名密钥的轮换步骤。
- **敏感字段**：身份证号、银行账号等用信封加密存储；需要精确查询的字段另存 HMAC 盲索引。
- **国密**：按客户要求再做。应用层可选 BouncyCastle 的 SM3 / SM4，国密 TLS 由入口代理承担。

### 7.5 阶段 D：规模治理

**G-03 大表分区与归档**

- **对象**：库存流水、凭证分录、审计日志，以及消息投递、AI 调用这类只追加的日志表。
- **分区**：
  - 先清点对象的入向和出向外键，在无外键的追加日志试行按月 `RANGE` 分区。库存流水被冲销、序列号及 WMS 引用，需单独验证归档后冲销、追溯和跨期对账。
  - MySQL 要求分区列包含在每个唯一键里，所以主键要从 `(id)` 改为 `(id, 分区列)`。按 id 查单行的地方，要么带上分区列，要么接受跨分区查找。
  - 结构变更写成新迁移文件，大表用 gh-ost 或 pt-online-schema-change 在线执行。
- **预建分区**：Worker 每月提前建好下个月的分区。
- **归档**：
  - 流水和分录在会计年度关闭满 2 年后归档；审计日志在线满 1 年后归档。
  - 在同实例验证 `EXCHANGE PARTITION` 的结构限制。异地归档另行传输和校验，由跨期查询入口统一联查。
  - 归档不等于销毁，保管期限按 G-10 执行。
- **验收**：
  - 在 G-02 造出的 12 期数据上，演练分区迁移和一次归档。
  - 归档前后八类对账结果一致。
  - 用 `EXPLAIN` 确认查询只扫描相关分区。

**G-04 分析库**

- **第一步（不增加组件）**：启用已支持的报表只读从库，把驾驶舱和报表查询切过去。
- **第二步（满足触发条件后再做）**：用 Debezium 或 Flink CDC 读取 binlog，写入 Apache Doris，报表和 BI 改查 Doris；每天对交易库和分析库做一次汇总对账。
- **触发条件**：从库上报表查询的 P95 超过 3 秒，或复制延迟经常超过 30 秒。

**G-15 零停机升级**

- **应用**：两个以上节点滚动发布，接口向后兼容一个版本。
- **数据库变更**：按“扩展 → 迁移 → 收缩”三步拆到两个版本。
  - 本版本：先加新列或新表，新代码同时写新旧两处，再回填数据。
  - 下个版本：删除旧列。
  - 大表 DDL 用 gh-ost 执行。
- **迁移审查**：新增规则，同一版本内不得删除或重命名旧代码仍在使用的列。
- **大版本**：仍使用现有的停写升级。
- **验收**：在两节点环境中滚动升级一个小版本，期间持续压测，错误率低于 0.1%。

**G-22 交付体系**

- **版本支持**：每个次版本维护到下一个次版本发布后 6 个月；安全修复覆盖最近两个次版本。写进 `SECURITY.md` 和 README。
- **实施方法**：按 调研 → 方案 → 资料与期初导入 → 培训 → 并行运行 → 上线验收 推进，每一步有模板，导入模板已有。
- **培训材料**：在《用户使用手册》基础上，按销售、采购、仓库、财务、管理员五个岗位整理课件。
- **迁移工具**：把用友、金蝶常见版本导出的科目、往来单位、商品和期初余额，转换成通用导入模板。
- **参考连接器**：开放平台先提供两三个，例如电商订单拉取、物流单号回传。
