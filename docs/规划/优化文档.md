## 1. 长期约定

以下是持续有效的约束，不是待办，新代码都要遵守。

### 1.1 数据库保持 MySQL 8.0

- 版本锁定 8.0.46，镜像和安装包写完整版本号。8.0 已停止官方支持，靠部署方式控制风险：只在内网监听、运行 / 迁移 / 备份账号分离、跨主机连接走 TLS、定期恢复演练。
- 为以后升级 8.4 留路：账号用 `caching_sha2_password`；字符集保持 `utf8mb4` + `utf8mb4_0900_ai_ci`；不用 `SQL_CALC_FOUND_ROWS`、`FLOAT(M,D)`、整数显示宽度（`TINYINT(1)` 作布尔除外）；`ON DUPLICATE KEY UPDATE` 用行别名，不用 `VALUES()`。
- 迁移文件只增不改。

### 1.2 时间

- 数据库存 UTC，接口返回**带时区的** ISO 8601 字符串（以 `Z` 或 `+08:00` 结尾）。
- 前端统一用 `utils/format.ts` 按北京时间显示；只有日期的业务字段（业务日期、签收日期）不做时区换算。

### 1.3 其他

- 金额、数量以字符串传输，前端不自行计算金额。
- 新增查询必须带租户和公司条件，并检查执行计划是否走索引。

## 3. 明细

### O-26 查询固定开销与目标环境容量验收（P1）

2026-11-16 修订：原描述引用早期失败轮；0.8.1 最终交付 JAR 已完成两轮 1000 RPS。本轮保留带 JFR 的失败样本和不带采样的成功对照，针对 SQL 解析热点启用有界驱动缓存，并按当前 M10 产物复验。普通验收与采样轮分别列在《M10本机验收报告》，目标服务器结果仍待补充。

**现状**（《容量测试报告》）：0.8.1 交付 JAR 在 20、200、500 RPS 下 P95 为 21—102ms；1000 RPS 两线程发生器有一轮通过（P95 172ms），但确认轮 P95 542ms、调度丢弃 703 次。报告结论是“需要继续缩减服务端每次请求的固定开销”。

**排查顺序**

1. 加上 O-28 的链路追踪，分别测出一次查询在会话读取（Redis）、权限与范围查询、SQL、JSON 序列化上的耗时。
2. 会话：确认 Spring Session 每次请求只读一次 Redis，且不必要的写回已关闭（`flush-mode`、`save-mode`）。
3. 权限：0.8.1 已把账号、角色、范围合并为一次查询并在同一请求内复用，可以再加一层带版本号的短期缓存（例如 5 秒），撤权时按用户版本号失效，保证撤权仍然及时。
4. 连接池：核对 HikariCP 最大连接数与 MySQL `max_connections`、Tomcat 线程数是否匹配。
5. 在目标服务器（而不是开发机）上复测，发生器与被测服务分机部署。

**验收**：目标服务器上 1000 RPS 连续三轮完成额定请求数、P95 < 500ms、调度丢弃为 0、对账零差异。

2.0 候选已把常见全部门授权改为一次轻量主库查询，权限连接按已确认账号查找角色。授权撤回继续在后续请求生效。2026-11-18 本机取得 20、200、500 RPS 通过记录。1000 RPS 下，最佳三轮 P95 为 388.43–445.63 ms，仍丢弃 935–1,072 次调度。增加至 650 个预分配 VU 后，按相同协议复测也未达到门槛。目标环境分机验收待执行，详见[容量测试报告](../测试/容量测试报告.md)。

后续本机组合候选将实时权限查询的返回行数从约 438 行减至 3 行，并调整了受限范围销售订单列表的索引选择。同一应用进程连续三轮 1000 RPS，各完成 30,001 次请求，端到端 P95 分别为 21、23、21 毫秒，均无调度丢弃、系统错误及对账差异。六条查询的测试范围和构件身份见[容量测试报告](../测试/容量测试报告.md)。正式入口仍需发生器与服务分机验证。

### O-29 报表直接查询交易库（P2）

2026-11-16 修订：第一步代码、本机只读账号、十类主备报表一致性、导出、SQL 归属及复制水位暂停 / 追平已验证。API 与 Worker 必须配置相同的 `ERP_REPORT_*`；未配置的本机环境沿用主库，配置后不可用时返回失败。目标环境配置和真实业务量验收继续保留。实施说明见《M10功能优化实施说明》。

**现状**：十类报表和导出直接查业务库，日期范围最多一年、单次最多 5 万行。数据量上来后，大报表会和交易争抢 IO 与缓冲池。

**改法**：分两步。第一步把报表和导出改走 MySQL 只读备库（主备模板已有），注意复制延迟，在报表顶部显示“数据截至 xx:xx”。第二步，单量明显增长后再引入分析库（binlog → Apache Doris），见《企业级演进规划》3.1 节。

**验收**：报表查询不出现在主库慢查询日志中；报表顶部显示数据截止时间。

### O-31 四个定时任务缺少逐项异常隔离，一项失败会卡住后续处理（P1）

**位置**

| 任务编码 | 代码 | 循环单位 |
|---|---|---|
| `workflow.timeout` | `workflow/WorkflowTimeout.java:35`（`poll`，第 42 行逐个调用 `runOne`） | 到期的审批任务 |
| `workflow.delay` | `workflow/WorkflowDelay.java:25`（`poll`，第 30 行逐个调用 `resume`） | 到期的延迟节点 |
| `crm.pool_reclaim` | `crm/CrmPoolJobs.java:23`（`run`，按公司循环） | 开启公海规则的公司 |
| `wms.replenishment` | `wms/Replenishment.java:176`（`run`，按公司、仓库循环） | 配置了补货规则的仓库 |

**原评审问题**：四个任务曾缺少逐项捕获，一项失败会中断本轮后续处理。当前四处循环均已调用 `JobBatch.run`，原缺陷已修复；后续持续核对异常退避与运行预警，不再把它描述为未实现的代码功能。下列场景和验收标准作为回归依据保留。`inventory.batch-expiry`、`alert.scan` 另有逐项捕获。

**可触发场景**

- 审批超时：某个办理节点配置了“超时自动办理”，而此前某位审批人已被撤权或离职。超时自动办理后流程走到结束回调，`WorkflowRuntime.finished` 校验审批人资格时抛出 `WORKFLOW_REVIEW_INVALID`。此后该租户所有审批的超时提醒、超时驳回 / 终止都不再执行。
- 延迟节点：恢复后下一个节点找不到审批人且空审批策略不是“自动驳回”时抛错，之后所有延迟节点都不再恢复。
- 公海回收、补货：排在前面的某家公司或某个仓库数据异常，排在后面的公司、仓库每次都被跳过。

**改法**：参照 `inventory/InventoryExpiryJob.java:53` 的写法，对每一项单独 `try/catch`：

- 失败项记录原因和次数；审批任务的 `next_remind_at`、延迟节点的 `due_at` 按 5、15、60 分钟退避，不阻塞后续项；
- 连续失败达到阈值时经预警中心通知管理员；工作流失败项在审批中心“流程实例”中标记“自动处理失败”，由管理员转办、退回或终止；
- 本轮有失败项时任务结果记为“部分失败”，便于在定时任务页面发现。

建议在 `JobEngine` 增加一个“逐项执行并汇总失败”的公共方法，以后新增的批量任务统一使用，避免同类问题再出现。

**验收**：每个任务各构造一个必定失败的项和若干正常项，正常项在同一轮内全部处理；失败项按退避时间重试，并产生一条预警。

本轮将定时任务的逐项失败记录接入现有预警扫描。扫描时达到阈值且仍异常的项会生成预警。若此前已恢复，运行日志保留部分失败记录。

### O-35 公开仓库中不能出现部署记录里的服务器信息（P0）

**现状**：GitHub 仓库是公开的。部署环境的地址、管理入口和目录由私有运维记录维护。Git 已忽略本机的 `docs/服务器部署记录.md`。

**改法**：

1. 这份记录不要提交到公开仓库：移到已被忽略的 `.local/` 目录，或者放进私有的运维仓库 / 文档系统。提交到仓库的部署文档只写通用步骤，IP、域名、面板地址用占位符。

**验收**：仓库和历史中没有真实服务器地址；CI 中的密钥扫描对一个故意放入的测试密钥能报错。

### O-36 多个工作树共用同一个测试库和开发库（P1）

**现状**：主工作区和 `codex/upgrade-2.0` 工作树的 `.env` 都把测试库配成 `erp_test`、开发库配成 `erp_dev`。目前 `erp_test` 已被 2.0 分支迁到 V52，而 `main` 和主工作区分支只到 V33，在旧分支上运行 `project.ps1 verify` 会被 Flyway 拒绝（数据库版本高于代码）。《服务器部署记录》中已出现过“测试库 V36 高于源码 V33”的警告。开发库同理：在 2.0 工作树启动一次开发服务，`erp_dev` 就会被迁到 V99，旧分支的开发服务从此无法启动。两个工作树同时跑测试还会互相清数据。

**改法**：

1. 每个工作树使用独立的库：`project.ps1` 已经允许 `erp_test_<后缀>` 形式的测试库名，按工作树或分支配置，例如 `erp_test_main`、`erp_test_v2`；开发库同理。
2. 在《环境检查》中写明“一个工作树一套库”，并给出建库和授权脚本。
3. 可选：`project.ps1` 启动前比较数据库的最高迁移版本和代码中的最高版本，数据库更新时直接给出中文提示并退出。

**验收**：在旧分支和 2.0 分支上交替运行 `project.ps1 verify`，都能通过且互不影响。

本机用旧版 V33 → 当前 V102 → 旧版重复运行了 `project.ps1 verify` 定向仓库集成，每轮 2 项单测和 4 项集成通过，迁移校验摘要一致。独立启动两套开发 API 后，各自读取本库成功、读取异库对象返回 404，数据库账号交叉直读全部拒绝。实际默认服务切换仍需要具备建库和授权权限的账号，见[环境检查](../运维/环境检查.md)。

### O-37 现有目标服务器资源不足以运行 2.0（P1）

**现状**：目标环境同时承载已有服务，可供 ERP 使用的资源待实测，实际配置保存在私有运维记录中。2.0 的完整部署包括 API、Worker、`erp-ai`、OpenSearch（建议 16 GB 内存）、向量与重排模型、Flowable、MySQL 主备和 Redis。

**改法**：

| 阶段 | 建议 |
|---|---|
| 1.0.0 | 单机精简部署：API 与 Worker 合并为一个进程（堆 1—1.5 GB），不启用 AI；MySQL 调小缓冲池；停用旧项目不再需要的服务。上线前按真实单量做一次容量复测（O-26） |
| 1.2.0—1.9.0 | 按启用的模块逐步扩容：工作流和总账主要增加数据库压力；启用 AI 时 `erp-ai`、OpenSearch 和模型服务放到单独的机器 |

### O-38 2.0 迁移中的整表回填没有分批（P2）

**位置**：`V37__department_data_scope.sql`（销售订单、发货、收款、采购订单、收货、付款等 6 张单据表加归属列和索引，各用一条 `UPDATE … LEFT JOIN` 整表回填）、`V38__business_representatives.sql`（同样 6 张表加业务员列并整表回填），以及 V39、V45、V46、V50、V64—V67 等给既有业务表加列、加索引的迁移。

**现状**：这些回填是原 1.x 迁移，最低支持的 2.0 源库已经完成 V87，因而在标准 1.x → 2.0 路径上不重复执行。对早于 V87 的源库，先按对应 1.x 路径单独核对列、索引和回填成本。2.0 升级工具会在独立目标库执行后续迁移，并对备份、恢复、迁移、业务与财务核对的实际停写阶段计时。

**改法**：

1. 在第一次客户数据副本演练记录 V87 后实际执行的迁移和各停写阶段耗时；用目标库的 `flyway_schema_history.execution_time` 核对单个迁移。
2. 如果实际停写窗口不足，按实测瓶颈设计新迁移或在副本预处理，保持原 Flyway 校验和。部门归属与业务员历史事实以单据当时记录为准，0 值是否可回填需依具体数据核对。
3. 对实际执行且耗时的索引迁移评估 `ALGORITHM=INPLACE, LOCK=NONE` 的可行性，以及副本延迟和空间开销。

**验收**：在接近真实规模的数据副本上，2.0 升级的停写时间在业务方批准的窗口内。
